> **শুরুর আগে — Kubernetes আসলে কী?**
>
> কল্পনা করুন আপনি একটা **বিশাল শিপিং পোর্টের ম্যানেজার**। বন্দরে হাজার হাজার **কন্টেইনার** (Docker container) আসছে-যাচ্ছে। প্রতিটা কন্টেইনার কোথায় রাখতে হবে, কোনটা নষ্ট হয়ে গেলে কী করতে হবে, ভিড় বাড়লে কীভাবে সামলাতে হবে — এসব একা হাতে সামলানো অসম্ভব।
>
> **Kubernetes (সংক্ষেপে K8s) হলো সেই স্বয়ংক্রিয় বন্দর ব্যবস্থাপক।** আপনি শুধু বলবেন "আমার এই অ্যাপের ৫টা কপি সবসময় চালু থাকা চাই" — বাকিটা Kubernetes নিজেই সামলাবে।
>
> **Kubernetes-এর মূল দর্শন — Declarative (ঘোষণামূলক):**
> আপনি বলেন না "এটা করো, তারপর ওটা করো"। আপনি বলেন **"আমি এই অবস্থাটা চাই"** (desired state)। Kubernetes নিরন্তর চেষ্টা করে বর্তমান অবস্থাকে সেই কাঙ্ক্ষিত অবস্থায় নিয়ে যেতে।
>
> এটা অনেকটা **এসির থার্মোস্ট্যাটের** মতো — আপনি ২৪° সেট করে দেন, তারপর ঘর গরম হলে এসি নিজেই চালু হয়, ঠান্ডা হলে বন্ধ হয়। আপনাকে প্রতি মিনিটে নির্দেশ দিতে হয় না।

## ১. Container Orchestration ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** এটা কন্টেইনারভিত্তিক অ্যাপ্লিকেশনের **স্বয়ংক্রিয় ডিপ্লয়মেন্ট, স্কেলিং ও ব্যবস্থাপনা** নিশ্চিত করে, যাতে ডেভেলপারদের নিচের অবকাঠামো (infrastructure) নিয়ে চিন্তা করতে না হয়।

**বাস্তব উদাহরণ — অর্কেস্ট্রা:**
"Orchestration" শব্দটা এসেছে **অর্কেস্ট্রা** থেকে। ৫০ জন বাদক আলাদা আলাদা বাজালে হবে কোলাহল। কিন্তু একজন **কন্ডাক্টর** থাকলে — কে কখন শুরু করবে, কে থামবে, কার আওয়াজ বাড়বে — সব সমন্বিত হয়ে সুন্দর সঙ্গীত তৈরি হয়।

Kubernetes হলো সেই কন্ডাক্টর, আর আপনার কন্টেইনারগুলো হলো বাদক।

**Orchestration ছাড়া যা করতে হতো:**

| কাজ | হাতে করলে | Kubernetes-এ |
|---|---|---|
| অ্যাপের নতুন ভার্সন ডিপ্লয় | প্রতিটা সার্ভারে SSH করে ম্যানুয়ালি | `kubectl apply -f deploy.yaml` |
| কন্টেইনার ক্র্যাশ করল | রাত ৩টায় ফোন এল, আপনি রিস্টার্ট করলেন 😴 | নিজে নিজেই রিস্টার্ট হয়ে যায় ✅ |
| ট্রাফিক বেড়ে গেল | নতুন সার্ভার কিনে সেটআপ করুন | HPA নিজেই কপি বাড়িয়ে দেয় |
| একটা সার্ভার মরে গেল | সব কন্টেইনার হাতে সরান | Kubernetes অন্য নোডে সরিয়ে দেয় |

## ২. Kubernetes-এ Pod কী?

**সংজ্ঞা:** এক বা একাধিক Linux কন্টেইনারের একটা গুচ্ছই হলো Pod। এটা Kubernetes অ্যাপ্লিকেশনের **সবচেয়ে ছোট একক**।

```bash
kubectl get pods -n <namespace>
```

**গুরুত্বপূর্ণ:** Kubernetes সরাসরি কন্টেইনার নিয়ে কাজ করে না — সবসময় **Pod** নিয়ে কাজ করে। একটা Pod-এর ভেতরে এক বা একাধিক কন্টেইনার থাকতে পারে।

**বাস্তব উদাহরণ — একটা ফ্ল্যাট:**
- **Pod** = একটা ফ্ল্যাট
- **কন্টেইনার** = ফ্ল্যাটে থাকা মানুষ
- একই ফ্ল্যাটের সবাই **একই ঠিকানা** ভাগ করে (একই IP)
- একই **রান্নাঘর/বাথরুম** ভাগ করে (একই storage volume)
- একজন আরেকজনকে সহজেই ডাকতে পারে (`localhost` দিয়ে)

**Pod-এর ভেতরে কন্টেইনাররা যা ভাগ করে:**
| জিনিস | মানে |
|---|---|
| Network (IP) | একে অপরকে `localhost:পোর্ট` দিয়ে ডাকতে পারে |
| Storage Volume | একই ফাইল পড়তে-লিখতে পারে |
| জীবনচক্র | একসাথে জন্মায়, একসাথে মরে |

**একটা Pod-এ একাধিক কন্টেইনার কখন রাখবেন — Sidecar প্যাটার্ন:**
```yaml
Pod:
  - কন্টেইনার ১: আপনার অ্যাপ (লগ ফাইলে লেখে)
  - কন্টেইনার ২: log-shipper (ঐ ফাইল পড়ে Elasticsearch-এ পাঠায়)
```
দুইজনই একই ফোল্ডার দেখতে পাচ্ছে, তাই সহজেই কাজ হয়ে যাচ্ছে।

**⚠️ Pod সম্পর্কে সবচেয়ে গুরুত্বপূর্ণ কথা — Pod ক্ষণস্থায়ী (ephemeral):**
Pod মরে গেলে সেটা **আর ফিরে আসে না**। Kubernetes একটা **নতুন Pod** বানায়, যার **নতুন নাম, নতুন IP**। তাই কখনোই Pod-এর IP মনে রেখে কাজ করবেন না — এজন্যই **Service** দরকার (৬ নম্বর দেখুন)।

> Pod হলো **ভাড়াটিয়ার মতো** — আসে, যায়। ঠিকানা বদলায়। তাই চিঠি পাঠাতে হলে ভাড়াটিয়ার নাম নয়, **বাড়ির নম্বর** (Service) ব্যবহার করতে হবে।

## ৩. Kubernetes কীভাবে কন্টেইনার স্কেল করে?

Kubernetes তিনভাবে স্কেল করে:

| নাম | কী বাড়ায়/কমায় | উপমা |
|---|---|---|
| **HPA** (Horizontal Pod Autoscaler) | Pod-এর **সংখ্যা** | ব্যাংকে **আরও কাউন্টার** খোলা |
| **VPA** (Vertical Pod Autoscaler) | প্রতি Pod-এর **CPU/মেমরি** | একই কাউন্টারে **আরও দ্রুত কম্পিউটার** বসানো |
| **Cluster Autoscaler** | **নোডের (সার্ভারের) সংখ্যা** | **নতুন শাখা** খোলা |

**তিনটার সম্পর্ক — একটা বাস্তব দৃশ্য:**

দুপুর ১২টা, আপনার ই-কমার্স সাইটে ফ্ল্যাশ সেল শুরু হলো:

```
১. ট্রাফিক বাড়ল → CPU ৮০% ছাড়াল
        ↓
২. HPA: "Pod ৩টা থেকে ১০টা করো" 📈
        ↓
৩. কিন্তু নোডে আর জায়গা নেই! নতুন Pod গুলো Pending অবস্থায় বসে আছে
        ↓
৪. Cluster Autoscaler: "AWS থেকে ২টা নতুন EC2 নোড আনো" 🖥️
        ↓
৫. নতুন নোড এল → Pod গুলো সেখানে বসল → সাইট ঠিকঠাক চলছে ✅
        ↓
৬. রাত ২টা, ট্রাফিক কমল → HPA Pod কমাল → Cluster Autoscaler নোড কমাল → খরচ বাঁচল 💰
```

**HPA-এর একটা উদাহরণ:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        averageUtilization: 70    # CPU ৭০% ছাড়ালে বাড়াও
```

**⚠️ HPA ও VPA একসাথে একই Pod-এ ব্যবহার করবেন না** (CPU/মেমরির উপর) — দুজন দুইদিকে টানাটানি করে গোলমাল বাধায়।

## ৪. Kubelet কী?

**সংজ্ঞা:** Kubelet হলো একটা Kubernetes এজেন্ট, যা **প্রতিটা নোডে চলে**। কন্ট্রোল প্লেন যেভাবে বলেছে, Pod-এর ভেতরের কন্টেইনারগুলো ঠিক সেভাবেই চলছে কিনা সেটা নিশ্চিত করে।

এটা Pod-এর স্বাস্থ্য পর্যবেক্ষণ করে, কন্টেইনারের জীবনচক্র ম্যানেজ করে এবং API সার্ভারের সাথে যোগাযোগ রেখে কাঙ্ক্ষিত অবস্থা বজায় রাখে।

**বাস্তব উদাহরণ — শাখা ব্যবস্থাপক:**
প্রধান কার্যালয় (কন্ট্রোল প্লেন) সিদ্ধান্ত নেয়। প্রতিটা শাখায় একজন **ম্যানেজার** (Kubelet) থাকেন, যিনি:
- প্রধান কার্যালয়ের নির্দেশ মেনে চলেন
- শাখার কর্মীরা (কন্টেইনার) ঠিকমতো কাজ করছে কিনা দেখেন
- কেউ অসুস্থ হলে (কন্টেইনার ক্র্যাশ) নতুন কাউকে বসান
- প্রতিদিন প্রধান কার্যালয়ে রিপোর্ট পাঠান

**Kubelet-এর নির্দিষ্ট কাজগুলো:**
1. API সার্ভার থেকে "এই নোডে কোন Pod চলবে" সেটা জেনে নেয়
2. কন্টেইনার রানটাইমকে (containerd/CRI-O) বলে কন্টেইনার চালু করতে
3. **Liveness Probe** চালায় → "কন্টেইনার কি বেঁচে আছে?" না হলে রিস্টার্ট করে
4. **Readiness Probe** চালায় → "ট্রাফিক নেওয়ার জন্য প্রস্তুত?" না হলে Service থেকে সরিয়ে রাখে
5. নোডের অবস্থা (CPU, মেমরি, ডিস্ক) রিপোর্ট করে

**⚠️ মনে রাখুন:** Kubelet **নিজে কন্টেইনার চালায় না** — সে শুধু কন্টেইনার রানটাইমকে নির্দেশ দেয়। সে ম্যানেজার, কর্মী নয়।

## ৫. StatefulSet ও Deployment-এর পার্থক্য ব্যাখ্যা করুন

**Deployment:** আপনার অ্যাপ্লিকেশনের অবস্থা নিয়ন্ত্রণ করতে দেয় এবং নিশ্চিত করে যে সবসময় সঠিক সংখ্যক কপি (replica) চলছে।

**StatefulSet:** এমন অ্যাপ্লিকেশন সামলাতে কাজে লাগে, যাদের **স্থায়ী স্টোরেজ** এবং **নির্ভরযোগ্য নেটওয়ার্ক পরিচয়** দরকার।

**পার্থক্যের টেবিল:**

| | Deployment | StatefulSet |
|---|---|---|
| Pod-এর নাম | এলোমেলো: `web-7d9f8-x2k4p` | ক্রমিক: `db-0`, `db-1`, `db-2` |
| Pod-এর পরিচয় | কেউ কারও চেয়ে আলাদা নয় | প্রত্যেকের আলাদা পরিচয় |
| স্টোরেজ | সবাই একই বা কোনোটাই নয় | **প্রত্যেকের নিজস্ব** স্থায়ী স্টোরেজ |
| তৈরির ক্রম | সবাই একসাথে | **একে একে**: ০ → ১ → ২ |
| মোছার ক্রম | সবাই একসাথে | **উল্টো ক্রমে**: ২ → ১ → ০ |
| Pod মরে ফিরে এলে | নতুন নাম, নতুন স্টোরেজ | **একই নাম, একই স্টোরেজ** ✅ |
| কীসের জন্য | Stateless অ্যাপ | ডেটাবেজ, কিউ |

**বাস্তব উদাহরণ:**

**Deployment = কল সেন্টারের এজেন্ট 📞**
১০ জন এজেন্ট আছে। কে কোন কল ধরল তাতে কিছু যায়-আসে না — সবাই একই কাজ করে। একজন ছুটি নিলে আরেকজন এলেই চলে। কার নাম কী, সেটা গ্রাহকের জানার দরকার নেই।

**StatefulSet = হাসপাতালের রোগীর বেড 🛏️**
বেড নম্বর ৩-এর রোগীর ফাইল, ওষুধ, রিপোর্ট সব ঐ বেডের সাথেই জড়িত। রোগী পরীক্ষা করে ফিরলে তাকে **আবার বেড ৩-এই** ফিরতে হবে — বেড ৭-এ নয়। কারণ তার সব তথ্য ওখানেই।

**বাস্তব ব্যবহার:**

```
Deployment ব্যবহার করুন:  ওয়েব সার্ভার, API, ফ্রন্টএন্ড, worker
StatefulSet ব্যবহার করুন: MySQL, PostgreSQL, MongoDB, Kafka, Elasticsearch, Redis
```

**StatefulSet কেন দরকার — একটা কংক্রিট উদাহরণ:**

আপনার MySQL-এর ৩টা কপি চলছে — ১টা master, ২টা replica।
- `mysql-0` = master (এখানে লেখা হয়)
- `mysql-1`, `mysql-2` = replica (এরা `mysql-0` থেকে কপি করে)

Deployment ব্যবহার করলে Pod-গুলোর নাম হতো এলোমেলো — কে master সেটা কেউ জানত না! আর Pod মরে ফিরলে **নতুন খালি ডিস্ক** পেত, সব ডেটা হারিয়ে যেত। 💀

StatefulSet-এ `mysql-0` মরে ফিরে এলেও **আবার `mysql-0`-ই হয়** এবং **আগের ডিস্কটাই** ফিরে পায়। ✅

## ৬. Kubernetes-এ Service কী?

**সংজ্ঞা:** Service হলো একটা বিমূর্ততা (abstraction), যা একগুচ্ছ Pod-কে বাইরে প্রকাশ করার জন্য একটা **স্থিতিশীল নেটওয়ার্ক ঠিকানা** তৈরি করে। এর মাধ্যমে বিভিন্ন অংশের মধ্যে যোগাযোগ বা বাইরে থেকে Pod-এ প্রবেশ সম্ভব হয়। এটা নিশ্চিত করে যে ট্রাফিক সব Pod-এর মধ্যে **সমানভাবে ভাগ** হচ্ছে।

**সমস্যাটা যা Service সমাধান করে:**

```
Pod গুলোর IP:  10.1.2.3,  10.1.2.7,  10.1.5.9

Pod একটা ক্র্যাশ করল → নতুন Pod এল → নতুন IP: 10.1.8.4

এখন ফ্রন্টএন্ড কোন IP-তে রিকোয়েস্ট পাঠাবে? 🤔
```

**Service-এর সমাধান:** একটা **স্থায়ী নাম ও IP** দেয়, যেটা কখনো বদলায় না।

```
ফ্রন্টএন্ড → http://backend-service:8080 → [Pod 1] [Pod 2] [Pod 3]
             (এই নাম কখনো বদলায় না)      (এদের IP বদলাতে থাকে)
```

**বাস্তব উদাহরণ — কোম্পানির হটলাইন নম্বর ☎️**

আপনি কোনো কোম্পানিতে ফোন করেন **১৬২৪৭** নম্বরে। এই নম্বরটা বছরের পর বছর একই থাকে। কিন্তু ফোনটা ধরে কে?
- আজ ধরল করিম
- কাল করিম চাকরি ছাড়ল, রহিম ধরল
- ব্যস্ত সময়ে ৫ জন এজেন্ট পালা করে ধরছে

আপনি কখনোই এজেন্টের ব্যক্তিগত নম্বরে ফোন করেন না — সবসময় **হটলাইনে**। Service হলো সেই হটলাইন নম্বর।

**Service কীভাবে Pod খুঁজে পায় — Label Selector দিয়ে:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend          # 👈 যেসব Pod-এ এই label আছে, তাদের কাছে ট্রাফিক যাবে
  ports:
  - port: 8080
    targetPort: 3000
```
যেকোনো Pod-এ `app: backend` লেবেল লাগালেই সে স্বয়ংক্রিয়ভাবে এই Service-এর অংশ হয়ে যাবে।

**DNS দিয়ে খুঁজে পাওয়া:** ক্লাস্টারের যেকোনো Pod থেকে শুধু `http://backend-service` লিখলেই কাজ হয়ে যায়। Kubernetes-এর নিজস্ব DNS (CoreDNS) নামটা IP-তে অনুবাদ করে দেয়।

## ৭. Kubernetes কীভাবে কনফিগারেশন ম্যানেজ করে?

Kubernetes দুইভাবে কনফিগারেশন সামলায়:
- **ConfigMap** → সাধারণ, গোপন নয় এমন ডেটা (যেমন এনভায়রনমেন্ট ভেরিয়েবল)
- **Secret** → সংবেদনশীল তথ্য (যেমন পাসওয়ার্ড, API key)

এগুলো Pod-এ **ফাইল হিসেবে** বা **এনভায়রনমেন্ট ভেরিয়েবল হিসেবে** যুক্ত করা যায়। ফলে ইমেজ আবার বানানো ছাড়াই কনফিগারেশন বদলানো যায়।

**সমস্যাটা কী — কনফিগ ছাড়া যা হতো:**
```dockerfile
# ❌ ভয়ংকর খারাপ
ENV DATABASE_URL="postgres://user:mypassword@prod-db:5432"
```
এখন dev, staging, production — তিন পরিবেশের জন্য **তিনটা আলাদা ইমেজ** বানাতে হবে। আর পাসওয়ার্ডটা ইমেজের ভেতরে চিরকালের জন্য ঢুকে গেল! 😱

**সমাধান — একটাই ইমেজ, আলাদা কনফিগ:**

```yaml
# ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "debug"
  MAX_CONNECTIONS: "100"
  API_URL: "https://api.example.com"
---
# Secret (base64 এনকোডেড)
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
data:
  DB_PASSWORD: bXlwYXNzd29yZA==
```

Pod-এ ব্যবহার:
```yaml
spec:
  containers:
  - name: app
    image: myapp:v1              # 👈 সব পরিবেশে একই ইমেজ ✅
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secret
```

**বাস্তব উদাহরণ:** একটা **টিভি রিমোট**-এর মতো। টিভি (ইমেজ) একটাই, কিন্তু রিমোট (ConfigMap) দিয়ে চ্যানেল, ভলিউম বদলানো যায় — টিভি খুলে ভেতরের তার পাল্টাতে হয় না।

**⚠️ Secret সম্পর্কে খুব গুরুত্বপূর্ণ সতর্কতা:**
Kubernetes-এর Secret ডিফল্টভাবে **এনক্রিপ্টেড নয়** — শুধু **base64 এনকোডেড**! যে কেউ এক কমান্ডেই পড়ে ফেলতে পারে:
```bash
echo "bXlwYXNzd29yZA==" | base64 -d    # mypassword
```

সত্যিকারের নিরাপত্তার জন্য দরকার:
- etcd-তে **encryption at rest** চালু করা
- **RBAC** দিয়ে কে Secret পড়তে পারবে সীমিত করা
- **HashiCorp Vault** বা **Sealed Secrets** ব্যবহার করা
- Secret কখনোই git-এ কমিট না করা

## ৮. Kubernetes-এ Master নোডের ভূমিকা কী?

Master নোড পুরো ক্লাস্টার নিয়ন্ত্রণ করে — **API server, scheduler, controller manager এবং etcd** ম্যানেজ করে।

এটা Pod-এর শিডিউলিং করে, ক্লাস্টারের অবস্থা পর্যবেক্ষণ করে, ওয়ার্কলোড ম্যানেজ করে এবং কনফিগারেশন ডেটা সংরক্ষণ করে।

> **নোট:** আধুনিক Kubernetes-এ "Master Node" শব্দটার বদলে **"Control Plane"** বলা হয়।

**বাস্তব উদাহরণ — এয়ারপোর্টের কন্ট্রোল টাওয়ার 🗼**

| Control Plane অংশ | এয়ারপোর্টে কার মতো |
|---|---|
| **kube-apiserver** | রিসেপশন — সব অনুরোধ এখান দিয়ে আসে |
| **etcd** | রেজিস্টার খাতা — সব রেকর্ড এখানে লেখা |
| **kube-scheduler** | ট্রাফিক কন্ট্রোলার — কোন প্লেন কোন রানওয়েতে নামবে ঠিক করে |
| **kube-controller-manager** | সুপারভাইজার — সব কিছু পরিকল্পনামাফিক চলছে কিনা নজর রাখে |

**পুরো ছবিটা:**
```
┌────────── CONTROL PLANE (মাস্টার) ──────────┐
│  kube-apiserver  ←→  etcd                   │
│         ↕                                   │
│  kube-scheduler   kube-controller-manager   │
└─────────────────────────────────────────────┘
              ↕ (নির্দেশ)
┌─── Worker Node 1 ───┐  ┌─── Worker Node 2 ───┐
│  kubelet            │  │  kubelet            │
│  kube-proxy         │  │  kube-proxy         │
│  [Pod] [Pod] [Pod]  │  │  [Pod] [Pod]        │
└─────────────────────┘  └─────────────────────┘
```

**⚠️ উৎপাদনে (production) সবসময় ৩টা Master নোড রাখুন।** কেন? etcd-এর সিদ্ধান্ত নিতে **সংখ্যাগরিষ্ঠতা (quorum)** লাগে। ৩টা থাকলে ১টা মরলেও বাকি ২টা মিলে সিদ্ধান্ত নিতে পারে। ১টা থাকলে সেটা মরলেই পুরো ক্লাস্টার অচল। 💀

---

## ৯. kube-proxy-এর ভূমিকা কী এবং এটা কীভাবে Pod-এর মধ্যে যোগাযোগ সহজ করে?

**সংজ্ঞা:** kube-proxy প্রতিটা নোডে নেটওয়ার্কের নিয়মকানুন (network rules) ম্যানেজ করে, যাতে Pod-রা একে অপরের সাথে যোগাযোগ করতে পারে।

এটা একটা Service-এর ভেতরে সঠিক Pod-এর কাছে ট্রাফিক পাঠায়, লোড ব্যালেন্সিং নিশ্চিত করে এবং Pod ও বাইরের ক্লায়েন্টের মধ্যে সংযোগ বজায় রাখে।

**বাস্তব উদাহরণ — টেলিফোন অপারেটর 📞**

পুরনো দিনের টেলিফোন এক্সচেঞ্জের কথা ভাবুন। আপনি "১৬২৪৭ নম্বরে দিন" বললে অপারেটর তারটা সঠিক লাইনে জুড়ে দিতেন। kube-proxy সেই অপারেটর — Service-এর ভার্চুয়াল IP-তে আসা রিকোয়েস্টকে আসল Pod-এর IP-তে পৌঁছে দেয়।

**ভেতরে কীভাবে কাজ করে:**

```
অ্যাপ বলল: "backend-service:8080 এ যাও"
        ↓
DNS: "backend-service মানে 10.96.0.15 (ClusterIP)"
        ↓
kube-proxy-এর বানানো iptables নিয়ম:
    10.96.0.15:8080 → এদের যেকোনো একটাতে যাও (এলোমেলোভাবে):
        - 10.1.2.3:3000  (Pod 1)
        - 10.1.2.7:3000  (Pod 2)
        - 10.1.5.9:3000  (Pod 3)
        ↓
রিকোয়েস্ট Pod 2-তে পৌঁছাল ✅
```

**তিনটা মোড:**

| মোড | কীভাবে | পারফরম্যান্স |
|---|---|---|
| **userspace** | পুরনো, kube-proxy নিজেই ট্রাফিক পাস করত | খুব ধীর ❌ |
| **iptables** | Linux-এর iptables নিয়ম বানায় (ডিফল্ট) | ভালো ✅ |
| **IPVS** | Linux-এর IPVS ব্যবহার করে | বড় ক্লাস্টারে দ্রুত ⚡ |

**⚠️ কখন IPVS দরকার:** ১,০০০+ Service থাকলে iptables-এর নিয়মের তালিকা এত লম্বা হয়ে যায় যে প্রতিটা প্যাকেটের জন্য সেটা খুঁজতে সময় লাগে। IPVS হ্যাশ টেবিল ব্যবহার করে, তাই দ্রুত।

## ১০. Kubernetes-এ Ingress ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** Ingress হলো একটা API অবজেক্ট, যা ক্লাস্টারের ভেতরের Service-গুলোতে **বাইরে থেকে প্রবেশ** ম্যানেজ করে — সাধারণত HTTP/HTTPS-এর জন্য।

এটা রাউটিংয়ের নিয়ম ঠিক করে দেয়, ফলে URL দিয়ে Service-এ পৌঁছানো যায়। লোড ব্যালেন্সিং, SSL termination এবং নাম-ভিত্তিক ভার্চুয়াল হোস্টিংও এটা সামলায়।

**সমস্যাটা কী:**

আপনার ৫টা মাইক্রোসার্ভিস আছে। প্রত্যেকটার জন্য আলাদা LoadBalancer বানালে?
```
frontend    → LoadBalancer → $18/মাস + একটা পাবলিক IP
api         → LoadBalancer → $18/মাস + একটা পাবলিক IP
admin       → LoadBalancer → $18/মাস + একটা পাবলিক IP
...
মোট: $90/মাস + ৫টা IP মনে রাখতে হবে 💸
```

**Ingress-এর সমাধান — একটাই প্রবেশদ্বার:**
```
                    ┌─────────────┐
   ইন্টারনেট  ───→   │   Ingress   │  (একটাই IP, একটাই LoadBalancer)
                    └──────┬──────┘
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
    example.com/      example.com/api   admin.example.com
          ↓                ↓                ↓
    frontend-svc      api-svc          admin-svc
```

**বাস্তব উদাহরণ — শপিং মলের মূল ফটক 🏬**

একটা মলে ২০০টা দোকান আছে। প্রতিটা দোকানের জন্য রাস্তা থেকে আলাদা দরজা বানানো হয় না। একটাই **মূল ফটক**, ভেতরে ঢুকে **সাইনবোর্ড** দেখে আপনি নিজের দোকান খুঁজে নেন।

Ingress = মূল ফটক + সাইনবোর্ড ব্যবস্থা।

**একটা উদাহরণ কনফিগ:**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  tls:
  - hosts: [example.com]
    secretName: tls-cert        # 👈 HTTPS এখানেই শেষ হয় (SSL termination)
  rules:
  - host: example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: { name: api-svc, port: { number: 80 } }
      - path: /
        pathType: Prefix
        backend:
          service: { name: frontend-svc, port: { number: 80 } }
```

**⚠️ একটা জরুরি কথা:** শুধু Ingress অবজেক্ট বানালেই কিছু হবে না! আপনার একটা **Ingress Controller** ইনস্টল করা লাগবে — যেমন **NGINX Ingress Controller**, **Traefik**, বা **HAProxy**। Ingress অবজেক্ট শুধু নিয়ম লিখে রাখে, কাজটা করে Controller।

> Ingress = **নিয়মের কাগজ**, Ingress Controller = **সেই নিয়ম মানানোর গার্ড**। গার্ড না থাকলে কাগজে যাই লেখা থাকুক, কিছুই হবে না।

**SSL Termination মানে কী:** HTTPS-এর এনক্রিপশন Ingress-এই খুলে ফেলা হয়, ভেতরে সাধারণ HTTP-তে যায়। ফলে প্রতিটা সার্ভিসে আলাদা সার্টিফিকেট বসাতে হয় না।

## ১১. ConfigMap কী?

**সংজ্ঞা:** ConfigMap হলো একটা API অবজেক্ট, যেখানে **গোপন নয় এমন কনফিগারেশন ডেটা** key-value জোড়া হিসেবে রাখা যায়।

এর ফলে অ্যাপ্লিকেশন কনফিগারেশন তথ্য গতিশীলভাবে ব্যবহার করতে পারে — কন্টেইনার ইমেজের ভেতরে হার্ডকোড করতে হয় না। ফলে কনফিগারেশন ম্যানেজ ও আপডেট করা সহজ হয়।

**তিনভাবে ব্যবহার করা যায়:**

**১) এনভায়রনমেন্ট ভেরিয়েবল হিসেবে:**
```yaml
env:
- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: LOG_LEVEL
```

**২) পুরোটা একসাথে:**
```yaml
envFrom:
- configMapRef:
    name: app-config    # সব key এনভায়রনমেন্ট ভেরিয়েবল হয়ে যাবে
```

**৩) ফাইল হিসেবে মাউন্ট করে (পুরো কনফিগ ফাইলের জন্য সবচেয়ে ভালো):**
```yaml
volumeMounts:
- name: config
  mountPath: /etc/nginx/nginx.conf
  subPath: nginx.conf
```

**পুরো ফাইল রাখার উদাহরণ:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  nginx.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://backend:3000;
      }
    }
```

**⚠️ একটা বড় ফাঁদ — ConfigMap বদলালে Pod নিজে থেকে জানে না!**

| ব্যবহারের ধরন | ConfigMap বদলালে |
|---|---|
| এনভায়রনমেন্ট ভেরিয়েবল | **কিছুই হবে না** — Pod রিস্টার্ট করতে হবে ❌ |
| ভলিউম হিসেবে মাউন্ট | ফাইলটা ~১ মিনিটে আপডেট হবে, কিন্তু **অ্যাপকে সেটা আবার পড়তে হবে** |

**সমাধান:** Deployment-এ একটা annotation-এ ConfigMap-এর হ্যাশ রাখুন — ConfigMap বদলালে হ্যাশ বদলাবে, আর Kubernetes নিজেই rolling restart করবে। (Helm-এ এটা খুব সাধারণ প্যাটার্ন।)

**ConfigMap-এর সীমা:** সর্বোচ্চ **১ MB** ডেটা রাখা যায় (etcd-এর সীমাবদ্ধতা)। বড় ফাইলের জন্য PersistentVolume ব্যবহার করুন।

## ১২. Kubernetes-এ etcd-এর ভূমিকা কী?

**সংজ্ঞা:** etcd হলো একটা **ডিস্ট্রিবিউটেড key-value স্টোর**, যা Kubernetes-এর ক্লাস্টার কনফিগারেশন, অবস্থা ও মেটাডেটার প্রধান ডেটা স্টোর হিসেবে কাজ করে।

এটা নোড, Pod, Service, কনফিগারেশন — ক্লাস্টারের সব তথ্য সংরক্ষণ করে এবং পুরো ক্লাস্টারজুড়ে সামঞ্জস্য (consistency) ও নির্ভরযোগ্যতা নিশ্চিত করে।

**বাস্তব উদাহরণ — সরকারি ভূমি রেজিস্ট্রি অফিস 📚**

কার জমি কোথায়, কে মালিক — সব লেখা থাকে একটা কেন্দ্রীয় খাতায়। কেউ জমি কিনলে সেই খাতায় এন্ট্রি হয়। খাতাটা হারিয়ে গেলে **কেউ প্রমাণ করতে পারবে না কার কী আছে**। 💀

etcd হলো Kubernetes-এর সেই খাতা।

**etcd-তে আসলে কী থাকে:**
```bash
/registry/pods/default/nginx-abc123
/registry/services/default/backend-service
/registry/deployments/production/api
/registry/secrets/default/db-password
/registry/configmaps/default/app-config
```
মানে — **আপনি `kubectl apply` দিয়ে যা কিছু বানিয়েছেন, সব এখানে**।

**etcd-এর বৈশিষ্ট্য:**

| বৈশিষ্ট্য | মানে |
|---|---|
| **Distributed** | কয়েকটা নোডে চলে, একটা মরলেও চলে |
| **Consistent** | Raft অ্যালগরিদম দিয়ে সবাই একই তথ্যে একমত হয় |
| **Watchable** | কোনো কিছু বদলালে সাথে সাথে খবর দেয় (এটাই Kubernetes-এর মূল চালিকাশক্তি!) |

**"Watch" ফিচারটা কেন এত গুরুত্বপূর্ণ:**
```
আপনি: kubectl scale deployment api --replicas=5
        ↓
API server → etcd-তে লিখল: "api-এর replicas = 5"
        ↓
etcd → Deployment Controller-কে জানাল: "কিছু বদলেছে!"
        ↓
Controller: "এখন ৩টা চলছে, ৫টা দরকার → ২টা নতুন Pod বানাও"
        ↓
Scheduler: "এই ২টা Pod কোন নোডে বসবে?"
        ↓
Kubelet: "ঠিক আছে, আমার নোডে কন্টেইনার চালু করছি"
```
কেউ কাউকে সরাসরি ফোন করছে না — সবাই শুধু etcd-এর দিকে তাকিয়ে আছে। ✨

**⚠️ সবচেয়ে গুরুত্বপূর্ণ ব্যবহারিক পরামর্শ:**
```bash
# etcd-এর ব্যাকআপ নিন — নিয়মিত!
ETCDCTL_API=3 etcdctl snapshot save backup.db
```
**etcd হারালে পুরো ক্লাস্টার হারালেন।** নোড ঠিক থাকলেও Kubernetes জানবে না কী চালাতে হবে।

**উৎপাদনে ৩ বা ৫টা etcd নোড রাখুন** (বিজোড় সংখ্যা)। কারণ quorum = (n/2)+1। ৩টায় ১টা মরলে চলবে, ৫টায় ২টা মরলে চলবে।

## ১৩. Deployment-এ Rolling Update কীভাবে কাজ করে?

Rolling update ধীরে ধীরে পুরনো Pod-গুলো নতুন দিয়ে বদলে দেয়, যাতে **downtime যতটা সম্ভব কম** হয়।

Kubernetes নতুন কনফিগারেশনের Pod বানায়, আর একই সাথে নির্দিষ্ট সংখ্যক পুরনো Pod চালু রাখে। নতুন Pod প্রস্তুত ও সুস্থ হলে তবেই পুরনোগুলো বন্ধ করা হয় — ফলে সেবা বিঘ্নিত না হয়ে মসৃণভাবে পরিবর্তন হয়।

**ধাপে ধাপে দেখুন (৪টা Pod, v1 → v2):**

```
শুরু:    [v1] [v1] [v1] [v1]              ← ৪টাই পুরনো
ধাপ ১:   [v1] [v1] [v1] [v1] [v2]         ← ১টা নতুন বানাল
ধাপ ২:   [v1] [v1] [v1]      [v2]         ← নতুনটা প্রস্তুত, ১টা পুরনো মুছল
ধাপ ৩:   [v1] [v1] [v1] [v2] [v2]
ধাপ ৪:   [v1] [v1]      [v2] [v2]
...
শেষ:     [v2] [v2] [v2] [v2]              ← সব নতুন ✅
```
পুরো সময়টা জুড়ে **কমপক্ষে ৪টা Pod সেবা দিয়েছে** — ব্যবহারকারী কিছুই টের পায়নি।

**নিয়ন্ত্রণের সেটিংস:**
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1           # কাঙ্ক্ষিত সংখ্যার চেয়ে সর্বোচ্চ কতগুলো বেশি বানানো যাবে
    maxUnavailable: 0     # সর্বোচ্চ কতগুলো একসাথে অনুপলব্ধ থাকতে পারে
```
`maxUnavailable: 0` মানে — **কখনোই সক্ষমতা কমবে না**, শূন্য downtime। ✅

**বাস্তব উদাহরণ — সেতুর লেন মেরামত 🚧**
৪ লেনের সেতু মেরামত করতে হবে। পুরো সেতু বন্ধ করলে যানজট। তাই **একটা করে লেন** বন্ধ করে মেরামত করা হয়, বাকি ৩ লেন দিয়ে গাড়ি চলতে থাকে। এক লেন শেষ হলে পরেরটা।

**অন্য ডিপ্লয়মেন্ট কৌশল:**

| কৌশল | কীভাবে | Downtime |
|---|---|---|
| **Recreate** | সব পুরনো মুছে, তারপর নতুন | হ্যাঁ ❌ |
| **Rolling Update** | একে একে বদলানো (ডিফল্ট) | না ✅ |
| **Blue-Green** | নতুন পরিবেশ পুরো তৈরি করে ট্রাফিক সুইচ | না, কিন্তু দ্বিগুণ রিসোর্স লাগে |
| **Canary** | ৫% ট্রাফিক নতুনে পাঠিয়ে পরীক্ষা | না, সবচেয়ে নিরাপদ |

**কাজের কমান্ড:**
```bash
kubectl rollout status deployment/api      # অগ্রগতি দেখুন
kubectl rollout history deployment/api     # আগের ভার্সনগুলো
kubectl rollout undo deployment/api        # 🚨 আগের ভার্সনে ফিরে যান!
kubectl rollout pause deployment/api       # মাঝপথে থামান
```

**⚠️ Rolling Update ঠিকমতো কাজ করতে হলে `readinessProbe` অবশ্যই দিন:**
```yaml
readinessProbe:
  httpGet: { path: /health, port: 8080 }
  initialDelaySeconds: 5
```
এটা না দিলে Kubernetes ধরে নেবে কন্টেইনার চালু হওয়ামাত্রই প্রস্তুত — কিন্তু অ্যাপ হয়তো তখনো লোড হচ্ছে! ফলে ব্যবহারকারী এরর পাবে।

## ১৪. Kubernetes-এ Namespace কী?

**সংজ্ঞা:** Namespace হলো ক্লাস্টারের একটা **যৌক্তিক বিভাজন**, যা রিসোর্সগুলোকে দলবদ্ধ ও আলাদা করে রাখতে দেয়।

এর ফলে একাধিক ব্যবহারকারী বা টিম একই ক্লাস্টার ভাগ করে ব্যবহার করতে পারে, অথচ তাদের Pod, Service, Deployment ইত্যাদি গোছানো ও আলাদা থাকে।

**বাস্তব উদাহরণ — একটা বিল্ডিংয়ের বিভিন্ন তলা 🏢**

| Namespace | কার জন্য |
|---|---|
| `production` | আসল ব্যবহারকারীদের অ্যাপ |
| `staging` | পরীক্ষার পরিবেশ |
| `development` | ডেভেলপারদের খেলার জায়গা |
| `monitoring` | Prometheus, Grafana |

সবাই একই বিল্ডিংয়ে (ক্লাস্টার), কিন্তু আলাদা তলায়। ৩ তলার কেউ ৫ তলার জিনিস ভুলে নষ্ট করে ফেলবে না।

**একই নাম বিভিন্ন Namespace-এ থাকতে পারে:**
```
production/api-service    ← আলাদা
staging/api-service       ← আলাদা
```
দুটোই `api-service` নামে, কিন্তু সম্পূর্ণ ভিন্ন জিনিস। ✅

**Namespace-এর আসল উপকারিতা:**

**১) Resource Quota — টিম প্রতি সীমা বেঁধে দেওয়া:**
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    pods: "50"
```
এখন team-a পুরো ক্লাস্টারের রিসোর্স খেয়ে ফেলতে পারবে না।

**২) RBAC — কে কোথায় ঢুকতে পারবে:**
জুনিয়র ডেভেলপারকে `development`-এ পূর্ণ অধিকার দিন, কিন্তু `production`-এ শুধু পড়ার অধিকার।

**৩) DNS-এ আলাদা হওয়া:**
```
একই namespace-এ:    http://backend-service
অন্য namespace-এ:    http://backend-service.production.svc.cluster.local
```

**ডিফল্ট Namespace গুলো:**
| নাম | কী থাকে |
|---|---|
| `default` | namespace না বললে এখানেই যায় |
| `kube-system` | Kubernetes-এর নিজের জিনিস (⚠️ হাত দেবেন না!) |
| `kube-public` | সবাই পড়তে পারে এমন তথ্য |

**⚠️ কোনগুলো Namespace-এর ভেতরে নয়:** Node, PersistentVolume, StorageClass, ClusterRole — এগুলো পুরো ক্লাস্টারের জন্য, কোনো নির্দিষ্ট namespace-এর নয়।

```bash
kubectl get pods -n production            # নির্দিষ্ট namespace
kubectl get pods --all-namespaces         # সব
kubectl config set-context --current --namespace=dev   # ডিফল্ট বদলান
```

## ১৫. Label ও Selector-এর ব্যবহার ব্যাখ্যা করুন

**Label:** এগুলো key-value জোড়া, যা অবজেক্টের (যেমন Pod) সাথে জুড়ে দেওয়া হয় — রিসোর্স গোছানো ও বাছাই করার জন্য মেটাডেটা হিসেবে।

**Selector:** এই label-গুলো দেখে রিসোর্স ফিল্টার ও শনাক্ত করার উপায়। এর মাধ্যমে দলবদ্ধ করা, ব্যবস্থাপনা এবং Service-এর লক্ষ্য নির্ধারণ করা যায়।

**বাস্তব উদাহরণ — জামাকাপড়ের ট্যাগ 🏷️**

দোকানে জামায় ট্যাগ লাগানো থাকে: `সাইজ: L`, `রং: নীল`, `ধরন: শার্ট`।

আপনি বললেন "নীল রঙের সব L সাইজের শার্ট দেখান" — এটাই **Selector**।

**Label লাগানো:**
```yaml
metadata:
  labels:
    app: backend
    tier: api
    env: production
    version: v2
```

**Selector দিয়ে খোঁজা:**
```bash
kubectl get pods -l app=backend                    # সহজ
kubectl get pods -l 'env in (production,staging)'  # একাধিক মান
kubectl get pods -l app=backend,tier=api           # AND শর্ত
kubectl get pods -l 'version!=v1'                  # নয়
```

**Label কেন এত গুরুত্বপূর্ণ — এটাই Kubernetes-এর আঠা:**

```
Service ─── selector: app=backend ───→ যেসব Pod-এ এই label আছে
Deployment ─ selector: app=backend ──→ এই Pod গুলো আমি সামলাই
NetworkPolicy ─ selector: app=backend → এই Pod গুলোর ট্রাফিক নিয়ন্ত্রণ
HPA ────────── target: deployment ────→ এদের সংখ্যা বাড়াই-কমাই
```

**একটা শক্তিশালী বাস্তব ব্যবহার — Canary Deployment:**
```yaml
# Service-এর selector শুধু app দেখছে, version দেখছে না
selector:
  app: myapp

# ৯টা Pod-এ label: app=myapp, version=v1
# ১টা Pod-এ label:  app=myapp, version=v2
```
ফলাফল: **১০% ট্রাফিক নতুন ভার্সনে** যাচ্ছে। সমস্যা হলে ঐ একটা Pod মুছে দিলেই হলো। ✅

**Label vs Annotation:**

| | Label | Annotation |
|---|---|---|
| উদ্দেশ্য | **বাছাই করা** | শুধু তথ্য রাখা |
| Selector-এ ব্যবহার | ✅ হ্যাঁ | ❌ না |
| আকারের সীমা | ৬৩ অক্ষর | অনেক বড় হতে পারে |
| উদাহরণ | `app: backend` | `description: "গত ১২ মে আপডেট হয়েছে"` |

**💡 ভালো চর্চা — স্ট্যান্ডার্ড label ব্যবহার করুন:**
```yaml
app.kubernetes.io/name: myapp
app.kubernetes.io/version: "1.2.0"
app.kubernetes.io/component: backend
app.kubernetes.io/managed-by: helm
```

## ১৬. Kubernetes-এ PV এবং PVC কী?

**Persistent Volume (PV):** এটা একটা স্টোরেজ রিসোর্স, যা **Pod-এর জীবনচক্র থেকে স্বাধীন** স্থায়ী স্টোরেজ দেয়।

**Persistent Volume Claim (PVC):** এটা ব্যবহারকারীর পক্ষ থেকে স্টোরেজের **অনুরোধ** — কত জায়গা লাগবে, কীভাবে ব্যবহার হবে সেটা বলে দেয়। এটা একটা মানানসই PV-এর সাথে যুক্ত হয়ে যায়, ফলে Pod সেই স্টোরেজ ব্যবহার করতে পারে।

**সমস্যাটা কী:**
Pod মুছে গেলে তার ভেতরের সব ফাইলও মুছে যায়! ডেটাবেজের জন্য এটা বিপর্যয়। 💀

**বাস্তব উদাহরণ — গুদাম ভাড়া নেওয়া 🏬**

| | উপমা |
|---|---|
| **PV** | একটা আসল গুদাম ঘর, যেটা বিল্ডিংয়ে আছে |
| **PVC** | "আমার ১০০ বর্গফুট গুদাম দরকার" — এই আবেদনপত্র |
| **StorageClass** | গুদামের ধরন — "শীতাতপ নিয়ন্ত্রিত" নাকি "সাধারণ" |
| **Pod** | ভাড়াটিয়া, যে গুদাম ব্যবহার করে |

ভাড়াটিয়া চলে গেলেও **গুদাম ও তার ভেতরের মাল থেকে যায়**। ✅

**পুরো প্রক্রিয়া:**
```yaml
# ১. ব্যবহারকারী PVC বানায় — "আমার ১০ GB দরকার"
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 10Gi
  storageClassName: gp3
---
# ২. Pod-এ সেটা ব্যবহার
spec:
  containers:
  - name: mysql
    volumeMounts:
    - name: data
      mountPath: /var/lib/mysql
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: mysql-data
```

**Access Mode গুলো:**

| মোড | মানে | উদাহরণ |
|---|---|---|
| `ReadWriteOnce` (RWO) | **একটা নোড** পড়তে-লিখতে পারে | AWS EBS, ডেটাবেজের জন্য |
| `ReadOnlyMany` (ROX) | অনেক নোড শুধু পড়তে পারে | কনফিগ ফাইল শেয়ার |
| `ReadWriteMany` (RWX) | **অনেক নোড** পড়তে-লিখতে পারে | NFS, শেয়ার্ড ফাইল |

**⚠️ সবচেয়ে সাধারণ ভুল:** AWS EBS দিয়ে `ReadWriteMany` চাওয়া। EBS একসাথে **একটা EC2 ইনস্ট্যান্সেই** যুক্ত হতে পারে। RWX লাগলে EFS বা NFS ব্যবহার করুন।

**Dynamic Provisioning — আধুনিক পদ্ধতি:**
আগে অ্যাডমিনকে হাতে হাতে PV বানাতে হতো। এখন **StorageClass** থাকলে PVC বানানোর সাথে সাথেই Kubernetes নিজে ক্লাউড প্রোভাইডার থেকে ডিস্ক নিয়ে PV বানিয়ে দেয়। ✨

**Reclaim Policy — PVC মুছলে ডেটার কী হবে:**
| নীতি | ফলাফল |
|---|---|
| `Delete` | ডিস্কও মুছে যাবে (ডিফল্ট, ক্লাউডে) ⚠️ |
| `Retain` | ডেটা থেকে যাবে, হাতে পরিষ্কার করতে হবে ✅ |

**উৎপাদনের ডেটাবেজে সবসময় `Retain` ব্যবহার করুন** — নাহলে ভুল করে PVC মুছলে সব ডেটা চিরতরে হারাবেন।

## ১৭. DaemonSet ও ReplicaSet-এর পার্থক্য ব্যাখ্যা করুন

**DaemonSet:** নিশ্চিত করে যে ক্লাস্টারের **প্রতিটা নোডে (বা নির্দিষ্ট কিছু নোডে) একটা করে Pod** চলছে। সাধারণত লগিং বা মনিটরিংয়ের মতো পটভূমির কাজে ব্যবহার হয়।

**ReplicaSet:** নিশ্চিত করে যে **নির্দিষ্ট সংখ্যক** একই রকম Pod সবসময় চলছে। মূলত স্কেলিং ও অ্যাপ্লিকেশনের প্রাপ্যতা বজায় রাখতে ব্যবহার হয়।

**মূল পার্থক্যটা এক লাইনে:**
- **ReplicaSet** = "আমার **৫টা** Pod চাই" (কোথায় থাকবে তাতে কিছু যায়-আসে না)
- **DaemonSet** = "**প্রতিটা নোডে একটা করে** Pod চাই" (মোট কয়টা হলো তাতে কিছু যায়-আসে না)

**ছবিতে দেখুন:**

```
ReplicaSet (replicas: 3):
  Node 1: [Pod] [Pod]
  Node 2: [Pod]
  Node 3: (খালি)          ← ৩টা হয়ে গেছে, তাই আর লাগবে না

DaemonSet:
  Node 1: [Pod]
  Node 2: [Pod]
  Node 3: [Pod]           ← প্রতিটা নোডে একটা করে
  (নতুন নোড যোগ হলে সেখানেও স্বয়ংক্রিয়ভাবে একটা বসবে)
```

**বাস্তব উদাহরণ:**

**ReplicaSet = রেস্টুরেন্টের রাঁধুনি 👨‍🍳**
আপনার ৫ জন রাঁধুনি দরকার। কোন রান্নাঘরে কে থাকবে তাতে কিছু যায়-আসে না, মোট ৫ জন হলেই হলো।

**DaemonSet = প্রতি তলার নিরাপত্তারক্ষী 💂**
বিল্ডিংয়ের **প্রতিটা তলায়** একজন করে গার্ড লাগবে। নতুন তলা বানালে সেখানেও একজন লাগবে। মোট কতজন হলো সেটা তলার সংখ্যার উপর নির্ভর করে।

**DaemonSet-এর বাস্তব ব্যবহার:**

| কাজ | কেন প্রতি নোডে দরকার |
|---|---|
| **লগ সংগ্রহ** (Fluentd, Filebeat) | প্রতিটা নোডের লগ ফাইল পড়তে হবে |
| **মনিটরিং** (node-exporter, Datadog) | প্রতিটা নোডের CPU/মেমরি মাপতে হবে |
| **নেটওয়ার্কিং** (Calico, Cilium) | প্রতিটা নোডে নেটওয়ার্ক নিয়ম বসাতে হবে |
| **স্টোরেজ** (Ceph, GlusterFS) | প্রতিটা নোডের ডিস্ক ব্যবহার করতে হবে |

**⚠️ একটা জরুরি কথা — ReplicaSet সরাসরি ব্যবহার করবেন না!**

```
Deployment  ──তৈরি করে──→  ReplicaSet  ──তৈরি করে──→  Pod
```

Deployment ব্যবহার করুন, সে নিজেই ReplicaSet সামলাবে। Deployment-এর বাড়তি সুবিধা: **rolling update ও rollback**। ReplicaSet একা এগুলো পারে না।

**Deployment কীভাবে rollback করে:** নতুন ভার্সনে গেলে সে **নতুন একটা ReplicaSet** বানায়, পুরনোটা `replicas: 0` করে রেখে দেয়। `kubectl rollout undo` দিলে পুরনো ReplicaSet-টা আবার চালু করে দেয়। ✅

## ১৮. বিভিন্ন নোডে থাকা Pod-দের মধ্যে যোগাযোগ কীভাবে হয়?

Kubernetes ক্লাস্টারের Pod-রা ডিফল্টভাবেই **ভেতরের IP ঠিকানা** ব্যবহার করে একে অপরের সাথে কথা বলতে পারে। নিচের কন্টেইনার রানটাইম বা নেটওয়ার্ক প্লাগইন এই যোগাযোগের জন্য একটা **ভার্চুয়াল নেটওয়ার্ক ওভারলে** তৈরি করে দেয়।

**Kubernetes-এর নেটওয়ার্কিং মডেলের তিনটা মূল নিয়ম:**
1. প্রতিটা Pod পায় **নিজস্ব একটা IP**
2. সব Pod **NAT ছাড়াই** একে অপরের সাথে যোগাযোগ করতে পারে
3. নোডেও Pod-এর সাথে NAT ছাড়া যোগাযোগ করতে পারে

মানে — **পুরো ক্লাস্টারটা যেন একটাই সমতল নেটওয়ার্ক**।

**বাস্তব উদাহরণ — শহরের ফোন নেটওয়ার্ক 📱**

ঢাকার একজন চট্টগ্রামের একজনকে ফোন করতে পারে, যদিও তারা আলাদা শহরে। কারণ পুরো দেশে একটাই ফোন নেটওয়ার্ক আছে। Pod-দের ক্ষেত্রেও তাই — আলাদা নোডে থাকলেও একই নেটওয়ার্কে।

**Overlay Network কীভাবে কাজ করে:**

```
Node A (192.168.1.10)              Node B (192.168.1.20)
  Pod-1: 10.244.1.5                  Pod-2: 10.244.2.8
       │                                   │
       └──── প্যাকেট মুড়ে (encapsulate) ────┘
             VXLAN টানেলের মধ্য দিয়ে
```

Pod-1 যখন Pod-2-কে (10.244.2.8) প্যাকেট পাঠায়:
1. CNI প্লাগইন দেখে "10.244.2.x তো Node B-তে"
2. প্যাকেটটাকে আরেকটা প্যাকেটের ভেতরে **মুড়ে দেয়** (VXLAN encapsulation)
3. আসল নেটওয়ার্ক দিয়ে Node B-তে পাঠায়
4. Node B-তে মোড়কটা খুলে Pod-2-এর কাছে দেয় ✅

**CNI প্লাগইন (Container Network Interface):**

| প্লাগইন | বিশেষত্ব |
|---|---|
| **Flannel** | সহজ, শেখার জন্য ভালো |
| **Calico** | Network Policy সাপোর্ট করে, দ্রুত (BGP) |
| **Cilium** | eBPF ভিত্তিক, সবচেয়ে আধুনিক ও দ্রুত |
| **Weave** | সহজ সেটআপ, এনক্রিপশন সাপোর্ট |

**⚠️ ব্যবহারিক পরামর্শ:** Pod-এর IP দিয়ে কখনো সরাসরি যোগাযোগ করবেন না — Pod মরলেই IP বদলে যায়। সবসময় **Service-এর নাম** ব্যবহার করুন:
```
❌ http://10.244.2.8:8080
✅ http://backend-service:8080
```

## ১৯. Kubernetes-এর সুবিধাগুলো কী কী?

| সুবিধা | মানে কী | বাস্তব উপকার |
|---|---|---|
| **Container Orchestration** | কন্টেইনার স্বয়ংক্রিয়ভাবে সামলানো | হাতে কাজ করতে হয় না |
| **Automated Load Balancing** | ট্রাফিক নিজে থেকে ভাগ হয় | কোনো Pod-এর উপর বাড়তি চাপ পড়ে না |
| **Auto Scaling** | চাহিদা অনুযায়ী কপি বাড়ে-কমে | সেলের দিনে সাইট ডাউন হয় না, রাতে খরচ বাঁচে |
| **Rolling Update & Rollback** | downtime ছাড়া নতুন ভার্সন, দরকারে ফিরে যাওয়া | রাত ২টায় ডিপ্লয় করার দরকার নেই |
| **Service Discovery** | নাম দিয়ে সার্ভিস খুঁজে পাওয়া | IP মনে রাখতে হয় না |
| **Storage Orchestration** | স্টোরেজ স্বয়ংক্রিয়ভাবে যুক্ত হয় | ডিস্ক ম্যানুয়ালি মাউন্ট করতে হয় না |
| **Self-Healing** | ক্র্যাশ করলে নিজে থেকে ঠিক হয় | রাত ৩টায় ফোন আসে না 😴 |
| **Secrets & Config Management** | গোপন তথ্য আলাদা ও নিরাপদ | পাসওয়ার্ড কোডে লিখতে হয় না |
| **Multi-Cloud সাপোর্ট** | AWS, Azure, GCP — সব জায়গায় একই | vendor lock-in থেকে মুক্তি |
| **RBAC** | কে কী করতে পারবে নিয়ন্ত্রণ | জুনিয়র ভুল করে production মুছতে পারবে না |
| **Multi-Container Pod** | Sidecar প্যাটার্ন | লগিং, প্রক্সি আলাদা কন্টেইনারে |
| **Monitoring & Logging** | মেট্রিক ও লগ সংগ্রহের সুবিধা | সমস্যা আগেই ধরা পড়ে |

**Self-Healing — সবচেয়ে প্রশংসিত ফিচারটা বাস্তব উদাহরণে:**

```
রাত ৩টা: আপনার একটা Pod মেমরি লিকের কারণে ক্র্যাশ করল
        ↓
Kubelet: "Pod মারা গেছে!" → সাথে সাথে রিস্টার্ট করল
        ↓
আবার ক্র্যাশ → আবার রিস্টার্ট (এবার একটু দেরিতে — exponential backoff)
        ↓
আপনি সকালে ঘুম থেকে উঠে দেখলেন সব ঠিক আছে,
শুধু লগে লেখা "RESTARTS: 3" ✅
```

Kubernetes ছাড়া এটা হতো — সাইট ডাউন, ব্যবহারকারীর অভিযোগ, রাত ৩টায় ফোন। 📞😫

**⚖️ ন্যায্যতার খাতিরে — Kubernetes-এর অসুবিধাও জেনে রাখুন:**
- শেখার বাঁক (learning curve) খুব খাড়া
- ছোট অ্যাপের জন্য অতিরিক্ত জটিল (কামান দিয়ে মশা মারা)
- কন্ট্রোল প্লেন নিজেই রিসোর্স খায়
- ডিবাগ করা কঠিন — সমস্যা কোন স্তরে তা বোঝা মুশকিল

> **কখন Kubernetes ব্যবহার করবেন না:** যদি আপনার একটা মাত্র অ্যাপ থাকে আর ট্রাফিক কম হয়, তাহলে একটা VM বা Heroku/Railway-ই যথেষ্ট।

## ২০. kube-scheduler-এর ভূমিকা কী?

**সংজ্ঞা:** kube-scheduler নতুন তৈরি হওয়া Pod-গুলোকে ক্লাস্টারের উপলব্ধ নোডে **বসানোর দায়িত্বে** থাকে।

এটা রিসোর্সের প্রয়োজন, নোডের সীমাবদ্ধতা ও শিডিউলিং নীতি বিবেচনা করে Pod-এর সবচেয়ে উপযুক্ত জায়গা ঠিক করে — যাতে পারফরম্যান্স ও রিসোর্স ব্যবহার সর্বোত্তম হয়।

**বাস্তব উদাহরণ — হোটেলের রিসেপশনিস্ট 🏨**

অতিথি এসে বললেন: "আমার একটা রুম লাগবে, ২ জনের জন্য, নন-স্মোকিং, লিফটের কাছে।"

রিসেপশনিস্ট:
1. **ফিল্টার:** কোন রুমগুলো খালি আছে এবং ২ জনের জায়গা আছে? → ২০টা রুম বাদ, ৫টা রইল
2. **স্কোরিং:** এই ৫টার মধ্যে কোনটা সবচেয়ে ভালো? লিফটের কাছেরটা বেশি নম্বর পাবে
3. **সিদ্ধান্ত:** সবচেয়ে বেশি নম্বর পাওয়া রুম বরাদ্দ

kube-scheduler ঠিক এই দুই ধাপেই কাজ করে।

**দুই ধাপের প্রক্রিয়া:**

**ধাপ ১ — Filtering (কোন নোডে আদৌ বসানো সম্ভব?):**
- নোডে কি যথেষ্ট CPU/মেমরি আছে?
- নোডে কি Taint আছে যেটা Pod সহ্য করতে পারে না?
- Pod-এর `nodeSelector` কি এই নোডের সাথে মেলে?
- দরকারি Volume কি এই নোডে যুক্ত হতে পারে?

**ধাপ ২ — Scoring (বাকিদের মধ্যে কোনটা সেরা?):**
- যে নোডে রিসোর্স বেশি খালি, সেটা বেশি নম্বর পায়
- ইমেজটা যে নোডে আগেই ডাউনলোড করা আছে, সেটা বেশি নম্বর পায় (দ্রুত চালু হবে)
- একই অ্যাপের Pod গুলো ছড়িয়ে রাখার চেষ্টা (একটা নোড মরলে সব যেন না যায়)

**আপনি কীভাবে প্রভাবিত করতে পারেন:**

```yaml
# ১. সহজ উপায় — নির্দিষ্ট label-এর নোডে
nodeSelector:
  disktype: ssd

# ২. Node Affinity — আরও নমনীয়
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      preference:
        matchExpressions:
        - key: zone
          operator: In
          values: [us-east-1a]

# ৩. Pod Anti-Affinity — একই অ্যাপের Pod আলাদা নোডে রাখো
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels: { app: backend }
      topologyKey: kubernetes.io/hostname
```

তৃতীয়টা খুব গুরুত্বপূর্ণ — এটা নিশ্চিত করে আপনার ৩টা backend Pod **৩টা আলাদা নোডে** বসবে। একটা নোড মরলেও সেবা চালু থাকবে। ✅

**⚠️ `Pending` অবস্থায় Pod আটকে থাকলে:**
```bash
kubectl describe pod <pod-name>
# Events দেখুন: "0/3 nodes are available: insufficient cpu"
```
মানে — scheduler কোনো উপযুক্ত নোড খুঁজে পায়নি।

## ২১. AWS-এ Kubernetes কীভাবে সেটআপ করবেন?

AWS-এ দুইভাবে Kubernetes সেটআপ করা যায় — **kubeadm** দিয়ে হাতে, অথবা **EKS (Elastic Kubernetes Service)** দিয়ে।

**kubeadm দিয়ে হাতে সেটআপের ধাপ:**
1. **EC2 ইনস্ট্যান্স চালু করুন:** একটা master নোড এবং কমপক্ষে একটা worker নোড
2. **সব নোডে Docker (বা containerd) ইনস্টল করুন**
3. **kubeadm, kubelet এবং kubectl ইনস্টল করুন**
4. **Master নোড init করুন**, **Pod network ইনস্টল করুন**, তারপর **worker নোডগুলো join করান**

**কমান্ডগুলো:**
```bash
# Master নোডে
sudo kubeadm init --pod-network-cidr=10.244.0.0/16

# kubectl কনফিগ করুন
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config

# Pod network (CNI) ইনস্টল করুন — এটা ছাড়া নোড NotReady থাকবে!
kubectl apply -f https://raw.githubusercontent.com/flannel-io/flannel/master/Documentation/kube-flannel.yml

# Worker নোডে (init-এর আউটপুট থেকে টোকেন পাবেন)
sudo kubeadm join <master-ip>:6443 --token <token> --discovery-token-ca-cert-hash <hash>
```

**EKS দিয়ে (অনেক সহজ):**
```bash
eksctl create cluster \
  --name my-cluster \
  --region ap-south-1 \
  --nodegroup-name workers \
  --node-type t3.medium \
  --nodes 3
```
একটা কমান্ড, ~১৫ মিনিট অপেক্ষা, ক্লাস্টার প্রস্তুত। ✅

**দুইটার তুলনা:**

| | kubeadm (নিজে) | EKS (ম্যানেজড) |
|---|---|---|
| Control Plane কে সামলায় | **আপনি** 😰 | **AWS** ✅ |
| etcd ব্যাকআপ | আপনার দায়িত্ব | AWS-এর দায়িত্ব |
| আপগ্রেড | হাতে, ঝুঁকিপূর্ণ | কয়েক ক্লিকে |
| খরচ | শুধু EC2-এর দাম | EC2 + $73/মাস (control plane) |
| শেখার জন্য | ✅ দুর্দান্ত | ভেতরটা লুকানো থাকে |
| উৎপাদনের জন্য | ❌ অনেক ঝামেলা | ✅ সুপারিশকৃত |

**💡 পরামর্শ:** **শিখতে চাইলে kubeadm** ব্যবহার করুন — ভেতরে কী হচ্ছে বোঝা যাবে। **উৎপাদনে EKS** ব্যবহার করুন — control plane সামলানোর ঝামেলা AWS নিক, আপনি অ্যাপে মন দিন।

## ২২. Horizontal Pod Autoscaler (HPA) কীভাবে কাজ করে?

**সংজ্ঞা:** HPA স্বয়ংক্রিয়ভাবে Pod-এর কপির সংখ্যা সমন্বয় করে — CPU ব্যবহারের মতো মেট্রিকের ভিত্তিতে। এটা নির্দিষ্ট বিরতিতে Pod বাড়ায় বা কমায়, যাতে পারফরম্যান্স ও রিসোর্স দক্ষতা ঠিক থাকে।

**হিসাবের সূত্রটা:**
```
নতুন replica = ⌈ বর্তমান replica × (এখনকার মেট্রিক / লক্ষ্য মেট্রিক) ⌉
```

**উদাহরণ দিয়ে দেখুন:**
```
এখন চলছে: ৩টা Pod
CPU ব্যবহার: গড়ে ৯০%
লক্ষ্য: ৫০%

নতুন replica = ⌈ 3 × (90 / 50) ⌉ = ⌈ 5.4 ⌉ = 6টা Pod
```
৬টা Pod-এ ভাগ হলে প্রতিটার CPU নামবে ~৪৫%-এ, লক্ষ্যের কাছাকাছি। ✅

**কাজের চক্র (প্রতি ১৫ সেকেন্ডে):**
```
Metrics Server → Pod-দের CPU/মেমরি সংগ্রহ করে
        ↓
HPA → গড় হিসাব করে, সূত্র প্রয়োগ করে
        ↓
প্রয়োজন হলে → Deployment-এর replicas বদলে দেয়
        ↓
Deployment → নতুন Pod বানায়/মোছে
```

**বাস্তব উদাহরণ — রেস্টুরেন্টের ওয়েটার 🍽️**

দুপুর ১টা, ভিড় বেড়ে গেল। ম্যানেজার দেখলেন প্রতিটা ওয়েটার ৯০% ব্যস্ত (লক্ষ্য ছিল ৫০%)। তিনি আরও ওয়েটার ডেকে আনলেন। বিকাল ৪টায় ভিড় কমলে বাড়তি ওয়েটারদের ছুটি দিলেন।

**⚠️ HPA কাজ করার পূর্বশর্ত:**

**১) Metrics Server ইনস্টল থাকতে হবে:**
```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl top nodes    # কাজ করছে কিনা পরীক্ষা
```

**২) Pod-এ `resources.requests` দিতেই হবে:**
```yaml
resources:
  requests:
    cpu: 100m       # 👈 এটা ছাড়া HPA শতাংশ হিসাব করতে পারবে না!
```
কারণ "CPU ৭০%" মানে হলো **request-এর ৭০%**। Request না দিলে ভিত্তিই নেই।

**Thrashing (দোদুল্যমানতা) ঠেকানো:**
```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300   # কমানোর আগে ৫ মিনিট অপেক্ষা
  scaleUp:
    stabilizationWindowSeconds: 0     # বাড়ানো সাথে সাথে
```
এটা না দিলে ট্রাফিক ওঠানামা করলে Pod বারবার বাড়বে-কমবে — অস্থিরতা তৈরি হবে।

**💡 নীতি:** **দ্রুত বাড়ান, ধীরে কমান।** কারণ Pod কম থাকলে ব্যবহারকারী ভোগে, কিন্তু Pod বেশি থাকলে শুধু একটু বেশি খরচ হয়।

## ২৩. Kubernetes-এ Custom Resource ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** Custom Resource হলো Kubernetes API-এর একটা **সম্প্রসারণ**, যা ডিফল্ট Kubernetes ইনস্টলেশনে সবসময় থাকে না।

কোনো custom resource ইনস্টল করার পর ব্যবহারকারীরা `kubectl` দিয়ে তার অবজেক্ট তৈরি ও ব্যবহার করতে পারেন — ঠিক যেভাবে Pod-এর মতো বিল্ট-ইন রিসোর্স ব্যবহার করেন।

Kubernetes-এর অনেক মূল কার্যক্রম এখন custom resource দিয়েই তৈরি, যা Kubernetes-কে আরও মডিউলার করেছে।

**বাস্তব উদাহরণ — মোবাইলে নতুন অ্যাপ ইনস্টল 📱**

আপনার ফোনে ডিফল্টভাবে ক্যামেরা, ক্যালকুলেটর থাকে। কিন্তু আপনি Play Store থেকে নতুন অ্যাপ ইনস্টল করলে সেটাও ঠিক আগেরগুলোর মতোই ব্যবহার করতে পারেন — একই স্ক্রিনে, একই অঙ্গভঙ্গিতে।

Custom Resource তেমনই — Kubernetes-এ নতুন "টাইপের জিনিস" যোগ করা, যা বিল্ট-ইন জিনিসের মতোই আচরণ করে।

**CRD (Custom Resource Definition) দিয়ে সংজ্ঞায়িত করা:**
```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              engine: { type: string }
              size:   { type: string }
  names:
    kind: Database
    plural: databases
```

**এরপর আপনি লিখতে পারবেন:**
```yaml
apiVersion: example.com/v1
kind: Database          # 👈 আপনার নিজের বানানো টাইপ!
metadata:
  name: my-app-db
spec:
  engine: postgres
  size: 10Gi
```

```bash
kubectl get databases           # বিল্ট-ইন রিসোর্সের মতোই কাজ করে ✅
kubectl describe database my-app-db
```

**বাস্তবে যেসব জনপ্রিয় টুল CRD ব্যবহার করে:**

| টুল | যে Custom Resource যোগ করে |
|---|---|
| **cert-manager** | `Certificate`, `Issuer` |
| **Prometheus Operator** | `ServiceMonitor`, `PrometheusRule` |
| **Istio** | `VirtualService`, `DestinationRule` |
| **ArgoCD** | `Application`, `AppProject` |

**⚠️ শুধু CRD বানালে কিছুই হয় না!**
CRD শুধু একটা **নতুন ধরনের ফর্ম** বানিয়ে দেয়। ফর্মটা পূরণ করলে কেউ কাজ করবে — সেই "কেউ"-টা হলো **Operator/Controller** (পরের প্রশ্নে)।

CRD ছাড়া Operator নেই → আপনি শুধু etcd-তে সুন্দর করে YAML জমা রাখছেন, আর কিছুই হচ্ছে না। 😄

## ২৪. Kubernetes নিরাপত্তা ও অ্যাক্সেস নিয়ন্ত্রণ কীভাবে সামলায়?

Kubernetes নিরাপত্তা সামলায় নিচের উপায়গুলোতে:

**১) RBAC (Role-Based Access Control):** ব্যবহারকারী ও গ্রুপ কোন রিসোর্সে কী কাজ করতে পারবে, তার অনুমতি ঠিক করে দেয়।

**২) Network Policies:** Pod ও Service-এর মধ্যে ট্রাফিক নিয়ন্ত্রণ করে নেটওয়ার্ক নিরাপত্তা বাড়ায়।

**৩) Secrets ও ConfigMaps:** সংবেদনশীল তথ্য ও কনফিগারেশন ডেটা নিরাপদে ম্যানেজ করে।

**৪) Pod Security Policies:** Pod-এর নিরাপত্তা প্রেক্ষাপট নির্ধারণ করে — সে কী করতে পারবে আর কী পারবে না।

**৫) Authentication ও Authorization:** সার্টিফিকেট, টোকেন ইত্যাদি বিভিন্ন পদ্ধতিতে ব্যবহারকারী যাচাই করে এবং নির্ধারিত নীতি অনুযায়ী অনুমতি দেয়।

**RBAC-এর চারটা অংশ:**

| অবজেক্ট | পরিধি | কাজ |
|---|---|---|
| `Role` | একটা namespace | কী কী করা যাবে তার তালিকা |
| `ClusterRole` | পুরো ক্লাস্টার | একই, কিন্তু সবখানে |
| `RoleBinding` | একটা namespace | কাকে ঐ Role দেওয়া হবে |
| `ClusterRoleBinding` | পুরো ক্লাস্টার | একই, সবখানে |

**একটা বাস্তব উদাহরণ — জুনিয়র ডেভেলপারকে সীমিত অধিকার:**
```yaml
# শুধু dev namespace-এ Pod দেখতে ও লগ পড়তে পারবে
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]      # 👈 delete নেই! ✅
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: dev
  name: junior-dev-binding
subjects:
- kind: User
  name: karim@company.com
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

এখন করিম `kubectl get pods -n dev` চালাতে পারবে, কিন্তু `kubectl delete pod` পারবে না। আর `production` namespace-এ তো ঢুকতেই পারবে না। ✅

**নিরাপত্তার স্তরগুলো — চারটা C:**
```
Cloud       → ক্লাউড প্রোভাইডারের নিরাপত্তা (VPC, IAM)
Cluster     → RBAC, Network Policy, etcd এনক্রিপশন
Container   → ইমেজ স্ক্যান, root ছাড়া চালানো
Code        → আপনার অ্যাপের নিজের নিরাপত্তা
```

**⚠️ Pod Security Policy অচল (deprecated) হয়ে গেছে!**
Kubernetes ১.২৫ থেকে PSP সরিয়ে ফেলা হয়েছে। এখন ব্যবহার করুন **Pod Security Admission**:
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
```

**নিরাপত্তার জন্য অবশ্যপালনীয় চেকলিস্ট:**
- ✅ কন্টেইনার **root হিসেবে চালাবেন না** (`runAsNonRoot: true`)
- ✅ ফাইল সিস্টেম শুধু-পড়া (`readOnlyRootFilesystem: true`)
- ✅ `privileged: true` কখনো নয়
- ✅ প্রতিটা namespace-এ ডিফল্ট **deny-all** Network Policy
- ✅ etcd-তে encryption at rest চালু
- ✅ ইমেজ স্ক্যান করুন (Trivy, Snyk)
- ✅ ডিফল্ট ServiceAccount-এর টোকেন বন্ধ করুন (`automountServiceAccountToken: false`)

## ২৫. Kubernetes-এ Network Policy কী?

**সংজ্ঞা:** Network Policy হলো একগুচ্ছ নিয়ম, যা ঠিক করে দেয় Pod-এর দলগুলো একে অপরের সাথে এবং অন্য নেটওয়ার্ক প্রান্তবিন্দুর সাথে **কীভাবে যোগাযোগ করতে পারবে**।

এর মাধ্যমে ঠিক করা যায় কোন Pod কার কাছ থেকে ট্রাফিক নিতে পারবে বা কার কাছে পাঠাতে পারবে — ফলে নেটওয়ার্ক অ্যাক্সেস নিয়ন্ত্রণ করে ও অ্যাপ্লিকেশন আলাদা রেখে নিরাপত্তা বাড়ানো যায়।

**⚠️ ডিফল্ট অবস্থাটা ভয়ংকর:**
Kubernetes-এ ডিফল্টভাবে **যেকোনো Pod যেকোনো Pod-এর সাথে কথা বলতে পারে**! মানে আপনার ফ্রন্টএন্ড Pod সরাসরি ডেটাবেজ Pod-এ ঢুকতে পারে। 😱

একটা Pod হ্যাক হলে হ্যাকার পুরো ক্লাস্টারে ঘুরে বেড়াতে পারবে (একে বলে **lateral movement**)।

**বাস্তব উদাহরণ — অফিসের দরজার কার্ড অ্যাক্সেস 🚪**

ডিফল্ট অবস্থা = সব দরজা খোলা। যে কেউ সার্ভার রুমে ঢুকে যেতে পারে।

Network Policy = প্রতিটা দরজায় কার্ড রিডার। শুধু অনুমোদিত লোকই ঢুকতে পারবে।

**প্রথম কাজ — সব বন্ধ করুন:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}          # সব Pod-এর জন্য
  policyTypes: [Ingress, Egress]
  # কোনো নিয়ম নেই = সব বন্ধ
```

**তারপর যা যা দরকার শুধু সেটা খুলুন:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-backend-only
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: postgres         # 👈 এই নিয়ম ডেটাবেজ Pod-এর জন্য
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: backend      # 👈 শুধু backend ঢুকতে পারবে
    ports:
    - protocol: TCP
      port: 5432
```

**ফলাফল:**
```
frontend Pod  ──✗──→  postgres    (আটকে গেল! ✅)
backend Pod   ──✓──→  postgres    (অনুমোদিত)
হ্যাকারের Pod ──✗──→  postgres    (আটকে গেল! ✅)
```

**⚠️ সবচেয়ে বড় ফাঁদ — সব CNI প্লাগইন Network Policy সাপোর্ট করে না!**

| CNI | Network Policy কাজ করে? |
|---|---|
| **Flannel** | ❌ না (নীরবে উপেক্ষা করবে!) |
| **Calico** | ✅ হ্যাঁ |
| **Cilium** | ✅ হ্যাঁ (আরও উন্নত, L7 পর্যন্ত) |
| **Weave** | ✅ হ্যাঁ |

Flannel ব্যবহার করলে আপনি Network Policy লিখবেন, `kubectl apply` সফল হবে, কিন্তু **কিছুই কার্যকর হবে না** — আর আপনি ভাববেন সব নিরাপদ! 💀 অবশ্যই পরীক্ষা করে দেখুন।

**পরীক্ষা করার উপায়:**
```bash
kubectl run test --rm -it --image=busybox -- sh
# ভেতরে গিয়ে:
wget -T 3 -O- http://postgres:5432    # আটকানো উচিত
```

## ২৬. Helm Chart কী এবং কীভাবে ব্যবহার হয়?

**সংজ্ঞা:** Helm chart হলো একটা প্যাকেজ, যাতে আগে থেকে কনফিগার করা Kubernetes রিসোর্স ও মেটাডেটা থাকে — একটা ক্লাস্টারে অ্যাপ্লিকেশন ডিপ্লয় করার জন্য।

এটা জটিল অ্যাপ্লিকেশনের ডিপ্লয়মেন্ট ও ব্যবস্থাপনা সহজ করে দেয় — সংজ্ঞায়িত করা, ইনস্টল করা ও আপগ্রেড করা সবই সহজে করা যায়। Helm chart শেয়ার ও পুনর্ব্যবহার করা যায়, ফলে বিভিন্ন পরিবেশে একইভাবে অ্যাপ্লিকেশন ম্যানেজ করা সহজ হয়।

**সমস্যাটা কী:**
একটা মাঝারি অ্যাপ ডিপ্লয় করতে লাগে —
```
deployment.yaml, service.yaml, ingress.yaml, configmap.yaml,
secret.yaml, hpa.yaml, pvc.yaml, serviceaccount.yaml...
```
৮-১০টা ফাইল। এখন dev, staging, production — তিনটা পরিবেশ। **৩০টা ফাইল!** আর প্রতিটাতে সামান্য পার্থক্য (replica সংখ্যা, ইমেজ ট্যাগ, ডোমেইন)। 😫

**Helm-এর সমাধান — টেমপ্লেট + ভ্যালু:**

```
mychart/
├── Chart.yaml           # chart-এর নাম, ভার্সন
├── values.yaml          # ডিফল্ট মানগুলো
└── templates/
    ├── deployment.yaml  # টেমপ্লেট
    ├── service.yaml
    └── ingress.yaml
```

**টেমপ্লেট:**
```yaml
# templates/deployment.yaml
spec:
  replicas: {{ .Values.replicaCount }}
  containers:
  - image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"
```

**পরিবেশভেদে আলাদা ভ্যালু:**
```yaml
# values-dev.yaml           # values-prod.yaml
replicaCount: 1             replicaCount: 10
image:                      image:
  tag: latest                 tag: v2.3.1
```

**ইনস্টল:**
```bash
helm install myapp ./mychart -f values-dev.yaml
helm install myapp ./mychart -f values-prod.yaml
```
একই chart, আলাদা কনফিগ। ✅

**বাস্তব উদাহরণ — রান্নার রেসিপি 📖**

| | উপমা |
|---|---|
| **Chart** | রান্নার রেসিপি |
| **values.yaml** | উপকরণের পরিমাণ (৪ জনের জন্য নাকি ১০ জনের) |
| **Release** | রান্না করা খাবারটা |
| **Helm Repo** | রান্নার বইয়ের লাইব্রেরি |

একই রেসিপি দিয়ে ৪ জনের রান্নাও হয়, ৪০ জনেরও — শুধু পরিমাণ বদলে যায়।

**Helm-এর সবচেয়ে বড় সুবিধা — রেডিমেড chart:**
```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install my-postgres bitnami/postgresql
```
এক কমান্ডে একটা পূর্ণাঙ্গ PostgreSQL — StatefulSet, Service, PVC, Secret, ব্যাকআপ কনফিগ সব সহ! ⚡

**কাজের কমান্ড:**
```bash
helm install myapp ./chart          # ইনস্টল
helm upgrade myapp ./chart          # আপগ্রেড
helm rollback myapp 1               # 🚨 ভার্সন ১-এ ফিরে যান
helm list                           # কী কী ইনস্টল আছে
helm template ./chart               # YAML দেখুন (ইনস্টল না করেই)
helm uninstall myapp                # সব রিসোর্স একসাথে মুছুন
```

**`helm rollback` কেন এত দারুণ:** Helm প্রতিটা রিলিজের ইতিহাস রাখে। ডিপ্লয়ের পর সমস্যা হলে **এক কমান্ডে সব রিসোর্স আগের অবস্থায়** ফিরে যাবে — শুধু Deployment নয়, ConfigMap, Service সবকিছু। ✅

## ২৭. Kubernetes কীভাবে Storage Orchestration সামলায়?

Kubernetes স্টোরেজ সামলায় **Persistent Volume (PV)** এবং **Persistent Volume Claim (PVC)**-এর মাধ্যমে। PV হলো ক্লাস্টারে থাকা স্টোরেজ রিসোর্স, আর PVC হলো ব্যবহারকারীর স্টোরেজের অনুরোধ।

*(বিস্তারিত ১৬ নম্বর প্রশ্নে দেখুন।)*

**এখানে একটা অতিরিক্ত গুরুত্বপূর্ণ ধারণা যোগ করি — StorageClass:**

StorageClass হলো **স্টোরেজের ধরন বা "মান"**।

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
reclaimPolicy: Retain
allowVolumeExpansion: true
```

**বাস্তব উদাহরণ — কুরিয়ার সার্ভিসের অপশন 📦**

| StorageClass | উপমা | দাম |
|---|---|---|
| `standard` | সাধারণ ডাক | সস্তা, ধীর |
| `fast-ssd` | এক্সপ্রেস ডেলিভারি | দামি, দ্রুত |
| `archive` | গুদামে জমা | খুব সস্তা, খুব ধীর |

আপনি শুধু বলবেন "এক্সপ্রেস চাই" — বাকিটা ব্যবস্থা হয়ে যাবে।

**Dynamic Provisioning-এর সৌন্দর্য:**
```
আপনি PVC বানালেন → StorageClass দেখল → AWS API কল করল
→ ১০ GB EBS ভলিউম তৈরি হলো → PV বানানো হলো → PVC-এর সাথে যুক্ত হলো
→ Pod-এ মাউন্ট হলো ✅

সময়: ~৩০ সেকেন্ড। আপনার হাত লাগেনি।
```

**Volume Expansion — ডিস্ক ভরে গেলে:**
```bash
kubectl edit pvc mysql-data
# storage: 10Gi → 50Gi করে দিন
```
`allowVolumeExpansion: true` থাকলে Kubernetes নিজেই ডিস্ক বড় করে দেবে — কোনো downtime ছাড়াই। ✅ (তবে ছোট করা যায় না!)

**⚠️ ব্যাকআপ Kubernetes-এর কাজ নয়!** PV-তে ডেটা থাকা মানেই নিরাপদ নয়। **Velero**-এর মতো টুল ব্যবহার করে নিয়মিত ব্যাকআপ নিন।

## ২৮. Taint ও Toleration ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** Taint ও Toleration ব্যবহার করা হয় নিয়ন্ত্রণ করতে যে **কোন Pod কোন নোডে বসতে পারবে**।

- **Taint** নোডে লাগানো হয় — এতে ঐ নোড নির্দিষ্ট কিছু Pod-এর জন্য "অনুপযুক্ত" চিহ্নিত হয়, মানে তাদের **তাড়িয়ে দেয়**।
- **Toleration** Pod-এ যোগ করা হয় — এতে ঐ Pod মিলে যাওয়া taint-ওয়ালা নোডে বসার **অনুমতি** পায়।

**সহজভাবে মনে রাখুন:**
- **Taint** = নোড বলছে "আমার এখানে সবাই আসতে পারবে না" 🚫
- **Toleration** = Pod বলছে "আমার বিশেষ পাস আছে, আমি ঢুকতে পারব" 🎫

**বাস্তব উদাহরণ — VIP লাউঞ্জ 🛋️**

এয়ারপোর্টের VIP লাউঞ্জে সাধারণ যাত্রীরা ঢুকতে পারে না (Taint)। কিন্তু যাদের কাছে বিজনেস ক্লাসের কার্ড আছে (Toleration), তারা ঢুকতে পারে।

**খেয়াল করুন — কার্ড থাকা মানেই সবাই লাউঞ্জে যাবে না।** কার্ডধারী চাইলে সাধারণ ওয়েটিং এরিয়াতেও বসতে পারে। **Toleration অনুমতি দেয়, বাধ্য করে না।**

**Taint লাগানো:**
```bash
kubectl taint nodes gpu-node-1 hardware=gpu:NoSchedule
```

**Toleration যোগ করা:**
```yaml
spec:
  tolerations:
  - key: "hardware"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```

**তিন ধরনের Effect:**

| Effect | কী হয় |
|---|---|
| `NoSchedule` | নতুন Pod বসবে না, কিন্তু আগের Pod থেকে যাবে |
| `PreferNoSchedule` | যথাসম্ভব এড়াবে, কিন্তু বাধ্য নয় (নরম নিয়ম) |
| `NoExecute` | নতুন Pod বসবে না, **আগের Pod গুলোও তাড়িয়ে দেবে** ⚠️ |

**বাস্তব ব্যবহারের উদাহরণ:**

**১) দামি GPU নোড সংরক্ষণ:**
```bash
kubectl taint nodes gpu-node-1 workload=ml:NoSchedule
```
এখন শুধু মেশিন লার্নিংয়ের Pod (যাদের toleration আছে) ঐ দামি নোডে বসবে। সাধারণ ওয়েব সার্ভার সেখানে জায়গা দখল করবে না। 💰

**২) Master নোড সংরক্ষণ (Kubernetes নিজেই করে):**
```bash
node-role.kubernetes.io/control-plane:NoSchedule
```
এজন্যই আপনার সাধারণ অ্যাপ কখনো master নোডে বসে না।

**৩) নোড রক্ষণাবেক্ষণ:**
```bash
kubectl taint nodes node-3 maintenance=true:NoExecute
```
সব Pod সাথে সাথে অন্য নোডে সরে যাবে। ✅

**Taint/Toleration বনাম Node Affinity — গুরুত্বপূর্ণ পার্থক্য:**

| | কে বলে | কী বলে |
|---|---|---|
| **Taint/Toleration** | **নোড** | "আমার এখানে যেকোনো Pod আসতে পারবে না" (তাড়িয়ে দেওয়া) |
| **Node Affinity** | **Pod** | "আমি এই ধরনের নোডে যেতে চাই" (আকর্ষণ) |

**দুটোই একসাথে ব্যবহার করলে সবচেয়ে ভালো:**
- Taint → অন্য কেউ GPU নোডে আসতে পারবে না
- Node Affinity → ML Pod নিশ্চিতভাবে GPU নোডেই যাবে

শুধু Taint দিলে ML Pod অন্য নোডেও চলে যেতে পারত। দুটো মিলিয়েই পূর্ণ নিয়ন্ত্রণ। ✅

## ২৯. Init Container-এর ব্যবহার বর্ণনা করুন

**সংজ্ঞা:** Init container একটা Pod-এর **মূল অ্যাপ্লিকেশন কন্টেইনার চালু হওয়ার আগে** চলে।

এগুলো প্রস্তুতিমূলক কাজ করে — যেমন ডেটা তৈরি করা বা কোনো সার্ভিসের জন্য অপেক্ষা করা — যাতে প্রয়োজনীয় শর্ত পূরণ হলে তবেই মূল কন্টেইনার চালু হয়।

**বাস্তব উদাহরণ — অনুষ্ঠানের প্রস্তুতি 🎪**

বিয়ের অনুষ্ঠান শুরু হওয়ার আগে — চেয়ার সাজানো, মাইক টেস্ট, খাবারের ব্যবস্থা করতে হয়। এগুলো শেষ না হলে অতিথিদের ঢুকতে দেওয়া হয় না।

Init container = সেই প্রস্তুতির দল। কাজ শেষ করে তারা চলে যায়, তারপর মূল অনুষ্ঠান (অ্যাপ কন্টেইনার) শুরু হয়।

**একটা বাস্তব উদাহরণ — ডেটাবেজের অপেক্ষা:**
```yaml
spec:
  initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ['sh', '-c',
      'until nc -z postgres 5432; do echo "ডেটাবেজের অপেক্ষায়..."; sleep 2; done']

  - name: run-migrations
    image: myapp:v1
    command: ['./migrate', 'up']

  containers:
  - name: app
    image: myapp:v1        # 👈 উপরের দুটো শেষ হলে তবেই চালু হবে
```

**যা ঘটবে:**
```
১. wait-for-db চলবে → ডেটাবেজ প্রস্তুত না হওয়া পর্যন্ত লুপে থাকবে
        ↓ (সফল)
২. run-migrations চলবে → টেবিল তৈরি/আপডেট
        ↓ (সফল)
৩. app চালু হবে ✅
```

**Init Container-এর বৈশিষ্ট্য:**

| বৈশিষ্ট্য | ব্যাখ্যা |
|---|---|
| **ক্রমানুসারে চলে** | একটার পর একটা, সবাই একসাথে নয় |
| **শেষ হতেই হবে** | ব্যর্থ হলে Pod বারবার চেষ্টা করবে |
| **আলাদা ইমেজ** | মূল অ্যাপ থেকে ভিন্ন টুল ব্যবহার করা যায় |
| **শেষ হয়ে মরে যায়** | মূল কন্টেইনার চালু হওয়ার আগেই বন্ধ |

**সবচেয়ে বড় সুবিধা — নিরাপত্তা:**
```yaml
initContainers:
- name: setup
  image: alpine:latest     # git, curl, চাই যা লাগে
  command: ['sh', '-c', 'git clone ... && chmod ...']

containers:
- name: app
  image: myapp:v1          # 👈 এখানে git বা curl কিছুই নেই!
```

মূল ইমেজে বাড়তি টুল না রাখায় **আক্রমণের সুযোগ কমে যায়**। হ্যাকার কন্টেইনারে ঢুকলেও `curl` দিয়ে কিছু ডাউনলোড করতে পারবে না। ✅

**সাধারণ ব্যবহার:**
- অন্য সার্ভিস প্রস্তুত হওয়ার অপেক্ষা
- ডেটাবেজ migration চালানো
- Git থেকে কনফিগ ডাউনলোড
- ফাইলের অনুমতি (permission) ঠিক করা
- Secret manager থেকে গোপন তথ্য আনা

**Init Container বনাম Sidecar:**
| | Init Container | Sidecar |
|---|---|---|
| কখন চলে | মূল কন্টেইনারের **আগে** | মূল কন্টেইনারের **পাশাপাশি** |
| কতক্ষণ | শেষ হয়ে মরে যায় | সারাক্ষণ চলে |
| উদাহরণ | migration চালানো | লগ পাঠানো |

## ৩০. Kubernetes-এ কী কী ধরনের Service আছে?

| Service Type | কী করে | কে ব্যবহার করতে পারে |
|---|---|---|
| **ClusterIP** | ক্লাস্টারের ভেতরের একটা IP-তে প্রকাশ করে | শুধু ক্লাস্টারের ভেতর থেকে |
| **NodePort** | প্রতিটা নোডের IP-তে একটা নির্দিষ্ট পোর্ট খুলে দেয় | বাইরে থেকেও |
| **LoadBalancer** | ক্লাউড প্রোভাইডারের লোড ব্যালেন্সার তৈরি করে | বাইরে থেকে, পাবলিক IP সহ |
| **ExternalName** | একটা বাইরের DNS নামে ম্যাপ করে | সার্ভিস ডিসকভারির জন্য |

### ১) ClusterIP (ডিফল্ট)

```yaml
spec:
  type: ClusterIP
  selector: { app: backend }
  ports: [{ port: 8080 }]
```

**বাস্তব উদাহরণ — অফিসের ইন্টারকম ☎️**
অফিসের ভেতরে ২০৩ নম্বর ডায়াল করলে অ্যাকাউন্টস ডিপার্টমেন্টে যায়। কিন্তু বাইরে থেকে কেউ ২০৩ ডায়াল করতে পারে না।

**কখন ব্যবহার:** ডেটাবেজ, ভেতরের API, ক্যাশ — যেগুলো বাইরে থেকে দেখার দরকার নেই।

### ২) NodePort

```yaml
spec:
  type: NodePort
  ports:
  - port: 8080
    nodePort: 30080      # ৩০০০০–৩২৭৬৭ রেঞ্জে
```
এখন `http://<যেকোনো-নোডের-IP>:30080` দিয়ে বাইরে থেকে ঢোকা যাবে।

**⚠️ উৎপাদনে NodePort ব্যবহার করবেন না।** কেন?
- পোর্ট নম্বর অদ্ভুত (৩০০৮০, ৮০ নয়)
- নোডের IP মনে রাখতে হবে, আর নোড বদলাতে পারে
- HTTPS/SSL সামলানোর ব্যবস্থা নেই

**কখন ব্যবহার:** লোকাল ডেভেলপমেন্ট, দ্রুত পরীক্ষা।

### ৩) LoadBalancer

```yaml
spec:
  type: LoadBalancer
```
ক্লাউডে (AWS/GCP/Azure) এটা দিলে **সত্যিকারের একটা লোড ব্যালেন্সার** তৈরি হয়ে যায় একটা পাবলিক IP সহ।

**⚠️ খরচের সতর্কতা:** প্রতিটা LoadBalancer AWS-এ প্রায় **$১৮/মাস**। ৫টা সার্ভিস মানে $৯০/মাস! এজন্যই সাধারণত একটাই LoadBalancer রেখে **Ingress** দিয়ে রাউটিং করা হয়। 💰

**⚠️ লোকাল ক্লাস্টারে (minikube, kind) LoadBalancer কাজ করবে না** — চিরকাল `<pending>` অবস্থায় থাকবে, কারণ কোনো ক্লাউড প্রোভাইডার নেই।

### ৪) ExternalName

```yaml
spec:
  type: ExternalName
  externalName: db.example.com
```
কোনো Pod, কোনো selector নেই — শুধু একটা DNS alias।

**বাস্তব ব্যবহার:** আপনার ডেটাবেজ AWS RDS-এ আছে, ক্লাস্টারের বাইরে। অ্যাপে লিখতে পারবেন `postgres://my-database:5432` — পরে যদি ডেটাবেজ ক্লাস্টারের ভেতরে আনেন, শুধু Service-টা বদলালেই হবে, **অ্যাপের কোডে হাত দিতে হবে না**। ✅

### একটা বোনাস — Headless Service

```yaml
spec:
  clusterIP: None        # 👈 এটাই "headless"
```
কোনো লোড ব্যালেন্সিং নেই — DNS জিজ্ঞেস করলে **সব Pod-এর IP** ফেরত দেয়।

**কখন দরকার:** StatefulSet-এর সাথে। যেমন Kafka-এর ক্লায়েন্টকে প্রতিটা broker-এর আলাদা ঠিকানা জানতে হয়:
```
kafka-0.kafka-headless.default.svc.cluster.local
kafka-1.kafka-headless.default.svc.cluster.local
```

**সিদ্ধান্তের সারসংক্ষেপ:**
```
ভেতরের সার্ভিস            → ClusterIP
বাইরে থেকে HTTP/HTTPS     → Ingress (LoadBalancer সহ)
বাইরে থেকে TCP/UDP        → LoadBalancer
লোকাল টেস্ট               → NodePort
বাইরের রিসোর্স            → ExternalName
StatefulSet               → Headless
```

## ৩১. Kubernetes-এ Custom Operator ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** Operator Kubernetes API ব্যবহার করে বিভিন্ন কাজ স্বয়ংক্রিয় করে — যেমন অ্যাপ্লিকেশন ডিপ্লয় করা, স্কেল করা এবং তার সামগ্রিক স্বাস্থ্য দেখাশোনা করা।

এরা কাস্টম টুলের মতো কাজ করে, যা Kubernetes-এ নতুন ক্ষমতা যোগ করে এবং জটিল অ্যাপ্লিকেশন সামলানো সহজ করে দেয়।

Operator সাধারণত **custom controller** হিসেবে তৈরি হয়, যা নির্ধারণ করে দেয় রিসোর্সগুলো কীভাবে ম্যানেজ হবে — ফলে সব কিছু সুষ্ঠুভাবে চলতে থাকে।

**Operator-এর মূল ধারণা:** *একজন মানব অপারেটরের জ্ঞানকে কোডে রূপান্তর করা।*

**বাস্তব উদাহরণ — একজন অভিজ্ঞ DBA 👨‍💻**

আপনার অফিসে একজন অভিজ্ঞ ডেটাবেজ অ্যাডমিন আছেন। তিনি জানেন:
- ডেটাবেজ কীভাবে ইনস্টল করতে হয়
- প্রতি রাতে কীভাবে ব্যাকআপ নিতে হয়
- master মরে গেলে কীভাবে replica-কে master বানাতে হয়
- ডিস্ক ভরে গেলে কীভাবে বড় করতে হয়
- ভার্সন আপগ্রেড কীভাবে নিরাপদে করতে হয়

**Operator হলো সেই DBA-এর সব জ্ঞান কোডে লেখা।** এখন আর তাকে রাত ৩টায় ফোন করতে হবে না — Operator নিজেই সব করবে। 🤖

**Operator-এর কাজের চক্র (Reconciliation Loop):**
```
      ┌─────────────────────────────┐
      ↓                             │
১. বর্তমান অবস্থা দেখো (৩টা Pod চলছে)
      ↓                             │
২. কাঙ্ক্ষিত অবস্থা পড়ো (৫টা দরকার)   │
      ↓                             │
৩. পার্থক্য মেটাও (২টা নতুন বানাও)     │
      ↓                             │
      └─────────────────────────────┘
              (অবিরাম চলতে থাকে)
```

**একটা কংক্রিট উদাহরণ — PostgreSQL Operator:**

আপনি শুধু এটুকু লিখবেন:
```yaml
apiVersion: acid.zalan.do/v1
kind: postgresql
metadata:
  name: my-database
spec:
  numberOfInstances: 3
  volume: { size: 100Gi }
  postgresql: { version: "15" }
  enableLogicalBackup: true
```

Operator নিজে থেকে করবে:
- ✅ ৩টা PostgreSQL Pod তৈরি (১ master, ২ replica)
- ✅ replication সেটআপ
- ✅ প্রতিটার জন্য ১০০ GB PVC তৈরি
- ✅ পাসওয়ার্ড তৈরি করে Secret-এ রাখা
- ✅ প্রতিদিন S3-এ ব্যাকআপ
- ✅ **master মরে গেলে স্বয়ংক্রিয়ভাবে failover** 🚨
- ✅ মনিটরিং সেটআপ

হাতে করলে এগুলো করতে কয়েক দিন লাগত, আর প্রতিবার ভুল হওয়ার সম্ভাবনা থাকত।

**Operator = CRD + Controller:**
```
CRD       → নতুন ধরনের রিসোর্স সংজ্ঞায়িত করে ("Database" নামে কিছু আছে)
Controller → সেই রিসোর্স দেখে কাজ করে (আসল কাজটা করে)
─────────────────────────────────────────
Operator   → দুটো মিলিয়ে একটা সম্পূর্ণ সমাধান
```

**জনপ্রিয় Operator:**
| Operator | কী সামলায় |
|---|---|
| Prometheus Operator | মনিটরিং সিস্টেম |
| cert-manager | SSL সার্টিফিকেট (স্বয়ংক্রিয় নবায়ন সহ) |
| Strimzi | Kafka ক্লাস্টার |
| ArgoCD | GitOps ডিপ্লয়মেন্ট |
| Elastic Operator | Elasticsearch |

**নিজে বানাতে চাইলে:** [Operator SDK](https://sdk.operatorframework.io/) বা [Kubebuilder](https://kubebuilder.io/) ব্যবহার করুন — Go দিয়ে লিখতে হয়।

## ৩২. Kubernetes Control Plane-এর ভেতরের গঠন বর্ণনা করুন

Control Plane হলো Kubernetes ক্লাস্টারের **মস্তিষ্ক**, যা পুরো ক্লাস্টারের অবস্থা ম্যানেজ করে। এর মূল অংশগুলো:

### kube-apiserver
সব যোগাযোগ ও REST অপারেশনের **কেন্দ্রীয় বিন্দু**।

### etcd
ডিস্ট্রিবিউটেড key-value স্টোর, যেখানে ক্লাস্টারের সব ডেটা, কনফিগারেশন ও অবস্থার তথ্য থাকে।

### kube-scheduler
রিসোর্সের প্রাপ্যতা ও শিডিউলিং নীতি অনুযায়ী Pod-গুলোকে নোডে বসানোর দায়িত্বে।

### kube-controller-manager
বিভিন্ন controller ম্যানেজ করে, যারা নিয়মিত কাজগুলো সামলায় — স্কেলিং, রেপ্লিকেশন, নোড ও Pod-এর অবস্থা পর্যবেক্ষণ।

### cloud-controller-manager
ক্লাউড প্রোভাইডারের API-এর সাথে যুক্ত হয়ে ক্লাউড পরিবেশের রিসোর্স ও সার্ভিস ম্যানেজ করে।

---

**পুরোটা কীভাবে একসাথে কাজ করে — একটা `kubectl apply`-এর যাত্রা:**

```
আপনি লিখলেন: kubectl apply -f deployment.yaml (replicas: 3)
        ↓
১. kube-apiserver
   - আপনি কে যাচাই করল (Authentication)
   - আপনার অনুমতি আছে কিনা দেখল (Authorization/RBAC)
   - YAML সঠিক কিনা যাচাই করল (Validation)
        ↓
২. etcd-তে লিখল: "একটা Deployment চাই, ৩টা replica"
        ↓
৩. Deployment Controller (controller-manager-এ) খবর পেল
   - "৩টা Pod দরকার, এখন ০টা আছে"
   - একটা ReplicaSet বানাল
        ↓
৪. ReplicaSet Controller
   - ৩টা Pod অবজেক্ট বানাল (কিন্তু কোনো নোড ঠিক হয়নি)
        ↓
৫. kube-scheduler
   - "এই ৩টা Pod-এর নোড ঠিক হয়নি!"
   - ফিল্টার + স্কোরিং করে সিদ্ধান্ত নিল
   - etcd-তে লিখল: "Pod-1 → Node A, Pod-2 → Node B, Pod-3 → Node A"
        ↓
৬. Kubelet (Node A-তে)
   - "আমার নোডে ২টা Pod বসানো হয়েছে!"
   - containerd-কে বলল কন্টেইনার চালু করতে
        ↓
৭. Kubelet অবস্থা রিপোর্ট করল → apiserver → etcd
        ↓
✅ kubectl get pods → Running
```

**খেয়াল করুন — কেউ কাউকে সরাসরি ফোন করেনি!**
সবাই শুধু **apiserver-এর মাধ্যমে etcd-এর দিকে তাকিয়ে আছে**। এই ডিজাইনকে বলে **level-triggered** — প্রত্যেকে নিজের কাজটুকু করছে, কেউ কারও উপর নির্ভরশীল নয়।

**কেন এই ডিজাইন এত ভালো:**
- Scheduler ক্র্যাশ করলে? বাকি সব চলতে থাকবে, শুধু নতুন Pod বসবে না। Scheduler ফিরলে সে বকেয়া কাজ ধরে নেবে ✅
- নতুন কোনো component যোগ করতে চান? শুধু apiserver-এর সাথে কথা বলা শেখান, কারও কোড বদলাতে হবে না ✅

**⚠️ apiserver হলো একমাত্র উপাদান যা সরাসরি etcd-এর সাথে কথা বলে।** এতে নিরাপত্তা ও সামঞ্জস্য দুটোই বজায় থাকে।

## ৩৩. Pod Disruption Budget ধারণাটা ব্যাখ্যা করুন

**সংজ্ঞা:** Pod Disruption Budget (PDB) হলো এমন একটা নীতি, যা নির্ধারণ করে **স্বেচ্ছায় করা বিঘ্নের** (voluntary disruption) সময় — যেমন নোড রক্ষণাবেক্ষণ বা স্কেল ডাউন — সর্বনিম্ন কতগুলো (বা শতকরা কত) Pod অবশ্যই চালু থাকতে হবে।

**দুই ধরনের বিঘ্ন:**

| ধরন | উদাহরণ | PDB কি রক্ষা করে? |
|---|---|---|
| **Voluntary** (স্বেচ্ছায়) | নোড আপগ্রেড, `kubectl drain`, cluster autoscaler | ✅ হ্যাঁ |
| **Involuntary** (অনিচ্ছাকৃত) | হার্ডওয়্যার নষ্ট, কার্নেল প্যানিক, OOM kill | ❌ না |

**সমস্যাটা কী — একটা বাস্তব দুর্ঘটনা:**

```
আপনার ৩টা API Pod চলছে — Node A, B, C-তে।

অ্যাডমিন ক্লাস্টার আপগ্রেড শুরু করলেন:
kubectl drain node-a  → Pod সরে গেল
kubectl drain node-b  → Pod সরে গেল
kubectl drain node-c  → Pod সরে গেল

এখন ০টা Pod চলছে! সাইট ডাউন! 💥
```

**PDB দিয়ে সমাধান:**
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2          # সবসময় কমপক্ষে ২টা চালু থাকতেই হবে
  selector:
    matchLabels:
      app: api
```

**এখন যা হবে:**
```
kubectl drain node-a  → ✅ অনুমতি (৩ → ২, এখনো ২টা আছে)
kubectl drain node-b  → 🛑 আটকে গেল! (২ → ১ হয়ে যাবে, নিয়ম ভাঙবে)

drain কমান্ড অপেক্ষা করবে যতক্ষণ না অন্য কোথাও নতুন Pod চালু হয়।
```

**বাস্তব উদাহরণ — হাসপাতালের ডাক্তার 🏥**

হাসপাতালে নিয়ম: "জরুরি বিভাগে সবসময় কমপক্ষে ২ জন ডাক্তার থাকতে হবে।"

৫ জন ডাক্তার আছে। একসাথে ৪ জন ছুটি চাইলে? ম্যানেজার বলবেন "না, সর্বোচ্চ ৩ জন ছুটি পেতে পারেন।" ✅

কিন্তু যদি ৩ জন হঠাৎ অসুস্থ হয়ে পড়েন (involuntary), তখন নিয়ম মানানো যাবে না — এটাই PDB-এর সীমাবদ্ধতা।

**দুইভাবে লেখা যায়:**
```yaml
minAvailable: 2          # কমপক্ষে ২টা চালু
# অথবা
minAvailable: "60%"      # কমপক্ষে ৬০% চালু
# অথবা
maxUnavailable: 1        # সর্বোচ্চ ১টা বন্ধ থাকতে পারে
```

**⚠️ একটা বিপজ্জনক ভুল:**
```yaml
replicas: 1
minAvailable: 1     # 🚨 নোড কখনোই drain করা যাবে না!
```
১টা Pod-এ ১টা অবশ্যই চালু থাকতে হলে — সেটা সরানোর কোনো উপায় নেই। ক্লাস্টার আপগ্রেড চিরকালের জন্য আটকে যাবে!

**নিয়ম:** `replicas` সবসময় `minAvailable`-এর চেয়ে বেশি রাখুন।

**💡 ভালো চর্চা:** সব গুরুত্বপূর্ণ সার্ভিসে PDB দিন। এটা ছাড়া ক্লাস্টার আপগ্রেড আপনার প্রোডাকশন ডাউন করে দিতে পারে।

## ৩৪. Kubernetes আর্কিটেকচারে kube-apiserver-এর ভূমিকা বর্ণনা করুন

**সংজ্ঞা:** kube-apiserver হলো Kubernetes-এর **কেন্দ্রীয় API গেটওয়ে**। এটা RESTful API রিকোয়েস্ট প্রসেস করে, যাচাই করে এবং etcd-তে ক্লাস্টারের অবস্থা আপডেট করে।

এটা control plane-এর উপাদান ও worker নোডের মধ্যে যোগাযোগ সহজ করে, যাতে ডিপ্লয়মেন্ট ও স্কেলিংয়ের মতো কাজ সামঞ্জস্যপূর্ণভাবে সম্পন্ন হয়।

**বাস্তব উদাহরণ — অফিসের রিসেপশন ডেস্ক 🏢**

কেউ ফাইল জমা দিতে চাইলে সরাসরি ফাইল রুমে ঢুকতে পারে না। রিসেপশনে গিয়ে:
1. পরিচয়পত্র দেখাতে হয় (Authentication)
2. তার এই ফাইল জমা দেওয়ার অধিকার আছে কিনা যাচাই হয় (Authorization)
3. ফর্ম ঠিকমতো পূরণ হয়েছে কিনা দেখা হয় (Validation)
4. তারপর রিসেপশনিস্ট নিজে গিয়ে ফাইল রুমে রেখে আসেন (etcd-তে লেখা)

**প্রতিটা রিকোয়েস্ট যে ধাপগুলো পার হয়:**

```
রিকোয়েস্ট আসল
      ↓
১. Authentication  → "তুমি কে?"
   (সার্টিফিকেট, টোকেন, OIDC)
      ↓
২. Authorization   → "তোমার কি এই কাজের অনুমতি আছে?"
   (RBAC নিয়ম যাচাই)
      ↓
৩. Admission Control → "এটা কি আমাদের নীতি মানে?"
   - Mutating: রিকোয়েস্ট বদলে দিতে পারে
     (যেমন: sidecar যোগ করা, ডিফল্ট মান বসানো)
   - Validating: গ্রহণ বা প্রত্যাখ্যান করে
     (যেমন: "resource limit ছাড়া Pod চলবে না")
      ↓
৪. Validation      → "YAML-টা কি বৈধ?"
      ↓
৫. etcd-তে লেখা    ✅
      ↓
৬. যারা "watch" করছে তাদের জানানো
```

**Admission Controller-এর একটা বাস্তব উদাহরণ:**

Istio-এর sidecar injection। আপনি একটা সাধারণ Pod ডিপ্লয় করলেন, কিন্তু Istio-এর Mutating Admission Webhook সেই YAML-এ **নিজে থেকে Envoy প্রক্সি কন্টেইনার যোগ করে দিল**। আপনার YAML-এ কিছু লিখতে হয়নি! ✨

**নিজের নীতি প্রয়োগ করতে চাইলে (OPA Gatekeeper):**
```
"কোনো Pod latest ট্যাগ দিয়ে ডিপ্লয় করা যাবে না"
"সব Pod-এ resource limit থাকতে হবে"
"শুধু আমাদের প্রাইভেট রেজিস্ট্রি থেকে ইমেজ নেওয়া যাবে"
```
এসব নিয়ম Admission Controller-এ লিখে দিলে **কেউ ভুল করেও নিয়ম ভাঙতে পারবে না**। ✅

**apiserver-এর অন্যান্য গুরুত্বপূর্ণ বৈশিষ্ট্য:**
- **Stateless** → তাই কয়েকটা কপি চালানো যায় (High Availability)
- **etcd-এর একমাত্র দরজা** → অন্য কেউ সরাসরি etcd-তে হাত দেয় না
- **Watch API** → বদল হলে সাথে সাথে সবাইকে জানায়

**⚠️ apiserver ডাউন হলে কী হয়:**
- ❌ `kubectl` কিছুই করতে পারবে না
- ❌ নতুন Pod তৈরি হবে না
- ✅ **কিন্তু যেসব Pod চলছে তারা চলতেই থাকবে!**

এটা একটা সুন্দর ডিজাইন — control plane মরে গেলেও আপনার অ্যাপ চলতে থাকে। শুধু নতুন কোনো পরিবর্তন হয় না।

## ৩৫. Kubernetes নোড ব্যর্থতা ও স্থিতিস্থাপকতা কীভাবে সামলায়?

যখনই কোনো নোড ব্যর্থ হয় বা কন্টেইনার অস্বাস্থ্যকর হয়ে পড়ে, Kubernetes অন্য সার্ভারে নতুন কপি চালু করে নিশ্চিত করে যে পর্যাপ্ত সংখ্যক replica বজায় আছে — ফলে সেবা অবিচ্ছিন্ন থাকে।

**যেসব ব্যবস্থা ও কৌশল ব্যবহার হয়:**

### ১) Node Health Monitoring
Kubelet প্রতি ১০ সেকেন্ডে apiserver-কে জানায় "আমি বেঁচে আছি"।

```
৪০ সেকেন্ড খবর নেই  → নোড "NotReady" চিহ্নিত হলো
৫ মিনিট খবর নেই      → Pod গুলো তাড়িয়ে অন্য নোডে সরানো শুরু
```

**⚠️ মানে ~৫ মিনিট পর্যন্ত সেবা আংশিক বিঘ্নিত হতে পারে।** এজন্যই Pod একাধিক নোডে ছড়িয়ে রাখা জরুরি।

### ২) Pod Restart Policies

| Policy | কখন রিস্টার্ট করবে |
|---|---|
| `Always` | সবসময় (Deployment-এর ডিফল্ট) |
| `OnFailure` | শুধু ব্যর্থ হলে (Job-এর জন্য) |
| `Never` | কখনো না |

বারবার ক্র্যাশ করলে Kubernetes **exponential backoff** ব্যবহার করে: ১০s → ২০s → ৪০s → ... সর্বোচ্চ ৫ মিনিট। এই অবস্থাটাই `CrashLoopBackOff`।

### ৩) Replication ও Desired State
Deployment/ReplicaSet নিরন্তর দেখে "৩টা চাই, কয়টা আছে?" কম হলেই নতুন বানায়।

### ৪) Pod Disruption Budgets
রক্ষণাবেক্ষণের সময় সর্বনিম্ন কতগুলো Pod চালু থাকবে তা নিশ্চিত করে। (৩৩ নম্বর দেখুন)

### ৫) Node Pool ও Multi-Cloud Deployment
বিভিন্ন availability zone বা ক্লাউডে নোড ছড়িয়ে রাখা।

---

**নিজের অ্যাপকে স্থিতিস্থাপক করতে যা করবেন:**

**১) Pod গুলো আলাদা নোডে ছড়িয়ে দিন:**
```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels: { app: api }
```
এখন আপনার Pod গুলো **আলাদা availability zone-এ** ছড়িয়ে থাকবে। একটা পুরো ডেটা সেন্টার মরলেও সেবা চলবে। ✅

**২) সঠিক Health Probe দিন:**
```yaml
livenessProbe:            # "বেঁচে আছে?" না হলে রিস্টার্ট
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:           # "ট্রাফিক নিতে প্রস্তুত?" না হলে Service থেকে সরাও
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5

startupProbe:             # ধীরে চালু হওয়া অ্যাপের জন্য
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
```

**⚠️ Liveness ও Readiness-এর পার্থক্য খুব গুরুত্বপূর্ণ:**
- **Liveness ব্যর্থ** → কন্টেইনার **রিস্টার্ট** হবে
- **Readiness ব্যর্থ** → শুধু **ট্রাফিক পাঠানো বন্ধ** হবে, রিস্টার্ট হবে না

একটা কমন বাগ: ডেটাবেজ সাময়িকভাবে ডাউন হলে liveness probe ব্যর্থ হয় → সব Pod রিস্টার্ট হতে থাকে → পরিস্থিতি আরও খারাপ! ✋ ডেটাবেজের নির্ভরতা **readiness**-এ দিন, liveness-এ নয়।

**৩) Resource Request ও Limit দিন:**
```yaml
resources:
  requests: { cpu: 100m, memory: 128Mi }    # নিশ্চিত পাবে
  limits:   { cpu: 500m, memory: 512Mi }    # এর বেশি নিতে পারবে না
```
Limit না দিলে একটা Pod পুরো নোডের মেমরি খেয়ে ফেলতে পারে, আর সব Pod মারা যাবে। 💀

**৪) Graceful Shutdown সামলান:**
```yaml
terminationGracePeriodSeconds: 30
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
```
Pod বন্ধ হওয়ার আগে চলমান রিকোয়েস্টগুলো শেষ করার সুযোগ পায়।

## ৩৬. Dockerfile আর docker-compose-এর পার্থক্য কী?

**Dockerfile:** একটা টেক্সট ফাইল, যাতে **একটা Docker ইমেজ বানানোর নির্দেশাবলি** থাকে। এতে বেস ইমেজ, এনভায়রনমেন্ট ভেরিয়েবল, চালানোর কমান্ড এবং কোন ফাইলগুলো যুক্ত হবে সব লেখা থাকে। অ্যাপ্লিকেশনের ইমেজ স্বয়ংক্রিয়ভাবে তৈরি করতে Dockerfile ব্যবহার হয়।

**Docker Compose:** একাধিক কন্টেইনারের অ্যাপ্লিকেশন সংজ্ঞায়িত ও চালানোর একটা টুল। এটা `docker-compose.yml` ফাইল দিয়ে সার্ভিস, নেটওয়ার্ক ও ভলিউম কনফিগার করে — ফলে অনেকগুলো কন্টেইনারকে একটা অ্যাপ্লিকেশন হিসেবে ম্যানেজ করা যায়।

**এক লাইনে পার্থক্য:**
- **Dockerfile** = **একটা** ইমেজ কীভাবে **বানাবেন**
- **docker-compose** = **অনেকগুলো** কন্টেইনার কীভাবে **একসাথে চালাবেন**

**বাস্তব উদাহরণ — রান্না 🍳**

| | উপমা |
|---|---|
| **Dockerfile** | একটা পদের রেসিপি (যেমন: বিরিয়ানি কীভাবে রাঁধবেন) |
| **docker-compose.yml** | পুরো মেনু পরিকল্পনা (বিরিয়ানি + সালাদ + বোরহানি একসাথে পরিবেশন) |

**Dockerfile-এর উদাহরণ:**
```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```
```bash
docker build -t myapp:v1 .
```

**docker-compose.yml-এর উদাহরণ:**
```yaml
services:
  app:
    build: .                 # 👈 এখানে Dockerfile ব্যবহার হচ্ছে
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://db:5432/mydb
    depends_on: [db, redis]

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7

volumes:
  pgdata:
```
```bash
docker compose up          # তিনটা কন্টেইনার একসাথে চালু! ⚡
```

**সম্পর্কটা বুঝুন:** docker-compose **Dockerfile-এর বিকল্প নয়** — বরং সে Dockerfile ব্যবহার করে। Compose বলে "এই সার্ভিসের ইমেজ বানাতে ঐ Dockerfile-টা ব্যবহার করো।"

**docker-compose বনাম Kubernetes:**

| | docker-compose | Kubernetes |
|---|---|---|
| কোথায় চলে | **একটা মেশিনে** | **অনেক মেশিনের ক্লাস্টারে** |
| স্কেলিং | সীমিত | স্বয়ংক্রিয় (HPA) |
| Self-healing | মৌলিক রিস্টার্ট | পূর্ণাঙ্গ |
| কখন ব্যবহার | **লোকাল ডেভেলপমেন্ট** ✅ | **উৎপাদন** ✅ |

**💡 বাস্তব কর্মপ্রবাহ:** ডেভেলপাররা লোকালে `docker compose up` দিয়ে কাজ করেন, আর উৎপাদনে একই ইমেজগুলোই Kubernetes-এ ডিপ্লয় হয়।

## ৩৭. Docker-এ CMD এবং RUN কমান্ডের পার্থক্য কী?

**RUN** ব্যবহার হয় **ইমেজ বানানোর সময়**, আর **CMD** ঠিক করে দেয় **কন্টেইনার চালু হলে কী চলবে**।

**পার্থক্যের টেবিল:**

| | RUN | CMD |
|---|---|---|
| কখন চলে | **Build** এর সময় (`docker build`) | **Run** এর সময় (`docker run`) |
| কতবার লেখা যায় | যত খুশি | **শেষেরটাই** কার্যকর |
| ফলাফল | ইমেজে একটা নতুন স্তর (layer) তৈরি হয় | কন্টেইনারের ডিফল্ট প্রক্রিয়া |
| উদ্দেশ্য | সফটওয়্যার ইনস্টল, ফাইল প্রস্তুত | অ্যাপ চালু করা |

**বাস্তব উদাহরণ — নতুন কম্পিউটার সেটআপ 💻**

- **RUN** = কম্পিউটারে **সফটওয়্যার ইনস্টল করা** (একবারই করতে হয়, তারপর হার্ডডিস্কে থেকে যায়)
- **CMD** = কম্পিউটার **চালু হলে যে প্রোগ্রামটা নিজে থেকে খোলে**

```dockerfile
FROM ubuntu:22.04

RUN apt-get update && apt-get install -y python3    # build-এর সময় ইনস্টল হলো
RUN pip install flask                                # build-এর সময়

CMD ["python3", "app.py"]                            # কন্টেইনার চালু হলে চলবে
```

**CMD একাধিক লিখলে কী হয়:**
```dockerfile
CMD ["echo", "প্রথম"]
CMD ["echo", "দ্বিতীয়"]     # 👈 শুধু এটাই চলবে
```

**CMD ওভাররাইড করা যায়:**
```bash
docker run myapp                    # CMD চলবে: python3 app.py
docker run myapp echo "হ্যালো"       # CMD উপেক্ষা করে এটা চলবে
```

**তৃতীয় একটা কমান্ড — ENTRYPOINT:**

| | CMD | ENTRYPOINT |
|---|---|---|
| ওভাররাইড করা যায়? | ✅ সহজেই | ❌ `--entrypoint` ছাড়া নয় |
| কাজ | ডিফল্ট কমান্ড | নির্দিষ্ট প্রোগ্রাম |

**দুটো একসাথে ব্যবহারের সুন্দর প্যাটার্ন:**
```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port", "8080"]                # ডিফল্ট আর্গুমেন্ট
```
```bash
docker run myapp                      # python3 app.py --port 8080
docker run myapp --port 9000          # python3 app.py --port 9000 ✅
```
এখানে ENTRYPOINT ঠিক করে দিল "এই কন্টেইনার সবসময় app.py চালাবে", আর CMD দিল বদলানোর মতো আর্গুমেন্ট।

**⚠️ RUN নিয়ে একটা গুরুত্বপূর্ণ অপ্টিমাইজেশন:**
```dockerfile
# ❌ খারাপ — ৩টা আলাদা স্তর, ইমেজ বড় হবে
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ ভালো — ১টা স্তর, ইমেজ ছোট
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```
প্রতিটা `RUN` একটা নতুন স্তর তৈরি করে। আলাদা স্তরে ফাইল মুছলেও আগের স্তরে সেটা থেকেই যায় — ইমেজের সাইজ কমে না!

**Shell form বনাম Exec form:**
```dockerfile
CMD python3 app.py                 # shell form — /bin/sh -c এর মধ্যে চলে
CMD ["python3", "app.py"]          # exec form — সরাসরি চলে ✅ (সুপারিশকৃত)
```
Exec form ব্যবহার করুন, কারণ তাতে আপনার অ্যাপ **PID 1** হয় এবং `SIGTERM` সিগন্যাল সরাসরি পায় — ফলে graceful shutdown ঠিকমতো কাজ করে।

### সবচেয়ে দরকারি কমান্ডগুলো

```bash
# দেখা
kubectl get pods -o wide

# ডিবাগ

kubectl port-forward <pod> 8080:80   # লোকাল থেকে সংযোগ
kubectl get events --sort-by=.metadata.creationTimestamp

# পরিবর্তন
kubectl apply -f file.yaml
kubectl scale deployment api --replicas=5
kubectl rollout undo deployment/api  # 🚨 ফিরে যান
kubectl delete pod <name>            # Deployment থাকলে নতুনটা আসবে

# রক্ষণাবেক্ষণ
kubectl cordon node-1                # নতুন Pod বসানো বন্ধ
kubectl drain node-1 --ignore-daemonsets   # Pod সরিয়ে নিন
kubectl uncordon node-1              # আবার চালু
```

### Pod-এর অবস্থা ও তার মানে

| অবস্থা | কী হয়েছে | প্রথমে কী দেখবেন |
|---|---|---|
| `Pending` | নোড পাওয়া যায়নি | `describe` → রিসোর্স আছে কিনা |
| `ImagePullBackOff` | ইমেজ নামানো যাচ্ছে না | ইমেজের নাম, রেজিস্ট্রি ক্রেডেনশিয়াল |
| `CrashLoopBackOff` | বারবার ক্র্যাশ করছে | `logs --previous` |
| `OOMKilled` | মেমরি লিমিট ছাড়িয়েছে | memory limit বাড়ান |
| `Running` কিন্তু Ready নয় | readinessProbe ব্যর্থ | probe-এর path ঠিক আছে কিনা |
