> **শুরুর আগে একটা কথা:** এই পুরো ডকুমেন্টে আমরা একটা **কলেজের ডেটাবেজ** আর একটা **অনলাইন শপের ডেটাবেজ** — এই দুইটা উদাহরণ ঘুরিয়ে ফিরিয়ে ব্যবহার করব। একই উদাহরণ বারবার দেখলে ধারণাগুলো মাথায় বসে যাবে।

## ১. ডেটাবেজ কী?

**সংজ্ঞা:** ডেটাবেজ হলো **সুসংগঠিত, কাঠামোবদ্ধ তথ্যের সংগ্রহ**, যা সাধারণত কম্পিউটার সিস্টেমে ইলেকট্রনিকভাবে সংরক্ষিত থাকে।

**বাস্তব উদাহরণ — একটা ফাইল ক্যাবিনেট 🗄️**

পুরনো দিনের অফিসে একটা লোহার আলমারি থাকত। সেখানে:
- **ড্রয়ার** = টেবিল (একটায় কর্মীদের ফাইল, একটায় গ্রাহকদের)
- **ফোল্ডার** = একেকটা রেকর্ড (একজন কর্মীর তথ্য)
- **ফোল্ডারের ভেতরের কাগজ** = কলাম (নাম, ঠিকানা, বেতন)

কেউ যদি সব কাগজ একটা বস্তায় ভরে রাখত, সেটা ডেটাবেজ হতো না — কারণ **সংগঠন নেই**। সংগঠিত হওয়াটাই মূল কথা।

**ডেটা vs তথ্য:**
- `২৫, ৩০, ৪৫` → এগুলো শুধু **ডেটা**, অর্থহীন
- "করিমের বয়স ২৫, রহিমের ৩০" → এটা **তথ্য**, অর্থবহ

## ২. DBMS কী?

**সংজ্ঞা:** DBMS (Database Management System) ডেটাবেজে ডেটা সংরক্ষণ ও ব্যবস্থাপনা করতে সাহায্য করে। এটা **ব্যবহারকারী ও ডেটাবেজের মধ্যে একটা সেতু** হিসেবে কাজ করে — ব্যবহারকারী দক্ষতার সাথে ডেটা তৈরি, পড়া, আপডেট ও মুছতে পারে, আর একই সাথে ডেটার **নিরাপত্তা, অখণ্ডতা (integrity) ও সমকালীনতা (concurrency)** নিশ্চিত হয়।

**পার্থক্যটা বুঝুন:**
- **ডেটাবেজ** = আলমারিতে রাখা ফাইলগুলো
- **DBMS** = সেই আলমারির দায়িত্বে থাকা **লাইব্রেরিয়ান** 👩‍💼

লাইব্রেরিয়ান যা করেন:
| কাজ | DBMS-এ কী নামে |
|---|---|
| বই খুঁজে দেন | Query processing |
| কে কোন বই নিতে পারবে ঠিক করেন | Security / Access control |
| দুইজন একই বই চাইলে সামলান | Concurrency control |
| বই হারালে ব্যাকআপ কপি দেন | Recovery |
| তালিকা ঠিক রাখেন | Data integrity |

**জনপ্রিয় DBMS:** MySQL, PostgreSQL, Oracle, SQL Server, MongoDB, SQLite

## ৩. RDBMS কী এবং এর বৈশিষ্ট্যগুলো কী?

**সংজ্ঞা:** RDBMS (Relational Database Management System) হলো এমন একটা ডেটাবেজ সিস্টেম, যা **রিলেশনাল মডেলের** উপর ভিত্তি করে তৈরি — এখানে ডেটা **টেবিলে (relation)** রাখা হয় এবং টেবিলগুলো **key** দিয়ে একে অপরের সাথে যুক্ত থাকে। SQL দিয়ে দক্ষতার সাথে কাঠামোবদ্ধ ডেটা সংরক্ষণ, উদ্ধার ও পরিবর্তন করা যায়।

**বাস্তব উদাহরণ — এক্সেল শিটের সম্পর্ক:**

```
students টেবিল                   courses টেবিল
┌─────┬────────┬──────────┐     ┌───────────┬──────────────┐
│ id  │ name   │ dept_id  │     │ course_id │ course_name  │
├─────┼────────┼──────────┤     ├───────────┼──────────────┤
│  1  │ করিম    │    10    │     │   CS101   │ প্রোগ্রামিং    │
│  2  │ রহিম    │    10    │     │   MA201   │ গণিত          │
└─────┴────────┴──────────┘     └───────────┴──────────────┘
              ↓ dept_id দিয়ে সংযুক্ত
      departments টেবিল
```

তথ্য বারবার লেখা হচ্ছে না — শুধু **আইডি দিয়ে সংযোগ** করা হচ্ছে। এটাই রিলেশনাল মডেলের সৌন্দর্য।

### ACID বৈশিষ্ট্য — RDBMS-এর মূল ভিত্তি

**১) Atomicity (অবিভাজ্যতা):**
নিশ্চিত করে যে একটা ট্রানজেকশনের **সব অংশ সম্পন্ন হবে**। না হলে ট্রানজেকশনটা তার শুরুর অবস্থায় **rollback** হয়ে যাবে — ফলে ডেটার সামঞ্জস্য বজায় থাকবে।

> **উদাহরণ — টাকা ট্রান্সফার 💸**
> করিমের অ্যাকাউন্ট থেকে ৫০০ টাকা কেটে রহিমের অ্যাকাউন্টে যোগ করতে হবে।
> ```
> ধাপ ১: করিমের ব্যালেন্স -= ৫০০   ✅ হলো
> ধাপ ২: রহিমের ব্যালেন্স += ৫০০   💥 সার্ভার ক্র্যাশ!
> ```
> Atomicity না থাকলে করিমের টাকা গায়েব হয়ে যেত! Atomicity বলে — **"হয় দুইটাই হবে, নয়তো একটাও হবে না।"** ধাপ ১ বাতিল হয়ে যাবে। ✅
>
> নামটা এসেছে "atom" থেকে — যা আর ভাগ করা যায় না।

**২) Consistency (সামঞ্জস্য):**
নিশ্চিত করে যে ডেটা এক বৈধ অবস্থা থেকে আরেক বৈধ অবস্থায় যাচ্ছে, ডেটার অখণ্ডতা বজায় থাকছে।

> **উদাহরণ:** ট্রান্সফারের আগে দুই অ্যাকাউন্টে মোট ছিল ১০,০০০ টাকা। পরেও মোট ১০,০০০ টাকাই থাকতে হবে। টাকা হাওয়া থেকে আসতেও পারবে না, হাওয়ায় মিলিয়েও যেতে পারবে না।
>
> সব **constraint** (যেমন `balance >= 0`, foreign key) মানতে হবে।

**৩) Isolation (বিচ্ছিন্নতা):**
নিশ্চিত করে যে ট্রানজেকশনগুলো **স্বাধীনভাবে** চলছে, একে অপরকে বিঘ্নিত করছে না।

> **উদাহরণ:** করিম যখন ৫০০ টাকা পাঠাচ্ছে, ঠিক সেই মুহূর্তে রহিমও ৩০০ টাকা তুলছে। দুইটা ট্রানজেকশন যেন একে অপরের অর্ধেক-হওয়া কাজ না দেখে।
>
> মনে হবে যেন **একটার পর একটা** হচ্ছে, যদিও আসলে একসাথে হচ্ছে।

**৪) Durability (স্থায়িত্ব):**
নিশ্চিত করে যে একবার ট্রানজেকশন **commit** হয়ে গেলে সেটা স্থায়ীভাবে সংরক্ষিত — এমনকি সিস্টেম ফেইল করলেও।

> **উদাহরণ:** ATM থেকে টাকা তোলার রসিদ হাতে পেলেন। ঠিক তখনই ব্যাংকের সার্ভারে বিদ্যুৎ চলে গেল। সার্ভার ফিরে আসার পর আপনার লেনদেনটা **অবশ্যই সেখানে থাকতে হবে**। ✅
>
> এটা সম্ভব হয় **Write-Ahead Log (WAL)** দিয়ে — ডেটা বদলানোর আগেই লগে লিখে রাখা হয়।

**মনে রাখার সহজ উপায়:**
```
A → সব, নয়তো কিছুই না
C → নিয়ম কখনো ভাঙবে না
I → একে অপরকে বিরক্ত করবে না
D → একবার হয়ে গেলে চিরস্থায়ী
```

## ৪. ডেটাবেজ ল্যাঙ্গুয়েজের প্রকারভেদ কী কী?

| ধরন | পুরো নাম | কাজ | কমান্ড |
|---|---|---|---|
| **DDL** | Data Definition Language | ডেটাবেজের **কাঠামো** সংজ্ঞায়িত ও ব্যবস্থাপনা | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** | Data Manipulation Language | ডেটাবেজের **ভেতরের ডেটা** নিয়ে কাজ | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **DCL** | Data Control Language | ডেটার **অনুমতি নিয়ন্ত্রণ** | `GRANT`, `REVOKE` |
| **TCL** | Transaction Control Language | **ট্রানজেকশন** ব্যবস্থাপনা | `COMMIT`, `ROLLBACK`, `SAVEPOINT` |

**বাস্তব উদাহরণ — একটা বাড়ি বানানো 🏠**

| | বাড়ির উপমা |
|---|---|
| **DDL** | ঘরের নকশা বানানো, দেয়াল তোলা (কাঠামো) |
| **DML** | ঘরে আসবাবপত্র রাখা, সরানো, বদলানো (ভেতরের জিনিস) |
| **DCL** | কার কাছে কোন ঘরের চাবি থাকবে |
| **TCL** | "কাজটা পাকা করো" নাকি "সব আগের মতো করে দাও" |

**কোডে দেখুন:**
```sql
-- DDL: কাঠামো বানালাম
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);

-- DML: ডেটা ঢোকালাম
INSERT INTO students VALUES (1, 'করিম');

-- DCL: অনুমতি দিলাম
GRANT SELECT ON students TO 'teacher';

-- TCL: পাকা করলাম
COMMIT;
```

**⚠️ একটা গুরুত্বপূর্ণ পার্থক্য:** DDL কমান্ড সাধারণত **auto-commit** হয়ে যায় — মানে `ROLLBACK` করা যায় না। কিন্তু DML কমান্ড rollback করা যায়। তাই `DROP TABLE` লেখার আগে দুইবার ভাবুন! 😰

## ৫. ACID বৈশিষ্ট্য কী?

ডেটাবেজে সামঞ্জস্য নিশ্চিত করতে সিস্টেমে ঘটা ট্রানজেকশনগুলো কিছু নির্দিষ্ট বৈশিষ্ট্য মেনে চলে।

*(বিস্তারিত ৩ নম্বর প্রশ্নে দেখুন।)*

**এখানে একটা অতিরিক্ত গুরুত্বপূর্ণ বিষয় যোগ করি — Isolation Level:**

Isolation পুরোপুরি নিশ্চিত করা খুব খরচসাপেক্ষ, তাই ডেটাবেজ কয়েকটা **স্তর** দেয়:

| Level | Dirty Read | Non-repeatable Read | Phantom Read | গতি |
|---|---|---|---|---|
| `READ UNCOMMITTED` | ✅ হতে পারে | ✅ হতে পারে | ✅ হতে পারে | সবচেয়ে দ্রুত |
| `READ COMMITTED` | ❌ | ✅ | ✅ | দ্রুত (PostgreSQL ডিফল্ট) |
| `REPEATABLE READ` | ❌ | ❌ | ✅ | মাঝারি (MySQL ডিফল্ট) |
| `SERIALIZABLE` | ❌ | ❌ | ❌ | ধীর, সবচেয়ে নিরাপদ |

**তিনটা সমস্যা সহজভাবে:**

- **Dirty Read:** অন্যের **অসমাপ্ত** কাজ পড়ে ফেলা। সে পরে rollback করলে আপনি ভুল তথ্য নিয়ে বসে থাকবেন।
- **Non-repeatable Read:** একই রো দুইবার পড়লেন, দুইবার দুই রকম মান পেলেন (মাঝে অন্য কেউ বদলে দিয়েছে)।
- **Phantom Read:** একই কোয়েরি দুইবার চালালেন, দ্বিতীয়বার **নতুন রো** দেখা গেল (অন্য কেউ ঢুকিয়েছে)।

> **উদাহরণ:** আপনি রিপোর্ট বানাচ্ছেন — "এই মাসে মোট বিক্রি কত?" প্রথমবার পেলেন ১০০টা অর্ডার। কয়েক সেকেন্ড পর আবার গুনলেন, পেলেন ১০২টা। রিপোর্টের দুই জায়গায় দুই সংখ্যা! 😵 এটাই Phantom Read।

## ৬. Vertical ও Horizontal Scaling-এর পার্থক্য কী?

**Vertical Scaling (উল্লম্ব স্কেলিং):**
- একটা মাত্র নোড বা সার্ভারে **আরও রিসোর্স** (CPU, RAM, স্টোরেজ) যোগ করা।
- বাস্তবায়ন সহজ, কিন্তু **হার্ডওয়্যারের সীমা** আছে এবং **একটাই ব্যর্থতার বিন্দু** (single point of failure) থাকে।
- সীমিত বৃদ্ধির প্রয়োজন আছে এমন অ্যাপ্লিকেশনের জন্য উপযুক্ত।

**Horizontal Scaling (অনুভূমিক স্কেলিং):**
- **আরও সার্ভার বা নোড** যোগ করে লোড ভাগ করে দেওয়া।
- ভালো ফল্ট টলারেন্স দেয় এবং অনেক বড় বৃদ্ধি সামলাতে পারে।
- সামলানো জটিল, কিন্তু চাহিদা অনুযায়ী **প্রায় অসীম** স্কেল করা যায়।

**বাস্তব উদাহরণ — রেস্টুরেন্ট 🍽️**

| | Vertical Scaling | Horizontal Scaling |
|---|---|---|
| উপমা | **একটাই রান্নাঘর, বড় করা** — বড় চুলা, বেশি ফ্রিজ | **আরও শাখা খোলা** — ৫টা রেস্টুরেন্ট |
| সীমা | রান্নাঘর কতই বা বড় করা যায়? | যত খুশি শাখা |
| ঝুঁকি | রান্নাঘরে আগুন লাগলে সব বন্ধ 💀 | এক শাখা বন্ধ হলে বাকিগুলো চলে ✅ |
| জটিলতা | সহজ | সমন্বয় করা কঠিন |

**তুলনার টেবিল:**

| | Vertical (Scale Up) | Horizontal (Scale Out) |
|---|---|---|
| কী করি | মেশিন বড় করি | মেশিন সংখ্যা বাড়াই |
| সহজ? | ✅ কোড বদলাতে হয় না | ❌ আর্কিটেকচার বদলাতে হয় |
| সীমা | হার্ডওয়্যারের সীমা আছে | প্রায় অসীম |
| খরচ | বড় মেশিনের দাম **লাফিয়ে** বাড়ে | সাধারণ মেশিন, দাম সরলরৈখিক |
| Downtime | আপগ্রেডের সময় সার্ভার বন্ধ | চালু অবস্থায় নোড যোগ করা যায় |
| Failure | একটা মরলে সব শেষ | একটা মরলেও চলে |

**খরচের বাস্তবতা:**
```
৮ GB RAM সার্ভার    → $৪০/মাস
১৬ GB RAM সার্ভার   → $৮০/মাস
৬৪ GB RAM সার্ভার   → $৪০০/মাস      ← দাম লাফাচ্ছে!
২৫৬ GB RAM সার্ভার  → $৩,০০০/মাস    ← 💸
```
৮টা ছোট সার্ভার ($৩২০) প্রায়ই একটা বিশাল সার্ভারের ($৩,০০০) চেয়ে সস্তা ও নিরাপদ।

**💡 বাস্তব পরামর্শ:** **Vertical দিয়ে শুরু করুন** (সহজ), আর যখন সীমায় পৌঁছাবেন তখন **Horizontal-এ যান**। শুরুতেই ডিস্ট্রিবিউটেড সিস্টেম বানানো অপ্রয়োজনীয় জটিলতা।

## ৭. Sharding কী?

**সংজ্ঞা:** Sharding হলো একটা ডেটাবেজ পার্টিশনিং কৌশল, যেখানে একটা বিশাল ডেটাবেজকে **ছোট ছোট ও সামলানোর মতো টুকরোয়** ভাগ করা হয় — এগুলোকে বলে **shard**। প্রতিটা shard-এ ডেটার একটা অংশ থাকে এবং সেগুলো **আলাদা আলাদা সার্ভারে** সংরক্ষিত হয়।

**উদ্দেশ্য:** একাধিক সার্ভারে লোড ছড়িয়ে দিয়ে পারফরম্যান্স ও স্কেলেবিলিটি বাড়ানো।

**বাস্তব উদাহরণ — লাইব্রেরি 📚**

একটা লাইব্রেরিতে ১০ লক্ষ বই। সব এক ঘরে রাখলে বই খুঁজতে ঘণ্টা লেগে যাবে।

সমাধান: **অক্ষর অনুযায়ী ভাগ করুন**
- ক-চ দিয়ে শুরু হওয়া লেখকদের বই → ১ নং কক্ষ
- ছ-প → ২ নং কক্ষ
- ফ-হ → ৩ নং কক্ষ

এখন প্রতিটা কক্ষে ৩ লক্ষ বই, আর ৩ জন লাইব্রেরিয়ান একসাথে কাজ করতে পারছেন। ✅

---

### Sharding-এর ধরন

**ক) Range-based Sharding (রেঞ্জ ভিত্তিক):**
Sharding key-এর মান অনুযায়ী ডেটা ভাগ করা।
```
user_id: 1 – 1000      → shard 1
user_id: 1001 – 2000   → shard 2
user_id: 2001 – 3000   → shard 3
```
- ✅ বাস্তবায়ন সহজ, **রেঞ্জ কোয়েরি দ্রুত** ("১০০-২০০ নম্বর ইউজার দাও" — এক shard-এই পাওয়া যাবে)
- ❌ ডেটা সমানভাবে ছড়ানো না থাকলে **অসম বণ্টন** হতে পারে

> **সমস্যাটা বাস্তবে:** তারিখ দিয়ে shard করলে **সব নতুন ডেটা শেষ shard-এ** যাবে। সেটা ওভারলোড হবে, বাকিগুলো অলস বসে থাকবে। একে বলে **hotspot**। 🔥

**খ) Hash-based Sharding (হ্যাশ ভিত্তিক):**
Sharding key-তে হ্যাশ ফাংশন প্রয়োগ করে ডেটা বণ্টন করা।
```
shard = hash(user_id) % মোট_shard_সংখ্যা
```
- ✅ ডেটা **সমানভাবে ছড়ায়**, লোড ব্যালেন্স হয়
- ❌ **রেঞ্জ কোয়েরি খুব কঠিন** হয়ে যায় (১০০-২০০ নম্বর ইউজার সব shard-এ ছড়িয়ে আছে!)

**গ) Consistent Hashing:**
Shard যোগ বা বাদ দেওয়ার সময় এটা ব্যবহার করা হয়।

> **সাধারণ hash-এর সমস্যা:** `hash(id) % 4` থেকে `hash(id) % 5`-এ গেলে **প্রায় সব ডেটা** নতুন shard-এ সরাতে হবে! 💀
>
> **Consistent Hashing-এর সমাধান:** একটা কাল্পনিক **বৃত্তে** shard আর ডেটা দুটোকেই বসানো হয়। নতুন shard যোগ করলে শুধু **তার প্রতিবেশীর ডেটাটুকু** সরাতে হয় — বাকি সব যেখানে ছিল সেখানেই থাকে। ✅
>
> এটা অনেকটা — বৃত্তাকার টেবিলে নতুন একজন বসলে শুধু তার দুই পাশের লোক একটু সরে বসে, পুরো টেবিলের সবাইকে উঠতে হয় না।

**সুবিধা:** কোয়েরির চাপ কমে, read/write থ্রুপুট বাড়ে এবং ফল্ট টলারেন্স পাওয়া যায়।

**⚠️ Sharding-এর কঠিন দিকগুলো:**

| সমস্যা | ব্যাখ্যা |
|---|---|
| **Cross-shard JOIN** | দুই shard-এর টেবিল JOIN করা খুব কঠিন ও ধীর |
| **Distributed Transaction** | দুই shard জুড়ে ACID নিশ্চিত করা প্রায় অসম্ভব |
| **Re-sharding** | shard সংখ্যা বদলানো একটা বিশাল কাজ |
| **অসম বণ্টন** | একটা shard-এ বেশি ডেটা জমে গেলে (celebrity problem) |

> **Celebrity Problem:** টুইটারে সাধারণ ইউজারের ১০০ ফলোয়ার, কিন্তু একজন তারকার ৫ কোটি। তারকার shard-টা ভেঙে পড়বে!

**💡 পরামর্শ:** Sharding **শেষ উপায়** হিসেবে ব্যবহার করুন। তার আগে চেষ্টা করুন — indexing, caching (Redis), read replica, vertical scaling। Sharding-এর জটিলতা অনেক বেশি।

## ৮. DBMS-এ Key কী কী?

**সংজ্ঞা:** Key হলো এমন এক বা একাধিক অ্যাট্রিবিউটের সেট, যা একটা টেবিলের প্রতিটা রেকর্ডকে **অনন্যভাবে শনাক্ত** করতে পারে।

| Key-এর ধরন | সংজ্ঞা |
|---|---|
| **Primary Key** | প্রতিটা রেকর্ড অনন্যভাবে শনাক্ত করে। অবশ্যই **unique** এবং **NULL নয়**। |
| **Foreign Key** | অন্য টেবিলের primary key-কে রেফার করে দুই টেবিলের মধ্যে সম্পর্ক তৈরি করে। |
| **Unique Key** | একটা বা কয়েকটা কলামের সব মান টেবিলজুড়ে অনন্য নিশ্চিত করে। NULL হতে পারে, তবে একক কলাম হলে **একটাই NULL** অনুমোদিত। |
| **Composite Key** | **২+ কলাম** মিলে তৈরি primary key। |
| **Candidate Key** | যেসব কলাম (primary key সহ) রেকর্ড অনন্যভাবে শনাক্ত করতে পারে। এদের একটাকে primary key বানানো হয়। |
| **Alternate Key** | যে candidate key কে primary key হিসেবে বাছা হয়নি। |

**বাস্তব উদাহরণ — একজন মানুষের পরিচয়:**

একজন বাংলাদেশি নাগরিককে অনন্যভাবে চেনা যায় —
- NID নম্বর দিয়ে
- পাসপোর্ট নম্বর দিয়ে
- মোবাইল নম্বর দিয়ে

এই তিনটাই **Candidate Key**।

সরকার ঠিক করল "আমরা NID-কে প্রধান পরিচয় ধরব" → NID হলো **Primary Key**।
বাকি দুটো (পাসপোর্ট, মোবাইল) হলো **Alternate Key**।

**কোডে দেখুন:**
```sql
CREATE TABLE students (
    student_id   INT PRIMARY KEY,              -- Primary Key
    nid          VARCHAR(20) UNIQUE,           -- Unique/Alternate Key
    email        VARCHAR(100) UNIQUE,          -- Unique Key
    name         VARCHAR(100) NOT NULL,
    dept_id      INT,
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id)   -- Foreign Key
);

-- Composite Key-এর উদাহরণ
CREATE TABLE enrollments (
    student_id INT,
    course_id  VARCHAR(10),
    grade      CHAR(2),
    PRIMARY KEY (student_id, course_id)    -- 👈 দুই কলাম মিলে Primary Key
);
```

**Composite Key কেন দরকার — বাস্তব উদাহরণ:**
একজন ছাত্র একাধিক কোর্স নিতে পারে, আর একটা কোর্সে অনেক ছাত্র থাকতে পারে। তাই শুধু `student_id` দিয়ে রো চেনা যাবে না (একই ছাত্রের ৫টা রো থাকবে), শুধু `course_id` দিয়েও না। কিন্তু **দুটো একসাথে** অনন্য — "করিম + CS101" এই জোড়াটা একবারই থাকবে। ✅

**Primary Key vs Unique Key:**

| | Primary Key | Unique Key |
|---|---|---|
| NULL রাখা যায়? | ❌ কখনো না | ✅ হ্যাঁ (একটা) |
| টেবিলে কয়টা? | **একটাই** | যত খুশি |
| index তৈরি হয়? | Clustered index | Non-clustered index |

**Foreign Key-এর শক্তি — Referential Integrity:**
```sql
DELETE FROM departments WHERE dept_id = 10;
-- ❌ Error: এই বিভাগে ছাত্র আছে, মোছা যাবে না!
```
এতে **অনাথ রেকর্ড (orphan record)** তৈরি হয় না — এমন ছাত্র থাকবে না যার বিভাগটাই অস্তিত্বহীন। ✅

## ৯. সম্পর্কের (Relationship) প্রকারভেদ কী কী?

### One-to-One (১:১)
এক টেবিলের প্রতিটা রেকর্ড অন্য টেবিলের **একটামাত্র** রেকর্ডের সাথে সম্পর্কিত, এবং উল্টোটাও সত্য।

**উদাহরণ:** `person` টেবিল ↔ `passport` টেবিল
> একজন মানুষের একটাই পাসপোর্ট, আর একটা পাসপোর্ট একজনেরই।

**কীভাবে বানাবেন:** যেকোনো এক টেবিলে অন্যটার primary key-কে **UNIQUE foreign key** হিসেবে রাখুন।

**কখন দরকার:** বড় টেবিলকে ভাগ করতে, বা কম ব্যবহৃত/সংবেদনশীল কলামগুলো আলাদা রাখতে।

---

### One-to-Many (১:n)
এক টেবিলের একটা রেকর্ড অন্য টেবিলের **অনেক** রেকর্ডের সাথে সম্পর্কিত।

**উদাহরণ:** `person` টেবিল → `order` টেবিল
> একজন গ্রাহকের অনেকগুলো অর্ডার থাকতে পারে, কিন্তু একটা অর্ডার একজন গ্রাহকেরই।

**কীভাবে বানাবেন:** **"অনেক" দিকের টেবিলে** foreign key রাখুন।
```sql
CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,                    -- 👈 এখানে FK
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

**⚠️ জুনিয়রদের কমন ভুল:** `customers` টেবিলে `order_id` রাখার চেষ্টা করা। কিন্তু একজন গ্রাহকের ৫০টা অর্ডার থাকলে ৫০টা কলাম লাগবে! ❌ FK সবসময় "many" দিকে।

---

### Many-to-Many (n:n)
এক টেবিলের অনেক রেকর্ড অন্য টেবিলের অনেক রেকর্ডের সাথে সম্পর্কিত।

**উদাহরণ:** `person` টেবিল ↔ `role` টেবিল
> একজন ব্যবহারকারীর অনেক ভূমিকা থাকতে পারে, আর একটা ভূমিকা অনেক ব্যবহারকারীর থাকতে পারে।

**কীভাবে বানাবেন:** সরাসরি করা **যায় না**! একটা **junction/bridge টেবিল** লাগে।

```sql
students          enrollments (junction)         courses
─────────         ──────────────────────         ───────
student_id  ←──── student_id                     
name              course_id  ─────────────────→  course_id
                  grade                          course_name
                  enrolled_date
```

```sql
CREATE TABLE enrollments (
    student_id INT,
    course_id  INT,
    grade      CHAR(2),                     -- 👈 বাড়তি তথ্যও রাখা যায়!
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(student_id),
    FOREIGN KEY (course_id)  REFERENCES courses(course_id)
);
```

**Junction টেবিলের বাড়তি সুবিধা:** সম্পর্কটা সম্পর্কে **অতিরিক্ত তথ্য** রাখা যায় — যেমন "কবে ভর্তি হলো", "কী গ্রেড পেল"। এটা অন্য কোনো টেবিলে রাখা যেত না, কারণ এটা ছাত্রের বৈশিষ্ট্যও নয়, কোর্সেরও নয় — **সম্পর্কের** বৈশিষ্ট্য।

## ১০. DBMS-এ Data Abstraction কী? এর ৩টা স্তর কী কী?

**সংজ্ঞা:** Data Abstraction মানে হলো ডেটাবেজের **ভেতরের জটিলতা ও কাঠামো ব্যবহারকারীর কাছ থেকে লুকিয়ে রাখা** — যাতে বিস্তারিত না জেনেই ডেটা নিয়ে কাজ করা যায়।

### তিনটা স্তর

**১) Physical Level (সংরক্ষণ স্তর) — সবচেয়ে নিচু স্তর**
ডেটা আসলে কীভাবে ডেটাবেজে সংরক্ষিত আছে সেটা নির্ধারণ করে। যেমন — ফাইল স্টোরেজ, ইনডেক্সিং ইত্যাদি।

**২) Logical Level (কাঠামো স্তর) — মাঝের স্তর**
কী কী ডেটা সংরক্ষিত আছে এবং সেই ডেটাগুলোর মধ্যে কী সম্পর্ক আছে সেটা নির্ধারণ করে।

**৩) View Level (ব্যবহারকারীর দৃষ্টিকোণ) — সর্বোচ্চ স্তর**
ব্যবহারকারী ও অ্যাপ্লিকেশনকে ডেটাবেজের **শুধু একটা অংশ** দেখায়।

**বাস্তব উদাহরণ — গাড়ি চালানো 🚗**

| স্তর | গাড়ির উপমা | কে জানে |
|---|---|---|
| **Physical** | ইঞ্জিনের ভেতরে পিস্টন কীভাবে চলে, জ্বালানি কীভাবে পোড়ে | মেকানিক / DB অ্যাডমিন |
| **Logical** | গাড়িতে ইঞ্জিন আছে, গিয়ারবক্স আছে, চাকার সাথে যুক্ত | ইঞ্জিনিয়ার / ডেভেলপার |
| **View** | স্টিয়ারিং, ব্রেক, অ্যাক্সিলারেটর | চালক / সাধারণ ব্যবহারকারী |

চালককে জানতে হয় না ইঞ্জিন কীভাবে কাজ করে — শুধু স্টিয়ারিং ঘোরালেই গাড়ি ঘোরে। এটাই abstraction।

**ডেটাবেজে বাস্তব উদাহরণ:**

```sql
-- Physical: এটা DBMS নিজে সামলায়
-- ডেটা /var/lib/postgresql/data/base/16384/2619 ফাইলে,
-- B+ tree ইনডেক্স, 8KB পেজে ভাগ করা...

-- Logical: স্কিমা
CREATE TABLE employees (
    id INT, name VARCHAR(100), salary DECIMAL, ssn VARCHAR(20)
);

-- View: HR ছাড়া কেউ বেতন বা SSN দেখবে না
CREATE VIEW public_employees AS
SELECT id, name FROM employees;
```

**Abstraction-এর সুবিধা — Data Independence:**

| ধরন | মানে |
|---|---|
| **Physical Data Independence** | HDD থেকে SSD-তে গেলেন, ইনডেক্স বদলালেন → **অ্যাপের কোড বদলাতে হবে না** ✅ |
| **Logical Data Independence** | টেবিলে নতুন কলাম যোগ করলেন → **যেসব view সেটা ব্যবহার করে না, তারা অক্ষত** ✅ |

## ১১. ডেটাবেজে Indexing

**সংজ্ঞা:** Indexing হলো এমন একটা কৌশল যা ডেটা উদ্ধারের গতি বাড়ায় — একটা **ডেটা স্ট্রাকচার (index)** তৈরি করে, যা টেবিলের রো-তে দ্রুত পৌঁছানোর ব্যবস্থা করে।

এটা কাজ করে **বইয়ের ইনডেক্সের মতো** — পুরো টেবিল স্ক্যান না করেই কাঙ্ক্ষিত ডেটা খুঁজে পাওয়া যায়। যেসব কলামে বেশি কোয়েরি হয়, সেগুলোতে ইনডেক্স বানালে বড় ডেটাবেজে বিশাল গতি পাওয়া যায়।

**বাস্তব উদাহরণ — বইয়ের ইনডেক্স 📖**

৫০০ পৃষ্ঠার একটা বইয়ে "Kubernetes" শব্দটা খুঁজতে হবে।
- **ইনডেক্স ছাড়া:** পৃষ্ঠা ১ থেকে ৫০০ পর্যন্ত পড়তে হবে → **Full Table Scan** 😩
- **ইনডেক্স দিয়ে:** পেছনের ইনডেক্সে গিয়ে "Kubernetes → পৃষ্ঠা ২৩৭" দেখে সোজা ২৩৭-এ যান ⚡

---

### ইনডেক্সিং কীভাবে কাজ করে — গণিত দিয়ে বুঝুন

ডেটাবেজ ডেটা রাখে **ডিস্কে**, আর ডেটা স্ট্রাকচার কাজ করে **RAM-এ**। ডিস্কে ডেটা থাকে **track ও sector**-এ; দুইটার ছেদবিন্দুকে বলে একটা **block**।

**ধরুন:**
- প্রতিটা block ধরে **৫১২ বিট** ডেটা (block offset ০ থেকে ৫১১)
- আমাদের টেবিলে **১০০টা রেকর্ড**, প্রতিটা রেকর্ড **১২৮ বিট**

**ইনডেক্স ছাড়া:**
```
১ block-এ রেকর্ড     = 512 / 128 = ৪টা
মোট block দরকার      = 100 / 4  = ২৫টা

একটা রেকর্ড খুঁজতে সবচেয়ে খারাপ ক্ষেত্রে → ২৫টা block পড়তে হবে 😩
```

**ইনডেক্স টেবিল যোগ করলে:**
প্রতিটা ইনডেক্স রো-তে থাকবে `(id, block-এর পয়েন্টার)` = **১৬ বিট**
```
১ block-এ ইনডেক্স রো  = 512 / 16 = ৩২টা
ইনডেক্সের জন্য block   = 100 / 32 ≈ ৪টা

এখন খুঁজতে লাগে → ৪ (ইনডেক্স) + ১ (আসল ডেটা) = ৫টা block ✅
```
**২৫ থেকে ৫ — ৫ গুণ দ্রুত!** ⚡

---

### Multi-level Indexing (Sparse Indexing)

ডেটা আরও বড় হলে ইনডেক্স নিজেই বিশাল হয়ে যায়। তখন **ইনডেক্সের ইনডেক্স** বানানো হয়।

**উদাহরণ — ১০০০টা রেকর্ড:**
```
ডেটা block      = 1000 / 4  = ২৫০টা
ইনডেক্স block   = 1000 / 32 ≈ ৪০টা     ← এটাও অনেক!
```

৪০টা block খোঁজাও ব্যয়বহুল। তাই **আরেকটা ইনডেক্স টেবিল** বানানো হয়, যেটা রেকর্ড নয় বরং **block-এর পয়েন্টার** রাখে।

```
২য় স্তরের ইনডেক্সে key হবে: 1, 33, 65, ...
                (প্রতিটা ইনডেক্স block-এর প্রথম key)
২য় স্তরের block  ≈ ২টা

এখন খুঁজতে লাগে → ২ + ১ + ১ = মাত্র ৪টা block ✅
```

**বাস্তব উদাহরণ — ঠিকানা খোঁজা 🗺️**
```
১ম স্তর: বিভাগ ঠিক করলাম (ঢাকা)      → ২ ধাপ
২য় স্তর: জেলা ঠিক করলাম (গাজীপুর)    → ১ ধাপ
৩য় স্তর: আসল বাড়ি                    → ১ ধাপ
```
পুরো দেশের সব বাড়ি একে একে খোঁজার চেয়ে অনেক দ্রুত!

---

**⚠️ ইনডেক্সের অসুবিধাও আছে:**

| অসুবিধা | ব্যাখ্যা |
|---|---|
| **জায়গা লাগে** | ইনডেক্স নিজেও ডিস্কে জায়গা নেয় |
| **লেখা ধীর হয়** | `INSERT`/`UPDATE`/`DELETE` করলে ইনডেক্সও আপডেট করতে হয় |
| **রক্ষণাবেক্ষণ** | সময়ের সাথে ইনডেক্স খণ্ডিত (fragmented) হয় |

> **নিয়ম:** যে কলামে **`WHERE`, `JOIN`, `ORDER BY`** বেশি ব্যবহার হয় — সেখানে ইনডেক্স দিন। প্রতিটা কলামে ইনডেক্স দেবেন না!

**একটা ফাঁদ — কম বৈচিত্র্যের (low cardinality) কলাম:**
```sql
CREATE INDEX idx_gender ON users(gender);   -- ❌ অর্থহীন
```
মাত্র ২-৩টা আলাদা মান থাকলে ইনডেক্স কোনো কাজে আসে না — ডেটাবেজ সরাসরি স্ক্যান করাই বেছে নেবে।

**Composite Index-এ ক্রম গুরুত্বপূর্ণ:**
```sql
CREATE INDEX idx ON orders(customer_id, order_date);

WHERE customer_id = 5                          -- ✅ ইনডেক্স কাজে লাগবে
WHERE customer_id = 5 AND order_date > '2024'  -- ✅ কাজে লাগবে
WHERE order_date > '2024'                      -- ❌ কাজে লাগবে না!
```
এটা **ফোন বইয়ের মতো** — (পদবি, নাম) ক্রমে সাজানো। পদবি জানলে খুঁজে পাবেন, শুধু নাম জানলে পাবেন না।

## ১২. Indexing বনাম Sharding

- যদি লক্ষ্য হয় **সামলানোর মতো আকারের** ডেটাবেজে কোয়েরির গতি বাড়ানো → **Indexing** ভালো পছন্দ।
- যদি **বিশাল ডেটাসেট** সামলাতে হয় এবং **একাধিক সার্ভারে** ছড়াতে হয় → **Sharding** উপযুক্ত।

**পার্থক্যটা সহজভাবে:**

| | Indexing | Sharding |
|---|---|---|
| কী সমাধান করে | **ধীর কোয়েরি** | **অতিরিক্ত ডেটা/লোড** |
| কোথায় কাজ করে | একটা সার্ভারের ভেতরে | অনেক সার্ভার জুড়ে |
| জটিলতা | কম, সহজে যোগ/বাদ দেওয়া যায় | অনেক বেশি |
| উপমা | বইয়ের ইনডেক্স | লাইব্রেরির আলাদা শাখা |

**সিদ্ধান্তের ক্রম (এই ক্রমেই চেষ্টা করুন):**
```
১. কোয়েরি অপ্টিমাইজ করুন (EXPLAIN দেখুন)
২. ইনডেক্স যোগ করুন                    ← সহজ, সস্তা
৩. ক্যাশিং (Redis) যোগ করুন
৪. Read Replica যোগ করুন
৫. Vertical scaling (বড় সার্ভার)
৬. Sharding                            ← শেষ উপায়, সবচেয়ে জটিল
```

## ১৩. B Tree এবং B+ Tree

এগুলো **m-way search tree** ব্যবহার করে কিছু নিয়ম মেনে, আর কাজ করে **multi-level indexing** হিসেবে।

**m-way tree-এ B tree যেসব নিয়ম মানে** (m = সন্তানের সংখ্যা, k = key-এর সংখ্যা, এবং k = m−1):

1. root ছাড়া প্রতিটা নোডে key থাকবে কমপক্ষে **⌈m/2⌉ − 1** টা।
2. root-এর কমপক্ষে **২টা** সন্তান থাকতে পারে।
3. সব **পাতা (leaf) একই স্তরে** থাকবে। উচ্চতা = log_m(n), যেখানে n = রেকর্ড সংখ্যা।
4. তৈরির প্রক্রিয়া **নিচ থেকে উপরে (bottom-up)**।

**B tree ও B+ tree-এর পার্থক্য:** B+ tree-তে **সব key এবং তাদের রেকর্ড পয়েন্টার পাতায় সংরক্ষিত** থাকে, আর **সব পাতা একটা linked list দিয়ে যুক্ত** থাকে। এতে **রেঞ্জ কোয়েরি** খুব দ্রুত হয়।

---

**কেন Binary Search Tree নয়, B Tree কেন?**

এটাই সবচেয়ে গুরুত্বপূর্ণ প্রশ্ন। উত্তরটা **ডিস্কে**।

```
RAM থেকে পড়তে       → ~১০০ ন্যানোসেকেন্ড
ডিস্ক থেকে পড়তে      → ~১০ মিলিসেকেন্ড  = ১০০,০০০ গুণ ধীর! 🐌
```

ডিস্ক একবারে **একটা পুরো block** পড়ে (সাধারণত ৪ KB বা ৮ KB)। তাই আমরা চাই — **যত কম বার ডিস্কে যেতে হয়**।

**তুলনা করুন (১০ লক্ষ রেকর্ড):**

| | Binary Search Tree | B Tree (m=100) |
|---|---|---|
| প্রতি নোডে key | ১টা | ৯৯টা |
| উচ্চতা | log₂(10⁶) ≈ **২০** | log₁₀₀(10⁶) = **৩** |
| ডিস্ক পড়া | **২০ বার** = ২০০ ms 😩 | **৩ বার** = ৩০ ms ⚡ |

B tree-এর প্রতিটা নোড ঠিক **একটা ডিস্ক block-এর সমান** বানানো হয়। এক পড়াতেই ৯৯টা key পাওয়া যায়!

> **উপমা:** BST হলো — প্রতিবার দোকানে গিয়ে **একটা করে জিনিস** কেনা। B Tree হলো — একবার গিয়ে **পুরো মাসের বাজার** করে আনা। যাতায়াতটাই আসল খরচ।

---

**B Tree বনাম B+ Tree — ছবিতে:**

```
B Tree:  ডেটা সব নোডেই থাকে
                [ ৫০ (ডেটা) ]
               /             \
      [২০(ডেটা)]            [৮০(ডেটা)]

B+ Tree: ডেটা শুধু পাতায়, পাতাগুলো linked list
                [ ৫০ ]              ← শুধু দিকনির্দেশ
               /      \
      [১০|২০|৩০] ←→ [৫০|৭০|৮০]     ← সব ডেটা এখানে + যুক্ত
```

**B+ Tree কেন ভালো (এজন্যই সব ডেটাবেজ এটাই ব্যবহার করে):**

| সুবিধা | ব্যাখ্যা |
|---|---|
| **আরও fan-out** | ভেতরের নোডে ডেটা নেই, তাই বেশি key ধরে → গাছ আরও খাটো |
| **রেঞ্জ কোয়েরি দ্রুত** | পাতাগুলো linked list, তাই `WHERE age BETWEEN 20 AND 30` করলে শুধু পাশে হেঁটে গেলেই হয় ✅ |
| **সব খোঁজা সমান** | সব ডেটা পাতায়, তাই প্রতিটা খোঁজায় একই সংখ্যক ডিস্ক পড়া |
| **পুরো স্ক্যান সহজ** | সবচেয়ে বাঁয়ের পাতা থেকে শুরু করে ডানে হাঁটলেই সব ডেটা |

**B Tree-তে রেঞ্জ কোয়েরির সমস্যা:** ডেটা সব স্তরে ছড়িয়ে আছে, তাই বারবার উপরে-নিচে যেতে হয়। B+ tree-তে শুধু **সরলরেখায় হাঁটা**। 🚶

> 📺 আরও ভালোভাবে বুঝতে **Abdul Bari**-এর ভিডিও দেখুন।

**বাস্তব ব্যবহার:** MySQL (InnoDB), PostgreSQL, Oracle, SQL Server — সবাই **B+ Tree** ব্যবহার করে।

## ১৪. Normalization কী? এর প্রকারভেদ কী?

**সংজ্ঞা:** এটা ডেটাবেজে ডেটা সংগঠিত করার একটা প্রক্রিয়া, যা **পুনরাবৃত্তি (redundancy) কমায়** — ডেটাবেজকে কয়েকটা টেবিলে ভাগ করে এবং তাদের মধ্যে সম্পর্ক নির্ধারণ করে ডেটা দক্ষভাবে সংরক্ষণ নিশ্চিত করে।

**Normalization কেন দরকার — সমস্যাটা দেখুন:**

একটা টেবিলে সব রাখলে:
```
┌────┬───────┬─────────┬──────────────┬─────────────────┐
│ id │ নাম    │ কোর্স    │ শিক্ষক        │ শিক্ষকের ফোন     │
├────┼───────┼─────────┼──────────────┼─────────────────┤
│ 1  │ করিম   │ গণিত     │ ড. রহমান     │ ০১৭১১১১১১১১     │
│ 2  │ রহিম   │ গণিত     │ ড. রহমান     │ ০১৭১১১১১১১১     │  ← পুনরাবৃত্তি!
│ 3  │ সাকিব  │ গণিত     │ ড. রহমান     │ ০১৭১১১১১১১১     │  ← পুনরাবৃত্তি!
└────┴───────┴─────────┴──────────────┴─────────────────┘
```

**তিন ধরনের সমস্যা (Anomaly):**

| Anomaly | সমস্যা |
|---|---|
| **Update Anomaly** | ড. রহমানের ফোন বদলালে **৩ জায়গায়** বদলাতে হবে। একটা ভুলে গেলে ডেটা অসামঞ্জস্যপূর্ণ! |
| **Insert Anomaly** | নতুন শিক্ষক নিয়োগ দিলেন, কিন্তু এখনো কোনো ছাত্র নেই → **তাকে যোগই করা যাচ্ছে না** |
| **Delete Anomaly** | তিন ছাত্রই কোর্স ছেড়ে দিল → **ড. রহমানের তথ্যও মুছে গেল!** 💀 |

---

### Normalization-এর ধাপগুলো

**১) First Normal Form (1NF):**
টেবিল থেকে **পুনরাবৃত্ত কলাম বাদ দিন**। প্রতিটা ঘরে একটাই মান থাকবে।

```
❌ 1NF নয়:
│ student │ course1 │ course2 │ course3 │
│ করিম     │ গণিত     │ পদার্থ    │ রসায়ন   │

✅ 1NF:
│ student │ course  │
│ করিম     │ গণিত     │
│ করিম     │ পদার্থ    │
│ করিম     │ রসায়ন    │
```

> **নিয়ম:** এক ঘরে একটাই মান, কোনো তালিকা নয়। `"গণিত,পদার্থ,রসায়ন"` এভাবে লেখাও 1NF ভঙ্গ।

**২) Second Normal Form (2NF):**
1NF-এর সব শর্ত পূরণ করবে, **এবং** non-key অ্যাট্রিবিউটগুলো **পুরো primary key-এর উপর সম্পূর্ণভাবে নির্ভরশীল** হবে।

```
❌ 2NF নয়: (id, course) → primary key
│ id │ name │ course │ instructor │
      ↑
   name শুধু id-এর উপর নির্ভরশীল, course-এর উপর নয় → Partial Dependency!

✅ 2NF: দুই টেবিলে ভাগ করুন
students:    │ id │ name │
enrollments: │ id │ course │ instructor │
```

> **2NF শুধু composite key থাকলে প্রাসঙ্গিক।** Primary key একটা কলাম হলে 1NF হলেই 2NF হয়ে যায়।

**৩) Third Normal Form (3NF):**
2NF-এর সব শর্ত পূরণ করবে, **এবং** non-key অ্যাট্রিবিউটগুলো **শুধু primary key-এর উপরই** নির্ভরশীল হবে — অন্য কোনো non-key অ্যাট্রিবিউটের উপর নয়। এটা **transitive dependency** দূর করে।

```
❌ 3NF নয়:
│ id │ course │ instructor │
                  ↑
   instructor আসলে course-এর উপর নির্ভরশীল, id-এর উপর নয়
   id → course → instructor  (transitive!)

✅ 3NF: ভাগ করুন
enrollments: │ id │ course │
courses:     │ course │ instructor │
```

> **মনে রাখার ছড়া:** *"The key, the whole key, and nothing but the key."*
> - **The key** → 1NF
> - **The whole key** → 2NF
> - **Nothing but the key** → 3NF

**৪) Boyce-Codd Normal Form (BCNF):**
3NF-এর একটা উন্নত সংস্করণ। প্রতিটা determinant অবশ্যই একটা candidate key হতে হবে।

---

**Normalization-এর অসুবিধা:**
- জটিলতা বাড়ে
- পারফরম্যান্স খরচ (**JOIN** করতে হয়)
- ল্যাটেন্সি বেড়ে যায়
- রক্ষণাবেক্ষণের ঝামেলা

```sql
-- 3NF-এ একটা সহজ প্রশ্নের জন্যও অনেক JOIN
SELECT s.name, c.course_name, i.instructor_name, d.dept_name
FROM students s
JOIN enrollments e ON s.id = e.student_id
JOIN courses c ON e.course_id = c.id
JOIN instructors i ON c.instructor_id = i.id
JOIN departments d ON i.dept_id = d.id;
```
৫টা টেবিল JOIN — লক্ষ লক্ষ রো থাকলে ধীর হয়ে যাবে। 🐌

**💡 বাস্তব পরামর্শ:** **3NF পর্যন্ত normalize করুন** — এটাই মিষ্টি জায়গা (sweet spot)। 4NF, 5NF তাত্ত্বিকভাবে সুন্দর, কিন্তু বাস্তবে খুব কমই দরকার হয়।

## ১৫. Denormalization কী?

**সংজ্ঞা:** Denormalization হলো ডেটাবেজে **ইচ্ছাকৃতভাবে পুনরাবৃত্তি যোগ করা** — টেবিল একত্র করে বা ডুপ্লিকেট ডেটা রেখে **পড়ার গতি বাড়ানোর** জন্য। JOIN-এর সংখ্যা কমাতে এটা করা হয়।

**সুবিধা:**
- পড়ার পারফরম্যান্স বাড়ে
- কোয়েরি সহজ হয়ে যায়

**অসুবিধা:**
- পুনরাবৃত্তির কারণে বেশি স্টোরেজ লাগে
- ডেটা anomaly-এর ঝুঁকি — একই ডেটা বিভিন্ন জায়গায় থাকায় অসামঞ্জস্য হতে পারে

**কখন ব্যবহার করবেন:** যখন **লেখার চেয়ে পড়ার কাজ অনেক বেশি** হয়।

**বাস্তব উদাহরণ — একটা ব্লগ সাইট 📝**

```sql
-- Normalized (3NF)
SELECT p.title, u.name, COUNT(c.id) AS comment_count
FROM posts p
JOIN users u ON p.user_id = u.id
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, u.name;
-- প্রতিটা পেজ লোডে এই ভারী কোয়েরি! 😩

-- Denormalized
SELECT title, author_name, comment_count FROM posts;
-- এক টেবিল, কোনো JOIN নেই ⚡
```

`posts` টেবিলে `author_name` আর `comment_count` **কপি করে রাখা হলো**।

**দাম কী দিতে হবে:**
- লেখকের নাম বদলালে → **সব পোস্টে** আপডেট করতে হবে
- নতুন কমেন্ট এলে → `comment_count` বাড়াতে হবে

কিন্তু একটা ব্লগে **পড়া হয় লক্ষবার, লেখা হয় হাজারবার** — তাই এই দাম দেওয়াই লাভজনক। ✅

**Denormalization-এর সাধারণ কৌশল:**

| কৌশল | উদাহরণ |
|---|---|
| **Pre-computed value** | `comment_count`, `total_amount` আগেই হিসাব করে রাখা |
| **Duplicated column** | `orders` টেবিলে `customer_name` কপি রাখা |
| **Materialized View** | জটিল কোয়েরির ফলাফল টেবিল হিসেবে সংরক্ষণ |
| **Table merging** | ১:১ সম্পর্কের দুই টেবিল একত্র করা |

**⚠️ ডেটা সিঙ্ক রাখার উপায়:**
- **Trigger** ব্যবহার করুন (ডেটাবেজ নিজে আপডেট করবে)
- **Application logic**-এ সাবধানে হ্যান্ডল করুন
- নিয়মিত **reconciliation job** চালান যেটা অসামঞ্জস্য ধরবে

**সোনালি নিয়ম:** *"Normalize until it hurts, denormalize until it works."*
মানে — **আগে normalize করুন, তারপর পরিমাপ করে দেখুন কোথায় ধীর হচ্ছে**, শুধু সেখানেই denormalize করুন। আগে থেকেই অনুমান করে denormalize করবেন না।

## ১৬. Functional Dependency কী?

**সংজ্ঞা:** Functional Dependency হলো এমন একটা শর্ত, যা দুই সেট অ্যাট্রিবিউটের মধ্যে সম্পর্ক নির্দেশ করে — যেখানে একটা সেট অন্য সেটের মান **নির্ভুলভাবে নির্ধারণ** করতে পারে।

লেখা হয় **X → Y** আকারে, যেখানে X হলো এমন অ্যাট্রিবিউটের সেট যা Y-এর মান নির্ধারণ করতে পারে।
- বাঁ পাশের X-কে বলে **Determinant** (নির্ধারক)
- ডান পাশের Y-কে বলে **Dependent** (নির্ভরশীল)

**উদাহরণ:** `user_id → user_name`

**বাস্তব উদাহরণ — NID নম্বর:**
```
NID → নাম, জন্মতারিখ, পিতার নাম, ঠিকানা
```
NID নম্বর জানলে বাকি সব তথ্য জানা যায়। **কিন্তু উল্টোটা সত্য নয়** — "করিম" নাম জানলে NID বলা যায় না, কারণ অনেক করিম আছে!

**তীরচিহ্নটা একমুখী** — এটাই মূল কথা।

**কয়েক ধরনের Functional Dependency:**

| ধরন | উদাহরণ | ব্যাখ্যা |
|---|---|---|
| **Trivial** | `{id, name} → name` | ডান পাশ বাঁ পাশের ভেতরেই আছে (তুচ্ছ) |
| **Non-trivial** | `id → name` | ডান পাশ বাঁ পাশে নেই (এটাই আসল কাজের) |
| **Partial** | `{id, course} → name` | শুধু `id` দিয়েই `name` পাওয়া যায় → 2NF ভঙ্গ |
| **Transitive** | `id → course → instructor` | ঘুরপথে নির্ভরশীলতা → 3NF ভঙ্গ |

**কেন এটা গুরুত্বপূর্ণ:** Functional Dependency-ই হলো **normalization-এর ভিত্তি**। কোন টেবিল কীভাবে ভাগ করতে হবে সেটা এই নির্ভরশীলতা দেখেই ঠিক করা হয়।

**একটা বাস্তব বিশ্লেষণ:**
```
টেবিল: (student_id, course_id, grade, instructor, instructor_phone)

নির্ভরশীলতা খুঁজি:
  {student_id, course_id} → grade         ✅ ঠিক আছে
  course_id → instructor                   ⚠️ Partial dependency (2NF ভঙ্গ)
  instructor → instructor_phone            ⚠️ Transitive (3NF ভঙ্গ)

সমাধান — তিন টেবিলে ভাগ:
  enrollments  (student_id, course_id, grade)
  courses      (course_id, instructor)
  instructors  (instructor, instructor_phone)
```

## ১৭. ER Diagram কী?

**সংজ্ঞা:** এটা একটা ধারণাগত কাঠামো (conceptual framework), যা ডেটাবেজের গঠন বর্ণনা ও ডিজাইন করতে ব্যবহৃত হয়।

এটা ডেটাকে তিনটা জিনিসে উপস্থাপন করে:
- **Entity** (বাস্তব জগতের বস্তু) — যেমন student, course
- **Attribute** (entity-এর বৈশিষ্ট্য) — যেমন student_id, student_name, course_id
- **Relationship** (entity-দের মধ্যে সংযোগ) — যেমন "student enrolls course", "professor teaches course"

**দুই ধরনের সম্পর্ক:**
- **'is a' সম্পর্ক (Inheritance/উত্তরাধিকার):** shape → triangle, circle
- **'has a' সম্পর্ক (Association/সংযোগ):** car → engine

**ER Diagram-এর প্রতীকগুলো:**

| আকৃতি | কী বোঝায় |
|---|---|
| **আয়তক্ষেত্র** ▭ | Entity |
| **দ্বৈত আয়তক্ষেত্র** ▤ | Weak Entity |
| **উপবৃত্ত** ⬭ | Attribute |
| **রেখাঙ্কিত উপবৃত্ত** | Key Attribute |
| **হীরক** ◇ | Relationship |
| **রেখা** | সংযোগ |

**একটা উদাহরণ — কলেজ ডেটাবেজ:**

```
   ⬭student_id      ⬭name              ⬭course_id    ⬭title
        \             /                      \          /
         ▭ STUDENT ▭ ──── ◇ ENROLLS ◇ ──── ▭ COURSE ▭
              │              (n:n)                │
              │                                   │
              └────── ◇ BELONGS ◇ ── ▭DEPT▭ ──────┘
                        (n:1)
```

**Cardinality (সংখ্যাগত সম্পর্ক) লেখার নিয়ম:**
```
STUDENT ──1────n── ORDER          একজন ছাত্রের অনেক অর্ডার
PERSON  ──1────1── PASSPORT       একজনের একটা পাসপোর্ট
STUDENT ──n────n── COURSE         অনেকে অনেক কোর্স
```

**'is a' বনাম 'has a' — খুব গুরুত্বপূর্ণ পার্থক্য:**

| | 'is a' (Inheritance) | 'has a' (Composition) |
|---|---|---|
| মানে | একটা **অন্যটার ধরন** | একটার **ভেতরে** অন্যটা আছে |
| উদাহরণ | ত্রিভুজ **হলো একটা** আকৃতি | গাড়ির **আছে** একটা ইঞ্জিন |
| ডেটাবেজে | আলাদা টেবিল + শেয়ার্ড PK | Foreign key |

**বাস্তব উদাহরণ:**
```
'is a':  Employee → Manager, Engineer, Salesperson
         (ম্যানেজার একজন কর্মচারীই, তার বাড়তি কিছু বৈশিষ্ট্য আছে)

'has a': Order → OrderItems
         (একটা অর্ডারের ভেতরে কয়েকটা আইটেম আছে)
```

**ER Diagram থেকে টেবিলে রূপান্তর:**
1. প্রতিটা **strong entity** → একটা টেবিল
2. প্রতিটা **weak entity** → টেবিল + মালিকের PK যোগ
3. **1:n সম্পর্ক** → "n" দিকের টেবিলে FK
4. **n:n সম্পর্ক** → নতুন junction টেবিল
5. **Multi-valued attribute** → আলাদা টেবিল

## ১৮. DBMS-এ Conflict Serializability কী?

**সংজ্ঞা:** Conflict Serializability হলো এমন একটা ধারণা যা **সমকালীন ট্রানজেকশনের নির্ভুলতা** নিশ্চিত করে। এটা পরীক্ষা করে দেখে — একটা নির্দিষ্ট **schedule** (অপারেশনের ক্রম) কে **serial schedule**-এ (যেখানে ট্রানজেকশনগুলো একটার পর একটা চলে) রূপান্তর করা যায় কিনা, **ফলাফল না বদলে**।

**সমস্যাটা কী:**

ট্রানজেকশন একটার পর একটা চালালে (serial) নিরাপদ, কিন্তু **ধীর**। একসাথে চালালে (concurrent) দ্রুত, কিন্তু **ঝুঁকিপূর্ণ**।

Conflict Serializability বলে দেয় — এই concurrent চালানোটা **নিরাপদ কিনা**।

**Conflict কখন হয়?** দুইটা অপারেশন conflicting হবে যদি:
1. তারা **আলাদা ট্রানজেকশনের** হয়, **এবং**
2. **একই ডেটা** নিয়ে কাজ করে, **এবং**
3. অন্তত **একটা write** হয়

| অপারেশন জোড়া | Conflict? |
|---|---|
| Read – Read | ❌ না (দুজন একসাথে পড়লে সমস্যা নেই) |
| Read – Write | ✅ হ্যাঁ |
| Write – Read | ✅ হ্যাঁ |
| Write – Write | ✅ হ্যাঁ |

**বাস্তব উদাহরণ — নোটিশ বোর্ড 📋**
- দুজন একসাথে **পড়ছে** → কোনো সমস্যা নেই ✅
- একজন **পড়ছে**, আরেকজন **মুছে লিখছে** → পাঠক অর্ধেক পুরনো অর্ধেক নতুন পড়বে! ❌

**কীভাবে যাচাই করবেন — Precedence Graph (আগে-পরে গ্রাফ):**

```
১. প্রতিটা ট্রানজেকশনের জন্য একটা নোড আঁকুন
২. Ti-এর একটা অপারেশন Tj-এর অপারেশনের সাথে conflict করলে
   এবং Ti আগে হলে → Ti থেকে Tj-তে একটা তীর আঁকুন
৩. গ্রাফে কি চক্র (cycle) আছে?
      চক্র নেই  → Conflict Serializable ✅ নিরাপদ
      চক্র আছে  → নয় ❌ বিপজ্জনক
```

**একটা উদাহরণ:**
```
T1: Read(A), Write(A)
T2: Read(A), Write(A)

Schedule: R1(A), W1(A), R2(A), W2(A)
গ্রাফ: T1 → T2   (চক্র নেই) ✅ নিরাপদ

Schedule: R1(A), R2(A), W1(A), W2(A)
গ্রাফ: T1 → T2 এবং T2 → T1   (চক্র!) ❌ বিপজ্জনক
```

**কেন এটা জানা দরকার:** ডেটাবেজের **scheduler** এই যাচাইটা করেই ঠিক করে কোন অপারেশন এখন চালানো নিরাপদ আর কোনটা অপেক্ষা করাতে হবে।

## ১৯. CCP (Concurrency Control Protocol) কী?

**সংজ্ঞা:** Concurrency Control Protocol ডেটাবেজে **একসাথে চলা ট্রানজেকশনগুলো সামলায়**, যাতে ডেটার সামঞ্জস্য ও অখণ্ডতা বজায় থাকে।

### ১) Lock-Based Protocol
**লক** ব্যবহার করে একাধিক ট্রানজেকশনকে একই ডেটায় একসাথে হাত দিতে বাধা দেয়।

> **উপমা:** বাথরুমের দরজার ছিটকিনি 🚪 — একজন ঢুকে বন্ধ করে দিল, বাকিরা অপেক্ষা করবে।

**Two-Phase Locking (2PL)** — সবচেয়ে প্রচলিত:
```
Growing Phase (বৃদ্ধির পর্যায়)  : শুধু লক নিতে পারবে
Shrinking Phase (সংকোচন পর্যায়) : শুধু লক ছাড়তে পারবে

একবার একটা লক ছেড়ে দিলে আর নতুন লক নেওয়া যাবে না।
```

**⚠️ Lock-এর সবচেয়ে বড় সমস্যা — Deadlock:**
```
T1: A লক করল → এখন B চায়
T2: B লক করল → এখন A চায়
       → দুজনেই চিরকাল অপেক্ষা করবে! 💀
```

**সমাধান:**
- **Deadlock Detection:** wait-for graph বানিয়ে চক্র খুঁজুন, একটা ট্রানজেকশন মেরে ফেলুন
- **Deadlock Prevention:** সবসময় একই ক্রমে লক নিন (যেমন সবাই আগে A, তারপর B)
- **Timeout:** নির্দিষ্ট সময় পর অপেক্ষা ছেড়ে দিন

### ২) Timestamp-Based Protocol
প্রতিটা ট্রানজেকশনকে একটা **অনন্য টাইমস্ট্যাম্প** দেওয়া হয়, আর অপারেশনগুলো টাইমস্ট্যাম্পের ক্রমে চালানো নিশ্চিত করা হয়।

> **উপমা:** ব্যাংকের **টোকেন নম্বর** 🎫 — যে আগে এসেছে, তার নম্বর ছোট, সে আগে সেবা পাবে।

কোনো ট্রানজেকশন যদি "সময়ের বিরুদ্ধে" কিছু করার চেষ্টা করে (যেমন পুরনো ট্রানজেকশন নতুনের লেখা ডেটা বদলাতে চায়), তাহলে তাকে **abort** করে আবার শুরু করানো হয়।

**সুবিধা:** কোনো লক নেই → **কোনো deadlock নেই** ✅
**অসুবিধা:** অনেক ট্রানজেকশন abort হতে পারে

### ৩) Validation-Based Protocol (Optimistic Concurrency Control)
ট্রানজেকশনগুলোকে **লক ছাড়াই চলতে দেয়**, আর commit করার **আগে** conflict আছে কিনা যাচাই করে।

**তিনটা পর্যায়:**
```
১. Read Phase      → নিজের ব্যক্তিগত কপিতে সব কাজ করো
২. Validation Phase → "আমি কাজ করার সময় কেউ কি এই ডেটা বদলেছে?"
৩. Write Phase     → ঠিক থাকলে লিখে ফেলো, নাহলে সব বাতিল করে আবার শুরু
```

> **উপমা:** গুগল ডকসে অফলাইনে লিখলেন, তারপর অনলাইনে এসে সিঙ্ক করলেন। কেউ যদি একই লাইন বদলে থাকে → conflict, নাহলে সহজেই মিশে গেল। ✅

**কখন ভালো:** যখন **conflict কম হয়** — যেমন বেশিরভাগ কাজই পড়া।
**কখন খারাপ:** conflict বেশি হলে বারবার কাজ বাতিল হবে → অপচয়।

**তিনটার তুলনা:**

| | Lock-based | Timestamp | Validation |
|---|---|---|---|
| দর্শন | নিরাশাবাদী (Pessimistic) | ক্রম মানা | আশাবাদী (Optimistic) |
| Deadlock | ✅ হতে পারে | ❌ হয় না | ❌ হয় না |
| Abort | কম | বেশি | conflict বেশি হলে বেশি |
| কখন ভালো | লেখা বেশি | মাঝারি | পড়া বেশি |

## ২০. Entity, Entity Type, Entity Set, Weak Entity Set কী?

**Entity:** বাস্তব জগতের এমন একটা বস্তু যার অস্তিত্ব আছে। যেমন — একটা কলেজ ডেটাবেজে entity হতে পারে Professor, Student, Course ইত্যাদি।

**Entity Type:** একই ধরনের অ্যাট্রিবিউট থাকা entity-দের সংগ্রহ।

### Entity Type-এর প্রকারভেদ

**ক) Strong Entity Type:**
এই ধরনে **primary key** দিয়ে প্রতিটা entity অনন্যভাবে শনাক্ত করা হয়। ER diagram-এ **আয়তক্ষেত্র** দিয়ে দেখানো হয়।

**খ) Weak Entity Type:**
এর কোনো key অ্যাট্রিবিউট নেই। নিজে নিজে শনাক্ত হতে পারে না — অনন্য পরিচয়ের জন্য কোনো **strong entity-এর উপর নির্ভর করে**।

**Entity Set:** একই entity type-এর entity-দের সংগ্রহ। একটা নির্দিষ্ট entity type-এর সব entity-র সেটকে বোঝায়।

---

**পার্থক্যগুলো সহজভাবে:**

| শব্দ | মানে | উদাহরণ |
|---|---|---|
| **Entity** | একটা নির্দিষ্ট বস্তু | "করিম, রোল ১০১" |
| **Entity Type** | ধরনটা (নকশা) | `STUDENT` |
| **Entity Set** | ঐ ধরনের সব entity | ডেটাবেজে থাকা সব ছাত্র |

> **প্রোগ্রামিংয়ের সাথে মিলিয়ে দেখুন:**
> - Entity Type = **class**
> - Entity = **object**
> - Entity Set = **সব object-এর তালিকা** (টেবিলের সব রো)

---

**Weak Entity বাস্তব উদাহরণ দিয়ে বুঝুন:**

**উদাহরণ ১ — কর্মচারী ও তার সন্তান:**
```
EMPLOYEE (strong)          DEPENDENT (weak)
─────────────────          ─────────────────
emp_id (PK)                name       ← শুধু নাম দিয়ে চেনা যায় না!
name                       age          (অনেক "রফিক" নামের সন্তান থাকতে পারে)
                           relation
```

`DEPENDENT`-কে চিনতে হলে **`emp_id` + `name`** দুটোই লাগবে।
মানে — "করিম সাহেবের ছেলে রফিক" — এভাবে বলতে হবে। শুধু "রফিক" বললে হবে না।

```sql
CREATE TABLE dependents (
    emp_id INT,
    name   VARCHAR(100),
    age    INT,
    PRIMARY KEY (emp_id, name),           -- 👈 partial key + owner-এর PK
    FOREIGN KEY (emp_id) REFERENCES employees(emp_id)
        ON DELETE CASCADE                 -- 👈 কর্মচারী মুছলে সন্তানও মুছবে
);
```

**উদাহরণ ২ — অর্ডার ও তার আইটেম:**
```
ORDER (strong)             ORDER_ITEM (weak)
──────────────             ─────────────────
order_id (PK)              line_number   ← "১ নম্বর লাইন" — কোন অর্ডারের?
order_date                 product_id
                           quantity
```

**Weak Entity-এর তিনটা বৈশিষ্ট্য:**
1. নিজস্ব কোনো পূর্ণ primary key নেই — আছে **partial key** (discriminator)
2. একটা **identifying relationship** দিয়ে strong entity-র সাথে যুক্ত
3. মালিক মুছে গেলে **weak entity-ও মুছে যায়** (existence dependency)

**ER Diagram-এ প্রতীক:**
```
▭ STRONG ▭ ═══◇ IDENTIFYING ◇═══ ▤ WEAK ▤
                (দ্বৈত হীরক)        (দ্বৈত আয়তক্ষেত্র)
```

## ২১. SQL কমান্ডগুলো কী কী?

*(মূল ডকুমেন্টে এই অংশটা খালি ছিল, তাই সম্পূর্ণ করে দিলাম।)*

SQL কমান্ডগুলো ৪ নম্বর প্রশ্নের ভাষা-শ্রেণী অনুযায়ী ভাগ করা যায়:

### DDL — কাঠামো নিয়ে কাজ
```sql
CREATE TABLE students (id INT PRIMARY KEY, name VARCHAR(100));
ALTER TABLE students ADD COLUMN email VARCHAR(100);
DROP TABLE students;                  -- ⚠️ টেবিলসহ সব ডেটা মুছে যাবে
TRUNCATE TABLE students;              -- ⚠️ ডেটা মুছবে, টেবিল থাকবে
RENAME TABLE students TO learners;
```

### DML — ডেটা নিয়ে কাজ
```sql
SELECT * FROM students WHERE id = 1;
INSERT INTO students (id, name) VALUES (1, 'করিম');
UPDATE students SET name = 'করিম উদ্দিন' WHERE id = 1;
DELETE FROM students WHERE id = 1;
```

### DCL — অনুমতি নিয়ে কাজ
```sql
GRANT SELECT, INSERT ON students TO 'teacher'@'localhost';
REVOKE INSERT ON students FROM 'teacher'@'localhost';
```

### TCL — ট্রানজেকশন নিয়ে কাজ
```sql
BEGIN;                                -- ট্রানজেকশন শুরু
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
SAVEPOINT after_debit;                -- একটা চেকপয়েন্ট রাখলাম
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;                               -- পাকা করলাম
-- অথবা
ROLLBACK TO after_debit;              -- চেকপয়েন্টে ফিরে গেলাম
ROLLBACK;                             -- পুরো বাতিল
```

### DQL — শুধু কোয়েরি (অনেকে DML-এর অংশ ধরে)
```sql
SELECT name, COUNT(*) AS total
FROM students
WHERE age > 18
GROUP BY name
HAVING COUNT(*) > 1
ORDER BY total DESC
LIMIT 10;
```

**⚠️ সবচেয়ে বিপজ্জনক ভুল:**
```sql
DELETE FROM students;      -- 😱 WHERE নেই — সব রো মুছে যাবে!
UPDATE students SET grade = 'A';   -- 😱 সবার গ্রেড A হয়ে যাবে!
```
**সবসময় আগে `SELECT` দিয়ে দেখে নিন কোন রো গুলো প্রভাবিত হবে**, তারপর `DELETE`/`UPDATE` লিখুন।

## ২২. SQL-এ Nested Query কী?

**সংজ্ঞা:** Nested query হলো এমন একটা কোয়েরি, যার ভেতরে আরেকটা কোয়েরি বসানো আছে। ভেতরের কোয়েরিটাকে বলে **subquery**।

**উদাহরণগুলো:**

**১) সবচেয়ে বেশি বেতন যার:**
```sql
SELECT * FROM Employees
WHERE Salary = (SELECT MAX(Salary) FROM Employees);
```
> ভেতরের কোয়েরি একটা মান ফেরত দেয় (যেমন ৯০০০০), তারপর বাইরেরটা সেই বেতনের কর্মীকে খোঁজে।

**২) নির্দিষ্ট শর্তে কর্মীর নাম:**
```sql
SELECT E.ename FROM employee E
WHERE E.eid IN (SELECT S.eid FROM salary S WHERE S.regno = 103);
```
> ভেতরের কোয়েরি একটা **তালিকা** ফেরত দেয়, তাই `IN` ব্যবহার হয়েছে।

**৩) নিজের বিভাগের গড়ের চেয়ে বেশি বেতন যাদের (Correlated Subquery):**
```sql
SELECT EmployeeID, Salary FROM Employees e1
WHERE Salary > (
    SELECT AVG(Salary) FROM Employees e2
    WHERE e1.DepartmentID = e2.DepartmentID
);
```

---

**দুই ধরনের Subquery — খুব গুরুত্বপূর্ণ পার্থক্য:**

| | Non-correlated | Correlated |
|---|---|---|
| বাইরের কোয়েরির উপর নির্ভরশীল? | ❌ না | ✅ হ্যাঁ |
| কতবার চলে | **একবারই** | **প্রতিটা রো-এর জন্য একবার** |
| গতি | দ্রুত ⚡ | ধীর 🐌 |
| উদাহরণ | উপরের ১ ও ২ | উপরের ৩ |

**Correlated Subquery কেন ধীর:**
```
১০,০০০ কর্মী থাকলে ভেতরের কোয়েরিটা ১০,০০০ বার চলবে! 😩
```

**বাস্তব উদাহরণ দিয়ে বুঝুন:**
- **Non-correlated** = "সবচেয়ে লম্বা মানুষের উচ্চতা কত?" → একবার হিসাব করলেই হলো
- **Correlated** = "প্রত্যেকের জন্য বলো, সে তার **নিজের ক্লাসের** গড়ের চেয়ে লম্বা কিনা" → প্রত্যেকের জন্য আলাদা করে ক্লাসের গড় বের করতে হবে

**Subquery কোথায় কোথায় বসতে পারে:**
```sql
-- SELECT-এ (scalar subquery)
SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.uid = u.id) AS order_count
FROM users u;

-- FROM-এ (derived table)
SELECT dept, avg_sal FROM (
    SELECT dept, AVG(salary) AS avg_sal FROM employees GROUP BY dept
) AS dept_avg
WHERE avg_sal > 50000;

-- WHERE-এ (সবচেয়ে সাধারণ)
SELECT * FROM products WHERE price > (SELECT AVG(price) FROM products);
```

**💡 পারফরম্যান্স টিপ — অনেক Correlated Subquery কে JOIN দিয়ে লেখা যায় (এবং সেটা দ্রুত হয়):**
```sql
-- ধীর
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- দ্রুত
SELECT DISTINCT u.name FROM users u
JOIN orders o ON o.user_id = u.id;
```

**`IN` বনাম `EXISTS`:**
- ভেতরের ফলাফল **ছোট** হলে → `IN` ভালো
- ভেতরের ফলাফল **বড়** হলে → `EXISTS` ভালো (প্রথম মিল পেলেই থেমে যায়)
- ⚠️ ভেতরের কোয়েরিতে `NULL` থাকলে `NOT IN` অদ্ভুত আচরণ করে — `NOT EXISTS` ব্যবহার করুন

## ২৩. JOIN কী?

**সংজ্ঞা:** SQL-এ JOIN ব্যবহার হয় দুই বা তার বেশি টেবিলের রো একত্র করতে — তাদের মধ্যে একটা সম্পর্কিত কলামের ভিত্তিতে।

**পুরো ব্যাপারটা ভেন ডায়াগ্রামে:**
```
INNER JOIN          LEFT JOIN           RIGHT JOIN          FULL JOIN
   ( ●●● )            (●●●●● )           ( ●●●●●)           (●●●●●●●)
   A   B              A     B            A     B            A      B
  মিলটুকু          A-এর সব + মিল       B-এর সব + মিল        দুটোরই সব
```

### INNER JOIN
শুধু সেসব রো ফেরত দেয় যেখানে **দুই টেবিলেই মিল আছে**।

**উদাহরণ:** যেসব কর্মী ও বিভাগের department ID মিলে যায়।
```sql
SELECT Employees.EmployeeID, Employees.Name, Departments.DepartmentName
FROM Employees
INNER JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;
```
> **বাস্তব অর্থ:** যাদের বিভাগ আছে **শুধু তারাই** আসবে। বিভাগহীন কর্মী বাদ যাবে।

### LEFT JOIN (LEFT OUTER JOIN)
**বাম টেবিলের সব রো** এবং ডান টেবিলের মিলে যাওয়া রো ফেরত দেয়। মিল না থাকলে ডান টেবিলের কলামে `NULL` আসে।

**উদাহরণ:** সব কর্মী ও তাদের বিভাগ — **যাদের কোনো বিভাগ নেই তারাও** থাকবে।
```sql
SELECT Employees.EmployeeID, Employees.Name, Departments.DepartmentName
FROM Employees
LEFT JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;
```

**💡 LEFT JOIN-এর সবচেয়ে কাজের ব্যবহার — "যাদের কিছু নেই" খুঁজে বের করা:**
```sql
SELECT e.Name
FROM Employees e
LEFT JOIN Departments d ON e.DepartmentID = d.DepartmentID
WHERE d.DepartmentID IS NULL;      -- 👈 যাদের কোনো বিভাগ নেই
```

> **বাস্তব ব্যবহার:** "কোন গ্রাহক এখনো একটাও অর্ডার করেনি?" — তাদের প্রমোশনাল অফার পাঠাতে হবে!

### RIGHT JOIN (RIGHT OUTER JOIN)
**ডান টেবিলের সব রো** এবং বাম টেবিলের মিলে যাওয়া রো ফেরত দেয়।

**উদাহরণ:** সব বিভাগ ও তাদের কর্মী — **যেসব বিভাগে কোনো কর্মী নেই সেগুলোও** থাকবে।
```sql
SELECT Employees.EmployeeID, Employees.Name, Departments.DepartmentName
FROM Employees
RIGHT JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;
```

> **⚠️ বাস্তবে RIGHT JOIN খুব কম ব্যবহার হয়** — টেবিল দুটোর ক্রম উল্টে দিয়ে LEFT JOIN লিখলেই একই ফল, আর পড়তেও সহজ।

### FULL JOIN (FULL OUTER JOIN)
যেকোনো এক টেবিলে মিল থাকলেই রো ফেরত দেয়। LEFT JOIN আর RIGHT JOIN-এর ফলাফল একসাথে।

```sql
SELECT Employees.EmployeeID, Employees.Name, Departments.DepartmentName
FROM Employees
FULL JOIN Departments ON Employees.DepartmentID = Departments.DepartmentID;
```
> **⚠️ MySQL-এ `FULL JOIN` নেই!** `LEFT JOIN UNION RIGHT JOIN` দিয়ে করতে হয়।

### CROSS JOIN
দুই টেবিলের **কার্টেসিয়ান গুণফল** — প্রথম টেবিলের প্রতিটা রো দ্বিতীয় টেবিলের প্রতিটা রো-এর সাথে জোড়া লাগে।

```sql
SELECT Employees.EmployeeID, Departments.DepartmentName
FROM Employees
CROSS JOIN Departments;
```

**⚠️ ভয়ংকর সতর্কতা:** ১,০০০ কর্মী × ৫০ বিভাগ = **৫০,০০০ রো!** ১০,০০০ × ১০,০০০ = ১০ কোটি রো — সার্ভার বসে যাবে। 💀

**কখন কাজে লাগে:** সব সম্ভাব্য সমন্বয় দরকার হলে — যেমন "প্রতিটা পণ্যের প্রতিটা সাইজ-রঙের সমন্বয় তৈরি করো"।

> **⚠️ দুর্ঘটনাবশত CROSS JOIN:** `ON` শর্ত লিখতে ভুলে গেলে অনেক ডেটাবেজ CROSS JOIN করে ফেলে! তাই সবসময় `ON` লিখতে ভুলবেন না।

### SELF JOIN
একটা টেবিলকে **নিজের সাথেই** JOIN করা। শ্রেণিবদ্ধ (hierarchical) ডেটা বা একই টেবিলের রো তুলনা করতে কাজে লাগে।

**উদাহরণ:** একই বিভাগে কাজ করে এমন কর্মী জোড়া খুঁজে বের করা।
```sql
SELECT e1.EmployeeID AS Employee1, e2.EmployeeID AS Employee2
FROM Employees e1
INNER JOIN Employees e2 ON e1.DepartmentID = e2.DepartmentID
WHERE e1.EmployeeID <> e2.EmployeeID;
```

**আরেকটা খুব সাধারণ উদাহরণ — কর্মী ও তার ম্যানেজার:**
```sql
SELECT e.Name AS Employee, m.Name AS Manager
FROM Employees e
LEFT JOIN Employees m ON e.ManagerID = m.EmployeeID;
```
> একই টেবিলে সবাই আছে, কিন্তু `ManagerID` দিয়ে নিজের ভেতরেই সম্পর্ক। LEFT JOIN ব্যবহার করলাম যাতে **CEO** (যার ম্যানেজার নেই) বাদ না পড়ে। ✅

---

**সারসংক্ষেপ টেবিল:**

| JOIN | কী ফেরত দেয় | কখন ব্যবহার |
|---|---|---|
| `INNER` | দুই দিকেই আছে এমন | সবচেয়ে সাধারণ, ৮০% ক্ষেত্রে |
| `LEFT` | বামের সব + মিল | "সবাইকে দেখাও, যাদের নেই তাদেরও" |
| `RIGHT` | ডানের সব + মিল | বিরল (LEFT দিয়ে লিখুন) |
| `FULL` | দুই দিকের সব | দুই তালিকা মেলানো |
| `CROSS` | সব সমন্বয় | সব জোড়া তৈরি করতে |
| `SELF` | নিজের সাথে নিজে | শ্রেণিবিন্যাস, তুলনা |

## ২৪. 2-Tier ও 3-Tier আর্কিটেকচারের পার্থক্য

### 2-Tier Architecture
অ্যাপ্লিকেশন দুইটা স্তরে ভাগ — **ক্লায়েন্ট ও সার্ভার**।

ক্লায়েন্ট সরাসরি সার্ভারের সাথে যোগাযোগ করে এবং presentation logic চালায় (যেমন GUI)। সার্ভার ডেটাবেজ ও বিজনেস লজিক সামলায়।

- ✅ **সুবিধা:** বাস্তবায়ন সহজ
- ❌ **অসুবিধা:** স্কেলেবিলিটি সীমিত, শক্তভাবে যুক্ত (tightly coupled), কম নিরাপদ — কারণ বিজনেস লজিক প্রায়ই ক্লায়েন্টের কাছে উন্মুক্ত হয়ে পড়ে

```
┌──────────────┐         ┌──────────────┐
│   ক্লায়েন্ট    │ ──────→ │   ডেটাবেজ     │
│ (UI + লজিক)  │         │   সার্ভার      │
└──────────────┘         └──────────────┘
```

**বাস্তব উদাহরণ:** পুরনো দিনের ডেস্কটপ অ্যাপ — যেমন একটা লাইব্রেরি সফটওয়্যার, যেটা সরাসরি MySQL-এ কানেক্ট করত।

**⚠️ কেন এটা বিপজ্জনক:** ডেটাবেজের ইউজারনেম-পাসওয়ার্ড **ক্লায়েন্ট অ্যাপের ভেতরে** থাকে! কেউ অ্যাপটা decompile করলে সেই ক্রেডেনশিয়াল পেয়ে যাবে, তারপর সরাসরি ডেটাবেজে ঢুকে যা খুশি করতে পারবে। 💀

---

### 3-Tier Architecture
অ্যাপ্লিকেশন তিনটা স্তরে ভাগ — **ক্লায়েন্ট (presentation layer)**, **মধ্যস্তর (business logic layer)** এবং **ডেটা স্তর**।

ক্লায়েন্ট ইউজার ইন্টারফেস সামলায়। মধ্যস্তরে থাকে প্রসেসিংয়ের নিয়ম। ডেটা স্তর ডেটাবেজ ও স্টোরেজ ম্যানেজ করে।

- ✅ **সুবিধা:** ভালো স্কেলেবিলিটি, নমনীয়তা ও রক্ষণাবেক্ষণযোগ্যতা। presentation, logic ও data আলাদা হওয়ায় নিরাপত্তা বাড়ে
- ❌ **অসুবিধা:** ডিজাইন ও ডেভেলপমেন্ট বেশি জটিল, ডিপ্লয়মেন্ট ও রক্ষণাবেক্ষণের খরচ বেশি

```
┌──────────┐      ┌──────────────┐      ┌──────────┐
│ ক্লায়েন্ট  │ ───→ │  API সার্ভার  │ ───→ │ ডেটাবেজ  │
│ (ব্রাউজার) │      │ (বিজনেস লজিক) │      │          │
└──────────┘      └──────────────┘      └──────────┘
   Tier 1              Tier 2              Tier 3
```

**বাস্তব উদাহরণ — একটা ই-কমার্স সাইট:**
```
Tier 1: React অ্যাপ (ব্রাউজারে) — শুধু দেখানো ও ইনপুট নেওয়া
Tier 2: Node.js API — "কুপনটা কি বৈধ? স্টকে আছে? দাম কত হবে?"
Tier 3: PostgreSQL — ডেটা সংরক্ষণ
```

**নিরাপত্তার দিকটা দেখুন:**
- ব্রাউজার **কখনোই** ডেটাবেজের পাসওয়ার্ড জানে না ✅
- ডেটাবেজ শুধু API সার্ভার থেকেই সংযোগ নেয় (ফায়ারওয়াল) ✅
- বিজনেস লজিক সার্ভারে, তাই কেউ ব্রাউজার থেকে দাম পাল্টাতে পারবে না ✅

**তুলনা:**

| | 2-Tier | 3-Tier |
|---|---|---|
| স্তর | ২টা | ৩টা |
| বিজনেস লজিক কোথায় | ক্লায়েন্টে বা DB-তে | **আলাদা সার্ভারে** |
| নিরাপত্তা | দুর্বল | শক্তিশালী |
| স্কেলিং | কঠিন | প্রতিটা স্তর আলাদা স্কেল করা যায় |
| জটিলতা | কম | বেশি |
| কখন ব্যবহার | ছোট ইন্ট্রানেট অ্যাপ | ওয়েব অ্যাপ, উৎপাদন |

**💡 আধুনিক প্রসঙ্গ:** মাইক্রোসার্ভিস আর্কিটেকচার হলো 3-tier-এরই একটা বিবর্তন — সেখানে Tier 2-টা আবার অনেকগুলো ছোট সার্ভিসে ভাগ হয়ে যায়।

## ২৫. SQL-এ TRUNCATE এবং DELETE-এর পার্থক্য কী?

### DELETE
- শর্তের ভিত্তিতে (`WHERE` clause) **নির্দিষ্ট রো** মোছে
- ট্রানজেকশন ব্যবহার করলে **rollback করা যায়**
- ধীর — কারণ একটা একটা করে রো মোছে এবং প্রতিটা মোছার লগ রাখে
```sql
DELETE FROM Employees WHERE Department = 'IT';
```

### TRUNCATE
- টেবিলের **সব রো** মুছে ফেলে, মূলত টেবিলটাকে রিসেট করে
- সাধারণত **rollback করা যায় না** (DBMS-ভেদে আলাদা)
- দ্রুত — কারণ আলাদা আলাদা মোছার লগ না রেখে **পুরো ডেটা পেজ মুক্ত করে দেয়**
```sql
TRUNCATE TABLE Employees;
```

**বাস্তব উদাহরণ — ঘর পরিষ্কার 🧹**

- **DELETE** = প্রতিটা জিনিস হাতে তুলে, "এটা ফেলব?" ভেবে, তালিকায় লিখে ফেলে দেওয়া। ধীর, কিন্তু চাইলে **আবার ফিরিয়ে আনা যায়** (ডাস্টবিন থেকে)।
- **TRUNCATE** = পুরো ঘরটা উল্টে দিয়ে সব একসাথে ফেলে দেওয়া। খুব দ্রুত, কিন্তু **ফেরানোর উপায় নেই**।

**সম্পূর্ণ তুলনা (DROP সহ):**

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| ভাষার ধরন | **DML** | **DDL** | **DDL** |
| `WHERE` দেওয়া যায়? | ✅ হ্যাঁ | ❌ না | ❌ না |
| Rollback? | ✅ হ্যাঁ | ❌ সাধারণত না | ❌ না |
| গতি | ধীর 🐌 | দ্রুত ⚡ | দ্রুত ⚡ |
| Trigger চলে? | ✅ হ্যাঁ | ❌ না | ❌ না |
| AUTO_INCREMENT রিসেট? | ❌ না | ✅ **হ্যাঁ** | — |
| টেবিলের কাঠামো থাকে? | ✅ | ✅ | ❌ **মুছে যায়** |
| জায়গা মুক্ত হয়? | তাৎক্ষণিক নয় | ✅ হ্যাঁ | ✅ হ্যাঁ |

**AUTO_INCREMENT রিসেটের ব্যাপারটা গুরুত্বপূর্ণ:**
```sql
-- ১০০টা রো আছে, শেষ id = ১০০
DELETE FROM users;        -- পরের INSERT-এ id হবে ১০১
TRUNCATE TABLE users;     -- পরের INSERT-এ id হবে ১ ✅
```

**⚠️ Foreign Key-এর সীমাবদ্ধতা:**
```sql
TRUNCATE TABLE departments;
-- ❌ Error: অন্য টেবিল এটাকে রেফার করছে
```
কোনো টেবিলকে foreign key দিয়ে রেফার করা হলে TRUNCATE করা যায় না, কিন্তু DELETE করা যায় (`ON DELETE CASCADE` থাকলে)।

**কখন কোনটা:**
- সব ডেটা মুছে টেবিল রিসেট করতে (যেমন টেস্ট ডেটা) → **TRUNCATE**
- শর্ত দিয়ে কিছু রো মুছতে → **DELETE**
- টেবিলটাই আর দরকার নেই → **DROP**

## ২৬. ডেটাবেজে Intension ও Extension-এর পার্থক্য

### Intension (Schema)
Intension ডেটাবেজ টেবিলের **স্কিমা বা কাঠামো** নির্ধারণ করে। এটা ডেটাবেজের **স্থির অংশ** — টেবিলের নাম, কলাম, ডেটা টাইপ, constraint ও সম্পর্ক নির্ধারণ করে।

**উদাহরণ:** `Employees` টেবিলের স্কিমা — কলাম: ID (integer), Name (varchar), Department (varchar)।

### Extension (Instance)
Extension বলতে বোঝায় কোনো নির্দিষ্ট মুহূর্তে ডেটাবেজে **আসলে যে ডেটা আছে** সেটা। এটা একটা টেবিলের সব রো-এর সংগ্রহ।

**পার্থক্যটা সহজভাবে:**

| | Intension | Extension |
|---|---|---|
| কী | কাঠামো / নকশা | আসল ডেটা |
| কখন বদলায় | **খুব কম** (ALTER TABLE করলে) | **প্রতি মুহূর্তে** (INSERT/UPDATE/DELETE) |
| অন্য নাম | Schema, Metadata | Instance, State, Snapshot |

**বাস্তব উদাহরণ — একটা ফর্ম 📋**

- **Intension** = **খালি আবেদন ফর্মটা**। এতে ঘর আছে: নাম, বয়স, ঠিকানা। এই ফর্মের নকশা বছরে একবারও বদলায় না।
- **Extension** = **পূরণ করা ফর্মগুলোর স্তূপ**। প্রতিদিন নতুন ফর্ম জমা পড়ছে, পুরনো কিছু বাতিল হচ্ছে।

**কোডে দেখুন:**
```sql
-- Intension (স্কিমা) — একবার লেখা হয়
CREATE TABLE Employees (
    ID         INT PRIMARY KEY,
    Name       VARCHAR(100) NOT NULL,
    Department VARCHAR(50)
);

-- Extension (ডেটা) — প্রতিদিন বদলায়
INSERT INTO Employees VALUES (1, 'করিম', 'IT');       -- সকাল ১০টা
INSERT INTO Employees VALUES (2, 'রহিম', 'HR');       -- দুপুর ১২টা
DELETE FROM Employees WHERE ID = 1;                    -- বিকাল ৩টা
```

সকাল ১০টার extension আর বিকাল ৩টার extension আলাদা, **কিন্তু intension একই**।

**প্রোগ্রামিংয়ের সাথে মিল:**
```
Intension = class ForConsumer { name: string; age: int; }
Extension = new Consumer("করিম", 25)  ← আসল object গুলো
```

## ২৭. Shared Lock ও Exclusive Lock-এর পার্থক্য; Lock-এর সংজ্ঞা

**Lock কী:** DBMS-এ Lock হলো এমন একটা ব্যবস্থা, যা ডেটায় প্রবেশ নিয়ন্ত্রণ করে — যাতে সমকালীন ট্রানজেকশনের সময় ডেটার অখণ্ডতা ও সামঞ্জস্য বজায় থাকে।

Lock **dirty read, lost update এবং inconsistent read**-এর মতো সমস্যা প্রতিরোধ করে।

**Dirty Read:** যখন একটা ট্রানজেকশন অন্য ট্রানজেকশনের **অসমাপ্ত (uncommitted)** ডেটা পড়ে ফেলে। অন্য ট্রানজেকশনটা পরে rollback করলে অসামঞ্জস্য তৈরি হয়।

> **উদাহরণ:** করিম ৫০০ টাকা জমা দিল (এখনো commit হয়নি)। রহিম ব্যালেন্স দেখল ৫০০ টাকা বেশি। তারপর করিমের ট্রানজেকশন ব্যর্থ হয়ে rollback হয়ে গেল। রহিম যা দেখেছিল সেটা **কখনো সত্যিই ছিলই না**! 😱

---

### Shared Lock (S-Lock)
একাধিক ট্রানজেকশনকে একই সাথে ডেটা **পড়তে দেয়**, কিন্তু কাউকে **বদলাতে দেয় না**।

### Exclusive Lock (X-Lock)
একটামাত্র ট্রানজেকশনকে ডেটা **পড়তে ও বদলাতে** দেয়। অন্য কোনো ট্রানজেকশন ঐ ডেটা **পড়তেও পারবে না, বদলাতেও পারবে না**।

**সামঞ্জস্যের টেবিল (Lock Compatibility Matrix):**

| | কেউ **S-Lock** চায় | কেউ **X-Lock** চায় |
|---|---|---|
| এখন **S-Lock** আছে | ✅ অনুমোদিত | ❌ অপেক্ষা করতে হবে |
| এখন **X-Lock** আছে | ❌ অপেক্ষা | ❌ অপেক্ষা |

**সহজ নিয়ম:** *"অনেকে পড়তে পারে, কিন্তু লিখবে একজনই — আর সে লেখার সময় কেউ পড়তেও পারবে না।"*

**বাস্তব উদাহরণ — গুগল ডকস 📄**

| | Shared Lock | Exclusive Lock |
|---|---|---|
| উপমা | **View Only** মোডে ১০ জন পড়ছে | একজন **Editing** করছে, বাকিরা লক আউট |
| একসাথে কতজন | যত খুশি 👥👥👥 | মাত্র একজন ✍️ |

**আরেকটা উপমা — নোটিশ বোর্ড:**
- ১০ জন একসাথে নোটিশ পড়তে পারে — কারও ক্ষতি হচ্ছে না ✅
- কিন্তু কেউ নোটিশ **বদলাতে** চাইলে সবাইকে সরে যেতে হবে — নাহলে কেউ অর্ধেক পুরনো অর্ধেক নতুন পড়ে ফেলবে ❌

**SQL-এ ব্যবহার:**
```sql
-- Shared Lock (পড়ার জন্য)
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;   -- MySQL
SELECT * FROM accounts WHERE id = 1 FOR SHARE;            -- PostgreSQL

-- Exclusive Lock (লেখার জন্য)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
```

**`FOR UPDATE` কেন দরকার — একটা বাস্তব দৃশ্য:**
```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- 👈 লক নিলাম
-- এখন অন্য কেউ এই রো পড়তে বা বদলাতে পারবে না
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
COMMIT;                                                  -- লক ছেড়ে দিলাম
```
`FOR UPDATE` না দিলে দুইজন একসাথে ব্যালেন্স পড়ে ফেলবে — **lost update** সমস্যা হবে (৬ নম্বর প্রশ্নের ATM উদাহরণটা মনে করুন)।

**Lock-এর পরিধি (Granularity):**

| স্তর | কী লক হয় | Concurrency | ওভারহেড |
|---|---|---|---|
| **Row-level** | একটা রো | বেশি ✅ | বেশি |
| **Page-level** | একটা ডিস্ক পেজ | মাঝারি | মাঝারি |
| **Table-level** | পুরো টেবিল | কম ❌ | কম |

আধুনিক ডেটাবেজ (InnoDB, PostgreSQL) সাধারণত **row-level lock** ব্যবহার করে — সবচেয়ে ভালো concurrency দেয়।

**⚠️ Lock-এর বিপদ — Deadlock:**
```
T1: A লক করল, এখন B চায়
T2: B লক করল, এখন A চায়
        → দুজনেই চিরকাল অপেক্ষা 💀
```
**প্রতিরোধের সহজ নিয়ম:** সব ট্রানজেকশনে **একই ক্রমে** লক নিন (যেমন সবসময় ছোট id আগে)।

## 📌 দ্রুত রিভিশন চিট-শিট

### ACID এক নজরে
```
A tomicity   → সব, নয়তো কিছুই না
C onsistency → নিয়ম কখনো ভাঙবে না
I solation   → একে অপরকে বিরক্ত করবে না
D urability  → একবার commit = চিরস্থায়ী
```

### Normalization মনে রাখার ছড়া
> *"The key, the whole key, and nothing but the key."*
> - **1NF** → এক ঘরে এক মান
> - **2NF** → পুরো key-এর উপর নির্ভরশীল (partial dependency নেই)
> - **3NF** → শুধু key-এর উপর নির্ভরশীল (transitive dependency নেই)

### Key গুলো
| Key | এক লাইনে |
|---|---|
| Primary | অনন্য + NULL নয়, টেবিলে একটাই |
| Foreign | অন্য টেবিলের PK-কে রেফার করে |
| Unique | অনন্য, NULL হতে পারে, একাধিক থাকতে পারে |
| Composite | ২+ কলাম মিলে PK |
| Candidate | যারা PK হতে পারত |
| Alternate | Candidate, কিন্তু PK হয়নি |

### JOIN দ্রুত মনে করা
```
INNER → শুধু মিল
LEFT  → বামের সব
RIGHT → ডানের সব
FULL  → দুটোরই সব
CROSS → সব × সব  ⚠️
SELF  → নিজের সাথে নিজে
```

### DELETE / TRUNCATE / DROP
```
DELETE   → রো মোছে, WHERE দেওয়া যায়, rollback হয়    (DML)
TRUNCATE → সব রো মোছে, দ্রুত, rollback হয় না         (DDL)
DROP     → টেবিলটাই মুছে ফেলে                        (DDL)
```

### সমস্যা ও সমাধান

| সমস্যা | সমাধান |
|---|---|
| কোয়েরি ধীর | **Index** যোগ করুন |
| একই ডেটা বারবার | **Normalization** |
| খুব বেশি JOIN, পড়া ধীর | **Denormalization** |
| ডেটা এক সার্ভারে ধরছে না | **Sharding** |
| সার্ভারে চাপ বেশি | **Vertical → Horizontal Scaling** |
| একসাথে লেখায় গোলমাল | **Lock / Transaction** |
| পড়ার চাপ বেশি | **Read Replica / Caching** |

### ইন্টারভিউয়ে সবচেয়ে বেশি আসা ৫টা প্রশ্ন
1. ACID বৈশিষ্ট্য ব্যাখ্যা করুন (উদাহরণ সহ!)
2. Normalization-এর ধাপগুলো — 1NF, 2NF, 3NF
3. INNER JOIN আর LEFT JOIN-এর পার্থক্য
4. Index কীভাবে কাজ করে, কেন B+ Tree
5. DELETE, TRUNCATE, DROP-এর পার্থক্য
