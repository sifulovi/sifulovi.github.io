> **সবচেয়ে আগে দুইটা শব্দের পার্থক্য বুঝে নিন — এটাই সব কিছুর ভিত্তি:**
>
> | | Authentication (AuthN) | Authorization (AuthZ) |
> |---|---|---|
> | প্রশ্ন | **"তুমি কে?"** | **"তুমি কী করতে পারবে?"** |
> | বাংলায় | পরিচয় যাচাই | অনুমতি যাচাই |
> | কখন হয় | আগে | পরে |
>
> **বাস্তব উদাহরণ — অফিসে ঢোকা:**
> - গেটে গার্ড আপনার **আইডি কার্ড** দেখল, ছবি মিলিয়ে দেখল আপনি সত্যিই করিম সাহেব → এটা **Authentication**।
> - ভেতরে ঢোকার পর দেখা গেল আপনার কার্ড দিয়ে ৩ তলা খোলে, কিন্তু সার্ভার রুম (৫ তলা) খোলে না → এটা **Authorization**।
>
> আপনি কে সেটা প্রমাণিত (AuthN), কিন্তু সব জায়গায় যাওয়ার অনুমতি নেই (AuthZ)।

## ১. OAuth 2.0 এবং OpenID Connect-এর মধ্যে পার্থক্য কী?

**OAuth 2.0:**
এটা একটা **Authorization** প্রোটোকল। এর কাজ হলো — কোনো অ্যাপকে ব্যবহারকারীর অ্যাকাউন্টে **সীমিত অ্যাক্সেস** দেওয়া। ওয়েব, ডেস্কটপ, মোবাইল — সব ধরনের অ্যাপের জন্য এর আলাদা আলাদা ফ্লো আছে।

**OpenID Connect (OIDC):**
এটা OAuth 2.0-এর **উপরে বসানো একটা পরিচয়ের স্তর (identity layer)**। OAuth-এর অনুমতির সাথে এটা **Authentication** যোগ করে। অর্থাৎ, অথরাইজেশন সার্ভার যে যাচাইটা করেছে, তার ভিত্তিতে ক্লায়েন্ট অ্যাপ ব্যবহারকারীর পরিচয় নিশ্চিত হতে পারে এবং তার নাম-ইমেইলের মতো প্রাথমিক তথ্য পেতে পারে।

**মূল পার্থক্য:** OAuth 2.0 শুধু **অনুমতি** নিয়ে কাজ করে (কে কোন রিসোর্সে ঢুকতে পারবে), আর OIDC এর সাথে **পরিচয় যাচাই** যোগ করে।

**বাস্তব উদাহরণ — হোটেলের চাবি:**

কল্পনা করুন আপনি হোটেলে উঠেছেন।

- **OAuth 2.0** = আপনাকে একটা **রুম কার্ড** দেওয়া হলো। এই কার্ড দিয়ে ৩০৫ নম্বর রুম খোলে, জিম খোলে, কিন্তু অন্য রুম খোলে না। কার্ডটা দেখে কেউ বুঝবে না আপনার নাম কী — শুধু জানবে "এই কার্ডধারী এই দরজাগুলো খুলতে পারবে"।
- **OIDC** = কার্ডের সাথে আপনার **ছবিসহ পরিচয়পত্র**ও দেওয়া হলো। এখন শুধু অনুমতিই নয়, "আপনি কে" সেটাও জানা যাচ্ছে।

**কোডে কীভাবে দেখা যায়:**
- OAuth 2.0 ফেরত দেয় → `access_token`
- OIDC ফেরত দেয় → `access_token` **+ `id_token`** (এই `id_token`-টাই একটা JWT যেখানে ব্যবহারকারীর নাম, ইমেইল ইত্যাদি থাকে)

> "Google দিয়ে লগইন করুন" বাটনে ক্লিক করলে আসলে **OIDC** ব্যবহার হয় — কারণ অ্যাপটা আপনার নাম-ইমেইল জানতে চায়।

## ২. OAuth 2.0-এর Authorization Code Flow কীভাবে কাজ করে?

**ধাপগুলো:**

1. ক্লায়েন্ট অ্যাপ ব্যবহারকারীকে **অথরাইজেশন সার্ভারে পাঠিয়ে দেয়** (redirect), সাথে অনুমতির অনুরোধ থাকে।
2. ব্যবহারকারী সেখানে **লগইন করে** এবং চাওয়া অনুমতিগুলোতে **সম্মতি দেয়**।
3. অথরাইজেশন সার্ভার ব্যবহারকারীকে ক্লায়েন্টের কাছে **ফেরত পাঠায়, সাথে একটা `authorization code`** দেয়।
4. ক্লায়েন্ট ঐ কোডটা নিয়ে **সার্ভার-টু-সার্ভার একটা নিরাপদ রিকোয়েস্ট** পাঠায় এবং বিনিময়ে **`access_token`** (এবং চাইলে `refresh_token`) নেয়।
5. এরপর ঐ `access_token` দিয়ে ব্যবহারকারীর হয়ে সুরক্ষিত রিসোর্সে অ্যাক্সেস করা হয়।

**বাস্তব উদাহরণ — একটা ফটো প্রিন্টিং অ্যাপ:**

ধরুন `PrintMyPhotos.com` আপনার Google Photos থেকে ছবি নিয়ে প্রিন্ট করতে চায়।

| ধাপ | বাস্তবে যা ঘটে |
|---|---|
| ১ | আপনি "Google Photos থেকে ছবি আনুন" বাটনে ক্লিক করলেন → Google-এর লগইন পেজে চলে গেলেন |
| ২ | Google-এ পাসওয়ার্ড দিলেন। Google জিজ্ঞেস করল: "PrintMyPhotos আপনার ছবি দেখতে চাইছে। অনুমতি দেবেন?" আপনি "Allow" চাপলেন |
| ৩ | Google আপনাকে PrintMyPhotos-এ ফেরত পাঠাল, URL-এ একটা কোড জুড়ে: `?code=abc123xyz` |
| ৪ | PrintMyPhotos-এর **সার্ভার** (ব্রাউজার নয়!) গোপনে Google-কে বলল: "এই কোড `abc123xyz`, আর এই আমার `client_secret`। আমাকে টোকেন দাও।" Google টোকেন দিল |
| ৫ | ঐ টোকেন দিয়ে PrintMyPhotos আপনার ছবিগুলো ডাউনলোড করল |

**সবচেয়ে গুরুত্বপূর্ণ প্রশ্ন — মাঝখানে `code` কেন? সরাসরি টোকেন দিলেই তো হতো!**

কারণ ধাপ ৩-এ কোডটা **ব্রাউজারের URL-এ** যায়। URL ব্রাউজার হিস্ট্রিতে থাকে, সার্ভার লগে থাকে, Referer হেডারে ফাঁস হতে পারে। কেউ যদি ঐ কোড চুরিও করে, সে **কিছুই করতে পারবে না** — কারণ টোকেন পেতে হলে `client_secret`-ও লাগবে, যেটা শুধু অ্যাপের সার্ভারে আছে।

> এটা অনেকটা — **কুরিয়ারের রসিদ নম্বর** পাঠানোর মতো। রসিদ নম্বর কেউ দেখে ফেললেও পার্সেল নিতে পারবে না, কারণ পার্সেল নিতে NID কার্ডও লাগবে।

**⚠️ আরেকটা গুরুত্বপূর্ণ পয়েন্ট:** `authorization code` মাত্র **একবার** ব্যবহার করা যায় এবং সাধারণত **৩০-৬০ সেকেন্ডে** মেয়াদ শেষ হয়ে যায়।

## ৩. JWT কী? আধুনিক ওয়েব অথেনটিকেশনে এটা এত ব্যবহৃত হয় কেন?

**সংজ্ঞা:** JWT (JSON Web Token) হলো একটা ছোট, URL-নিরাপদ টোকেন ফরম্যাট, যা দিয়ে দুই পক্ষের মধ্যে নিরাপদে তথ্য আদান-প্রদান করা যায়। এটা একটা গোপন কী বা পাবলিক/প্রাইভেট কী জোড়া দিয়ে **ডিজিটালি সাইন করা** থাকে।

**গঠন:** একটা JWT-তে তিনটা অংশ থাকে, ডট (`.`) দিয়ে আলাদা করা:

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMjMiLCJuYW1lIjoiS2FyaW0ifQ . SflKxwRJSMeKKF2QT4
└────── Header ──────┘ └──────────── Payload ──────────────┘ └───── Signature ────┘
```

| অংশ | কী থাকে | উদাহরণ |
|---|---|---|
| **Header** | কোন অ্যালগরিদমে সাইন করা | `{"alg": "HS256", "typ": "JWT"}` |
| **Payload** | আসল তথ্য (claims) | `{"sub": "123", "name": "করিম", "role": "admin", "exp": 1735689600}` |
| **Signature** | Header + Payload-এর উপর করা ডিজিটাল স্বাক্ষর | সার্ভারের গোপন কী দিয়ে তৈরি |

**কেন JWT ব্যবহার করবেন:**

- **Stateless Authentication:** JWT নিজেই সব তথ্য বহন করে। সার্ভারে আলাদা করে সেশন জমা রাখার দরকার নেই।

  > **কনসার্টের টিকিটের উদাহরণ:** আপনার কাছে একটা সিল-মারা টিকিট আছে। গেটে ঢোকার সময় গার্ডকে কোনো তালিকায় আপনার নাম খুঁজতে হয় না। সে শুধু **সিলটা আসল কিনা** দেখে — আসল হলে ঢুকতে দেয়। JWT-ও ঠিক এভাবে কাজ করে।

- **Scalable:** মাইক্রোসার্ভিস আর্কিটেকচারের জন্য আদর্শ। ১০টা সার্ভিস থাকলে প্রত্যেকে নিজে নিজেই টোকেন যাচাই করতে পারে — কোনো কেন্দ্রীয় ডেটাবেজে জিজ্ঞেস করতে যেতে হয় না।

- **Security:** Signature-এর কারণে টোকেন **পাল্টানো যায় না**। কেউ যদি Payload-এ `"role": "user"` বদলে `"role": "admin"` করে দেয়, Signature আর মিলবে না — সার্ভার সাথে সাথে টোকেনটা বাতিল করে দেবে। RSA-এর মতো অ্যালগরিদম ব্যবহার করলে আরও নিরাপদ যাচাই সম্ভব।

**⚠️ জুনিয়রদের সবচেয়ে বড় ভুল ধারণা:**
JWT **এনক্রিপ্টেড নয়**, শুধু **এনকোডেড** (Base64)। যে কেউ [jwt.io](https://jwt.io)-তে পেস্ট করে ভেতরের সব তথ্য পড়ে ফেলতে পারবে!

সাইন করা মানে — কেউ **বদলাতে** পারবে না, কিন্তু **পড়তে** পারবে।

👉 **তাই JWT-এর Payload-এ কখনোই পাসওয়ার্ড, ক্রেডিট কার্ড নম্বর বা কোনো গোপন তথ্য রাখবেন না।**

## ৪. OAuth 2.0-এর নিরাপত্তা ঝুঁকিগুলো কী কী এবং কীভাবে সেগুলো ঠেকানো যায়?

### ক) Authorization Code Interception (কোড চুরি)

**সমস্যা:** টোকেনে বদলানোর আগেই যদি কেউ `authorization code`-টা চুরি করে ফেলে, সে সেটা ব্যবহার করে ফেলতে পারে।

**বাস্তব দৃশ্য:** মোবাইল অ্যাপে redirect হয় একটা কাস্টম URL স্কিমে (যেমন `myapp://callback`)। একটা ক্ষতিকর অ্যাপ একই স্কিম রেজিস্টার করে রাখতে পারে এবং কোডটা আগেই ছোঁ মেরে নিয়ে যেতে পারে।

**সমাধান — PKCE** (উচ্চারণ "পিক্সি", Proof Key for Code Exchange):
বিশেষত মোবাইল অ্যাপের মতো **পাবলিক ক্লায়েন্ট**-এর জন্য অবশ্যই ব্যবহার করুন। PKCE একটা `code_challenge` ও `code_verifier` জোড়া দিয়ে বাড়তি সুরক্ষা যোগ করে।

**PKCE কীভাবে কাজ করে (সহজভাবে):**
1. অ্যাপ একটা এলোমেলো গোপন স্ট্রিং বানায় → `code_verifier`
2. তার হ্যাশ পাঠায় অথরাইজেশন সার্ভারে → `code_challenge`
3. পরে কোড বিনিময়ের সময় **আসল `code_verifier`** পাঠাতে হয়
4. চোর কোড পেলেও `code_verifier` জানে না → টোকেন পাবে না ✅

> এটা অনেকটা — কুরিয়ার পাঠানোর সময় বলে রাখলেন "আমার পাসওয়ার্ড হবে *আম-কাঁঠাল*"। কেউ রসিদ চুরি করলেও পাসওয়ার্ড জানবে না।

### খ) Token Leakage (টোকেন ফাঁস)

**সমস্যা:** ঠিকভাবে সামলানো না হলে access token URL-এর মাধ্যমে ফাঁস হয়ে যেতে পারে।

**সমাধান:** **Implicit Flow** ব্যবহার করবেন না (এটা এখন অচল/deprecated) — এতে টোকেন সরাসরি URL-এ আসে। বরং **Authorization Code Flow** ব্যবহার করুন, যেখানে টোকেন বিনিময় হয় সার্ভারে, URL-এ কখনো আসে না।

### গ) Redirect URI Manipulation (রিডাইরেক্ট URI কারচুপি)

**সমস্যা:** আক্রমণকারী redirect URI বদলে দিয়ে কোডটা নিজের সার্ভারে পাঠিয়ে নিতে পারে।

**বাস্তব দৃশ্য:** আসল লিংক `?redirect_uri=https://myapp.com/callback`, কিন্তু আক্রমণকারী পাঠাল `?redirect_uri=https://hacker.com/steal`। সার্ভার যদি চেক না করে, তাহলে কোডটা হ্যাকারের কাছে চলে যাবে।

**সমাধান:** অথরাইজেশন সার্ভারে **আগে থেকেই অনুমোদিত (whitelisted) redirect URI**-এর তালিকা রাখুন এবং **হুবহু মিলিয়ে (exact match)** যাচাই করুন।

> **⚠️ সতর্কতা:** `startsWith()` দিয়ে চেক করবেন না! `https://myapp.com.hacker.com` কিন্তু `https://myapp.com` দিয়েই শুরু হয়। সবসময় সম্পূর্ণ মিল দেখুন।

## ৫. Refresh Token কী এবং এটা নিরাপত্তা কীভাবে বাড়ায়?

**সংজ্ঞা:** Refresh Token হলো এমন একটা ক্রেডেনশিয়াল, যা দিয়ে ব্যবহারকারীকে আবার লগইন করতে না বলেই নতুন access token পাওয়া যায়। সাধারণত অথরাইজেশনের সময় access token-এর সাথেই এটা দেওয়া হয়।

**কেন ব্যবহার করবেন:**
- **নিরাপত্তা বাড়ে:** Access token-এর মেয়াদ খুব কম রাখা যায় (যেমন ১৫ মিনিট)। ফলে টোকেন চুরি হলেও চোর মাত্র অল্প সময় ব্যবহার করতে পারবে।
- **ব্যবহারকারীর সুবিধা:** Access token-এর মেয়াদ শেষ হলে ব্যবহারকারীকে আবার লগইন করতে হয় না — অ্যাপ নিজেই refresh token দিয়ে নতুন টোকেন নিয়ে নেয়।

**নিরাপত্তা বিবেচনা:** Refresh token খুব যত্ন করে রাখতে হবে, কারণ এটা দিয়ে বারবার নতুন access token বানানো যায়।

**বাস্তব উদাহরণ — জিমের সদস্যপদ:**

| | Access Token | Refresh Token |
|---|---|---|
| উপমা | **দিনের এন্ট্রি পাস** | **বাৎসরিক সদস্য কার্ড** |
| মেয়াদ | ১৫ মিনিট – ১ ঘণ্টা | ৭ দিন – ৩০ দিন |
| কোথায় পাঠানো হয় | প্রতিটা API কলে | শুধু টোকেন রিফ্রেশের সময় |
| ঝুঁকি | চুরি হলে অল্প সময়ের ক্ষতি | চুরি হলে বড় ক্ষতি |

দিনের পাস কেউ চুরি করলে আজকের দিনটাই শুধু ব্যবহার করতে পারবে। কিন্তু বাৎসরিক কার্ড চুরি হলে সারা বছর ঢুকতে পারবে — তাই সেটা যত্নে রাখতে হয়।

**যেভাবে সংরক্ষণ করবেন:**

| জায়গা | নিরাপদ? | কারণ |
|---|---|---|
| `localStorage` | ❌ | JavaScript পড়তে পারে → XSS আক্রমণে চুরি হবে |
| `HttpOnly` + `Secure` Cookie | ✅ | JavaScript পড়তেই পারে না |
| মোবাইলের Keychain / Keystore | ✅ | অপারেটিং সিস্টেম সুরক্ষিত রাখে |

**আরেকটা ভালো চর্চা — Refresh Token Rotation:** প্রতিবার refresh করার সময় পুরনোটা বাতিল করে **নতুন refresh token** দিন। এতে পুরনো টোকেন কেউ ব্যবহার করার চেষ্টা করলে সাথে সাথে বোঝা যাবে যে চুরি হয়েছে, আর পুরো সেশন বাতিল করে দেওয়া যাবে।

## ৬. RBAC এবং ABAC-এর মধ্যে পার্থক্য কী?

**RBAC (Role-Based Access Control) — ভূমিকা ভিত্তিক:**
অনুমতি দেওয়া হয় **ভূমিকা (role)** অনুযায়ী, আর ব্যবহারকারীদের ভূমিকায় বসানো হয়। কোন ভূমিকা কোন রিসোর্সে কী করতে পারবে, সেটা আগে থেকে ঠিক করা থাকে।

**উদাহরণ:** `admin` ভূমিকার সবাই সব কিছু করতে পারবে, আর `viewer` ভূমিকার সবাই শুধু পড়তে পারবে।

**ABAC (Attribute-Based Access Control) — বৈশিষ্ট্য ভিত্তিক:**
অনুমতি ঠিক হয় ব্যবহারকারী, রিসোর্স এবং পরিবেশের **বৈশিষ্ট্য (attribute)** দেখে। নীতিমালা (policy) ঠিক করে দেয় কোন বৈশিষ্ট্য কীভাবে অ্যাক্সেসকে প্রভাবিত করবে — যেমন ব্যবহারকারীর ডিপার্টমেন্ট, সময়, বা ডেটার সংবেদনশীলতা।

**উদাহরণ:** একটা নীতি বলতে পারে — "ফিন্যান্স ডিপার্টমেন্টের কর্মীরা `financial_reports` দেখতে পারবে, তবে শুধু সকাল ৯টা থেকে বিকাল ৫টার মধ্যে।"

**পাশাপাশি তুলনা:**

| | RBAC | ABAC |
|---|---|---|
| ভিত্তি | তুমি **কে** (ভূমিকা) | **পরিস্থিতি** কী (বৈশিষ্ট্য) |
| নিয়মের ধরন | `admin → সব করতে পারবে` | `if (dept == "finance" && time in 9-17) → পারবে` |
| সরলতা | সহজ, বোঝা ও সেটআপ সহজ | জটিল, কিন্তু অনেক নমনীয় |
| সমস্যা | ব্যতিক্রম বাড়লে ভূমিকার সংখ্যা বিস্ফোরিত হয় | নীতি ডিবাগ করা কঠিন |

**বাস্তব উদাহরণ — হাসপাতাল:**

**RBAC দিয়ে:**
- `ডাক্তার` → রোগীর রিপোর্ট দেখতে ও লিখতে পারবে
- `নার্স` → রিপোর্ট দেখতে পারবে, লিখতে পারবে না
- `রিসেপশনিস্ট` → শুধু নাম-ঠিকানা দেখতে পারবে

**সমস্যা কোথায়:** একজন ডাক্তার কি **যেকোনো** রোগীর রিপোর্ট দেখতে পারবেন? এমনকি অন্য ওয়ার্ডের? RBAC এটা আলাদা করতে পারে না। আলাদা করতে হলে `কার্ডিওলজি-ডাক্তার`, `নিউরো-ডাক্তার`... এভাবে ভূমিকার সংখ্যা বাড়তেই থাকবে।

**ABAC দিয়ে সমাধান:**
```
অনুমতি দাও, যদি:
    user.role == "ডাক্তার"
    AND user.department == patient.admitted_department
    AND patient.status == "ভর্তি আছে"
```

একটা নীতিতেই সব ঢাকা পড়ে গেল। ✅

> **কখন কোনটা:** ছোট-মাঝারি অ্যাপে **RBAC** দিয়ে শুরু করুন — সহজ ও যথেষ্ট। যখন "কিন্তু শুধু যদি..." টাইপের শর্ত বাড়তে থাকবে, তখন **ABAC**-এ যান।

## ৭. ডেটাবেজে পাসওয়ার্ড নিরাপদে রাখার সেরা চর্চাগুলো কী?

### ক) Hashing (হ্যাশিং)

পাসওয়ার্ড **কখনোই** সাদা টেক্সটে (plain text) রাখা যাবে না। **bcrypt, scrypt বা Argon2**-এর মতো ক্রিপ্টোগ্রাফিক হ্যাশ ফাংশন ব্যবহার করুন।

**হ্যাশিং কী:** এটা একমুখী রাস্তা — পাসওয়ার্ড থেকে হ্যাশ বানানো যায়, কিন্তু হ্যাশ থেকে পাসওয়ার্ড ফিরে পাওয়া যায় না।

```
"amarPassword123"  →  হ্যাশ  →  "$2b$12$KIXxPfnK6..."
"$2b$12$KIXxPfnK6..."  →  ফেরত?  →  ❌ অসম্ভব
```

> **কিমা বানানোর উপমা:** মাংস থেকে কিমা বানানো যায়, কিন্তু কিমা থেকে আর আস্ত মাংস ফেরত পাওয়া যায় না।

**তাহলে লগইন যাচাই হয় কীভাবে?** ব্যবহারকারী পাসওয়ার্ড দিলে সেটা আবার হ্যাশ করা হয়, তারপর ডেটাবেজে রাখা হ্যাশের সাথে মেলানো হয়। মিললে ✅।

**⚠️ MD5 বা SHA-256 দিয়ে পাসওয়ার্ড হ্যাশ করবেন না!** এগুলো **খুব দ্রুত** — একটা আধুনিক GPU সেকেন্ডে কোটি কোটি SHA-256 হ্যাশ চেষ্টা করতে পারে। bcrypt/Argon2 ইচ্ছাকৃতভাবে **ধীর** বানানো হয়েছে, যাতে ব্রুট-ফোর্স আক্রমণ অসম্ভব হয়ে যায়।

### খ) Salting (সল্ট যোগ করা)

প্রতিটা পাসওয়ার্ডের সাথে একটা **আলাদা এলোমেলো টেক্সট (salt)** জুড়ে দিয়ে তারপর হ্যাশ করুন। এতে আক্রমণকারী আগে থেকে বানিয়ে রাখা হ্যাশ টেবিল (**rainbow table**) ব্যবহার করতে পারবে না।

**সল্ট ছাড়া যে বিপদ:**

| ব্যবহারকারী | পাসওয়ার্ড | হ্যাশ (সল্ট ছাড়া) |
|---|---|---|
| করিম | `123456` | `e10adc3949ba59ab...` |
| রহিম | `123456` | `e10adc3949ba59ab...` ← **একদম একই!** |

হ্যাকার ডেটাবেজ চুরি করে দেখল দুইজনের হ্যাশ এক — সে বুঝে গেল দুজনের পাসওয়ার্ডও এক। আর একটা ভাঙলেই দুইটাই ভাঙল।

**সল্ট দিয়ে:**

| ব্যবহারকারী | পাসওয়ার্ড | Salt | হ্যাশ |
|---|---|---|---|
| করিম | `123456` | `xY7q` | `a91bf2c8...` |
| রহিম | `123456` | `pL3m` | `77de4b1a...` ← **আলাদা!** ✅ |

> **সল্ট গোপন রাখার দরকার নেই** — এটা হ্যাশের পাশেই ডেটাবেজে রাখা যায়। এর কাজ গোপনীয়তা নয়, বরং প্রতিটা হ্যাশকে **অনন্য** করা। (bcrypt নিজেই সল্ট বানিয়ে হ্যাশের ভেতরে ঢুকিয়ে দেয়।)

### গ) Peppering (পেপার যোগ করা)

হ্যাশ করার আগে একটা **গোপন মান (pepper)** যোগ করুন — এটা বাড়তি একটা সুরক্ষার স্তর।

**Salt আর Pepper-এর পার্থক্য:**

| | Salt | Pepper |
|---|---|---|
| প্রতি ব্যবহারকারীর জন্য | আলাদা | পুরো অ্যাপে একটাই |
| কোথায় থাকে | ডেটাবেজে, হ্যাশের পাশে | ডেটাবেজের **বাইরে** (env variable / vault-এ) |
| উদ্দেশ্য | rainbow table ঠেকানো | ডেটাবেজ চুরি হলেও সুরক্ষা |

**কেন pepper কাজে দেয়:** হ্যাকার যদি পুরো ডেটাবেজ চুরিও করে ফেলে, pepper-টা তো ডেটাবেজে নেই! সেটা ছাড়া কোনো পাসওয়ার্ড ভাঙা যাবে না।

## ৮. Stateless এবং Stateful অথেনটিকেশনের পার্থক্য কী?

**Stateless Authentication:**
সার্ভার ব্যবহারকারীর কোনো সেশন তথ্য জমা রাখে না। বরং ক্লায়েন্ট প্রতিটা রিকোয়েস্টের সাথে দরকারি সব তথ্য পাঠায় (যেমন JWT-এর ভেতরে)। সার্ভার শুধু টোকেনের Signature যাচাই করে ব্যবহারকারীকে চিনে নেয়।
- ✅ **সুবিধা:** স্কেল করা সহজ, কারণ সার্ভারে কোনো সেশন স্টোরেজ লাগে না।
- ❌ **অসুবিধা:** টোকেন বাতিল করা কঠিন — মেয়াদ শেষ না হওয়া পর্যন্ত সেটা বৈধ থেকে যায়।

**Stateful Authentication:**
সার্ভার ব্যবহারকারীর সেশন ডেটা নিজের কাছে রাখে — সাধারণত একটা সেশন স্টোর বা ডেটাবেজে। ক্লায়েন্টের কাছে থাকে শুধু একটা `session ID`, যেটা দিয়ে সার্ভার সেশন ডেটা খুঁজে বের করে।
- ✅ **সুবিধা:** সেশন বাতিল করা বা অকার্যকর করা সহজ।
- ❌ **অসুবিধা:** সেশন স্টোরেজ লাগে বলে স্কেল করা তুলনামূলক কঠিন।

**বাস্তব উদাহরণ — সিনেমা হল:**

**Stateful = অতিথি তালিকা 📋**
গেটে একটা খাতা আছে। আপনি নাম বললে গার্ড খাতায় খুঁজে দেখে। আপনাকে বাদ দিতে চাইলে? খাতা থেকে নাম কেটে দিলেই হলো — সাথে সাথে কার্যকর। কিন্তু ১০টা গেট থাকলে ১০টা খাতা সিঙ্ক রাখতে হবে (ঝামেলা!)।

**Stateless = সিল-মারা টিকিট 🎟️**
কোনো খাতা নেই। গার্ড শুধু টিকিটের সিল দেখে আসল কিনা যাচাই করে। ১০০টা গেট থাকলেও সমস্যা নেই (দারুণ স্কেলিং!)। কিন্তু একটা টিকিট বাতিল করতে চাইলে? **পারবেন না** — সব গেটে খবর পাঠাতে হবে, যা আবার stateless থাকল না।

**সিদ্ধান্তের টেবিল:**

| দরকার | বেছে নিন |
|---|---|
| অনেক মাইক্রোসার্ভিস, বেশি ট্রাফিক | Stateless (JWT) |
| সাথে সাথে লগআউট/ব্যান করা জরুরি (যেমন ব্যাংকিং) | Stateful |
| দুটোই চাই | **Hybrid** — ছোট মেয়াদের JWT + সার্ভারে refresh token, অথবা Redis-এ একটা blacklist |

**বাস্তবে যেটা সবচেয়ে বেশি হয় (Hybrid):**
Access token-এর মেয়াদ রাখুন খুব কম (৫-১৫ মিনিট)। লগআউট করলে refresh token-টা সার্ভারে মুছে দিন। তাহলে সবচেয়ে খারাপ ক্ষেত্রেও চুরি হওয়া টোকেন মাত্র ১৫ মিনিট কাজ করবে।

## ৯. OAuth 2.0 Scope কী এবং কীভাবে ব্যবহার হয়?

**সংজ্ঞা:** Scope দিয়ে বোঝানো হয় ক্লায়েন্ট রিসোর্স সার্ভারের কাছে **কোন কোন অনুমতি** চাইছে। এটা access token-এর ক্ষমতা সীমিত করে দেয়।

**উদাহরণ:** একটা ক্লায়েন্ট `read:user` scope চাইতে পারে ব্যবহারকারীর তথ্য পড়ার জন্য, বা `write:posts` চাইতে পারে নতুন পোস্ট বানানোর জন্য।

**Scope-এর ভূমিকা:** Scope নিশ্চিত করে যে ক্লায়েন্ট **শুধু ততটুকু অ্যাক্সেসই পায়, যতটুকু তার সত্যিই দরকার**। এটাকেই বলে **Principle of Least Privilege** (ন্যূনতম অধিকারের নীতি)।

**ব্যবহারের উদাহরণ:** অথরাইজেশনের সময় ব্যবহারকারীকে দেখানো হয় ক্লায়েন্ট কোন কোন scope চাইছে, আর সে চাইলে নির্দিষ্ট কিছু অনুমতি দিতে বা বাতিল করতে পারে।

**বাস্তব উদাহরণ:**
আপনি নিশ্চয়ই দেখেছেন — কোনো অ্যাপ Google দিয়ে লগইন করার সময় একটা পর্দা আসে:

> **"Photo Editor App এই অনুমতিগুলো চাইছে:"**
> - ☑️ আপনার নাম ও প্রোফাইল ছবি দেখা → `profile`
> - ☑️ আপনার ইমেইল ঠিকানা দেখা → `email`
> - ☑️ আপনার Google Drive-এর ছবি দেখা → `drive.photos.readonly`

ঠিক এগুলোই হলো **scope**।

**এখানে গুরুত্বপূর্ণ কী:** অ্যাপটা চেয়েছে `drive.photos.**readonly**` — শুধু পড়ার অনুমতি। মানে সে আপনার ছবি **দেখতে** পারবে, কিন্তু **মুছতে পারবে না**। যদি অ্যাপটা হ্যাকও হয়ে যায়, হ্যাকার আপনার ছবি ডিলিট করতে পারবে না। ✅

> **উল্টো দিকটা ভাবুন:** একটা ক্যালকুলেটর অ্যাপ যদি `drive.full_access` চায়, তাহলে বুঝবেন কিছু একটা গড়বড় আছে। প্রয়োজনের চেয়ে বেশি অনুমতি চাওয়া একটা লাল পতাকা।

## ১০. মাইক্রোসার্ভিসের মধ্যে নিরাপদ API অথেনটিকেশন ও অথরাইজেশন কীভাবে নিশ্চিত করবেন?

### ক) Mutual TLS (mTLS)

সাধারণ TLS-এ শুধু **ক্লায়েন্ট সার্ভারকে যাচাই করে**। mTLS-এ **দুই পক্ষই একে অপরকে যাচাই করে** — সার্ভারও নিশ্চিত হয় যে ক্লায়েন্ট আসলে বৈধ।

> **উপমা:** সাধারণ TLS = আপনি দোকানের সাইনবোর্ড দেখে নিশ্চিত হলেন এটা আসল দোকান। mTLS = দোকানদারও আপনার আইডি কার্ড দেখে নিশ্চিত হলো আপনি বৈধ ক্রেতা।

### খ) JWT

কলিং সার্ভিসের পরিচয় বোঝাতে **সাইন করা JWT** ব্যবহার করুন, সাথে দরকারি scope বা claim দিন। যেমন `order-service` যখন `payment-service`-কে ডাকে, সে একটা JWT পাঠাবে যাতে লেখা থাকে সে কে এবং কী করার অনুমতি আছে।

### গ) API Gateway

একটা **API Gateway** বসান, যেটা রিকোয়েস্ট ব্যাকএন্ড সার্ভিসে পৌঁছানোর **আগেই** অথেনটিকেশন ও অথরাইজেশন চেক করে ফেলবে।

> **উপমা:** অফিসের **মূল ফটক**। সব বাইরের মানুষ এই এক গেট দিয়েই ঢোকে, এখানেই আইডি চেক হয়। ভেতরের প্রতিটা রুমে আলাদা গার্ড বসাতে হয় না।

**সুবিধা:** প্রতিটা মাইক্রোসার্ভিসে আলাদা করে লগইন যাচাইয়ের কোড লিখতে হয় না — এক জায়গায় লিখলেই হয়।

### ঘ) Service Mesh

**Istio**-এর মতো একটা Service Mesh ব্যবহার করুন। এটা নিজে থেকেই mTLS সামলায়, অথরাইজেশন নীতি প্রয়োগ করে এবং মাইক্রোসার্ভিসগুলোর মধ্যে নিরাপদ যোগাযোগ ম্যানেজ করে।

**সেরা সুবিধাটা কী:** আপনার অ্যাপ্লিকেশন কোডে **একটা লাইনও** নিরাপত্তার কোড লিখতে হয় না! Service Mesh প্রতিটা সার্ভিসের পাশে একটা প্রক্সি (sidecar) বসিয়ে দেয়, যেটা যাওয়া-আসা সব ট্র্যাফিক সামলায়।

**পুরো ছবিটা একসাথে:**

```
বাইরের ব্যবহারকারী
        ↓  (OAuth/OIDC দিয়ে লগইন)
   API Gateway  ← এখানে ব্যবহারকারীর টোকেন যাচাই হয়
        ↓  (ভেতরের JWT)
  order-service  ←→  payment-service   ← এদের মধ্যে mTLS
        ↕                  ↕              (Service Mesh সামলায়)
   inventory-service   email-service
```

## ১১. Keycloak কি Stateful না Stateless অথেনটিকেশন দেয়?

Keycloak **পুরোপুরি stateless নয়** — কারণ এটা ব্যবহারকারীর সেশন জমা রাখে এবং কে কখন লগইন-লগআউট করল তার হিসাব রাখে। এর ফলেই **SSO (Single Sign-On)** এবং **কেন্দ্রীয় লগআউট**-এর মতো ফিচার সম্ভব হয় — একটা সার্ভিস থেকে লগআউট করলে সব সার্ভিস থেকেই সেশন শেষ হয়ে যায়।

তবে এটা একটা **হাইব্রিড পদ্ধতি** নেয়। Keycloak JWT (access token) ইস্যু করে, যার ভেতরে ব্যবহারকারীর তথ্য থাকে। সার্ভিসগুলো প্রতিটা রিকোয়েস্টে Keycloak-কে জিজ্ঞেস না করেই সেটা যাচাই করতে পারে। ফলে stateless-এর সুবিধাও পাওয়া যায়, আবার সার্ভারে সেশন নিয়ন্ত্রণও থাকে।

**দুই দিকটা সহজভাবে:**

| দিক | কেমন আচরণ | কেন |
|---|---|---|
| Keycloak-এর নিজের ভেতরে | **Stateful** | ব্যবহারকারীর সেশন ডেটাবেজে রাখে |
| যেসব অ্যাপ টোকেন যাচাই করে | **Stateless** | JWT-এর Signature দেখেই যথেষ্ট |

**এই ডিজাইনটা কেন সেরা:**
- আপনার ১০টা মাইক্রোসার্ভিস প্রতি সেকেন্ডে হাজারো রিকোয়েস্ট পাচ্ছে → সবাই স্থানীয়ভাবে JWT যাচাই করছে → **Keycloak-এর উপর কোনো চাপ নেই** ⚡
- একই সাথে Keycloak-এ সেশন থাকায় → দরকার হলে **সাথে সাথে সব জায়গা থেকে লগআউট** করানো যায় 🔒

## ১২. লগআউট করলে সার্ভিসগুলো যেন টোকেনটা আর গ্রহণ না করে — কীভাবে নিশ্চিত করব?

**সমাধান — Token Introspection:**
টোকেনটা এখনো বৈধ কিনা যাচাই করতে introspection ব্যবহার করুন। মানে হলো, সার্ভিসগুলো টোকেন গ্রহণ করার আগে Keycloak-এর **introspection endpoint**-এ গিয়ে টোকেনের অবস্থা জেনে নেবে। লগআউটের কারণে টোকেনটা বাতিল হয়ে থাকলে Keycloak উত্তরে জানাবে যে টোকেনটা আর সক্রিয় নেই।

**কেন সমস্যাটা হয়:** JWT নিজে থেকে "আমি বাতিল হয়ে গেছি" জানার কোনো উপায় রাখে না। সিল-মারা টিকিটের মতো — সিলটা তো আসলই, তাই গার্ড ঢুকতে দেবে, যদিও আপনি টিকিটটা ফেরত দিয়ে দিয়েছেন।

**Introspection যেভাবে কাজ করে:**
```
POST /realms/myrealm/protocol/openid-connect/token/introspect
    token=<access_token>

উত্তর → { "active": false }   ← লগআউট হয়ে গেছে, প্রত্যাখ্যান করুন ❌
উত্তর → { "active": true, "sub": "...", "scope": "..." }   ← বৈধ ✅
```

**⚠️ কিন্তু একটা মূল্য দিতে হয়:** প্রতিটা রিকোয়েস্টে যদি Keycloak-কে জিজ্ঞেস করতে হয়, তাহলে stateless-এর সব সুবিধা চলে গেল — গতি কমে যাবে, আর Keycloak একটা bottleneck হয়ে দাঁড়াবে।

**বাস্তবে যেসব সমাধান ব্যবহার হয়:**

| উপায় | কীভাবে | কখন ব্যবহার করবেন |
|---|---|---|
| **ছোট মেয়াদের টোকেন** | Access token-এর মেয়াদ ১-৫ মিনিট রাখুন | সবচেয়ে সহজ। লগআউটের পর সর্বোচ্চ ৫ মিনিট ঝুঁকি |
| **Introspection** | প্রতিবার Keycloak-এ জিজ্ঞেস করুন | খুব সংবেদনশীল কাজে (যেমন টাকা ট্রান্সফার) |
| **Redis Blacklist** | লগআউটের সময় টোকেনের `jti` Redis-এ রাখুন, প্রতিবার চেক করুন | মাঝামাঝি সমাধান — Redis খুব দ্রুত |
| **Back-Channel Logout** | Keycloak সব সার্ভিসকে "এই সেশন শেষ" বলে জানিয়ে দেয় | সবচেয়ে ভালো, কিন্তু সেটআপ জটিল |

**বাস্তব পরামর্শ:** বেশিরভাগ অ্যাপের জন্য **ছোট মেয়াদের টোকেন + লগআউটে refresh token বাতিল** — এই সমন্বয়টাই যথেষ্ট। ৫ মিনিটের ঝুঁকি বনাম প্রতিটা রিকোয়েস্টে নেটওয়ার্ক কল — বেশিরভাগ ক্ষেত্রে প্রথমটাই ভালো সিদ্ধান্ত।

## ১৩. Single Sign-On (SSO) ব্যাখ্যা করুন

**সংজ্ঞা:** SSO মানে হলো — ব্যবহারকারী **একবার** কোনো আইডেন্টিটি প্রোভাইডারে (যেমন Keycloak) লগইন করবে, আর সেই লগইনটাই **একাধিক সার্ভিস বা অ্যাপ্লিকেশনে** গ্রহণযোগ্য হবে। প্রতিটা অ্যাপে আলাদা করে লগইন করতে হবে না।

**কীভাবে কাজ করে:** SSO-তে আইডেন্টিটি প্রোভাইডারের সাথে একটা **সেশন** তৈরি হয়, আর সার্ভিসগুলোকে **JWT টোকেন** দেওয়া হয়। সেশনটা ব্যবহারকারীর লগইন অবস্থার হিসাব রাখে, আর টোকেনগুলো সার্ভিসগুলোকে যাচাই করার সুযোগ দেয় যে ব্যবহারকারী সত্যিই লগইন করা আছে।

**বাস্তব উদাহরণ — Google-এর সেবাগুলো:**

সকালে আপনি Gmail-এ লগইন করলেন। এরপর:
- YouTube খুললেন → **লগইন করতে হলো না** ✅
- Google Drive খুললেন → **লগইন করতে হলো না** ✅
- Google Maps খুললেন → **লগইন করতে হলো না** ✅

আপনি একবারই পাসওয়ার্ড দিয়েছেন, কিন্তু সব সেবাই আপনাকে চিনে ফেলেছে। এটাই SSO।

**ভেতরে যা ঘটে:**

```
১. আপনি app-A.com খুললেন
        ↓
২. app-A বলল "লগইন করা নেই" → Keycloak-এ পাঠিয়ে দিল
        ↓
৩. Keycloak-এ পাসওয়ার্ড দিলেন
        ↓
৪. Keycloak একটা সেশন কুকি সেট করল (keycloak.example.com ডোমেইনে)
   + app-A-কে একটা টোকেন দিল
        ↓
৫. এখন আপনি app-B.com খুললেন
        ↓
৬. app-B আপনাকে Keycloak-এ পাঠাল
        ↓
৭. Keycloak তার নিজের কুকি দেখল → "আরে, একে তো চিনি!"
   → পাসওয়ার্ড না চেয়েই সোজা টোকেন দিয়ে ফেরত পাঠাল ⚡
```

**ধাপ ৭-ই হলো SSO-এর জাদু।** ব্যবহারকারীর চোখে মনে হয় কিছুই হয়নি — শুধু একটা ঝলকানি, তারপরই সে লগইন অবস্থায়।

**SSO-এর সুবিধা:**

| সুবিধা | ব্যাখ্যা |
|---|---|
| **ব্যবহারকারীর জন্য আরাম** | একটাই পাসওয়ার্ড মনে রাখতে হয়, বারবার লগইন করতে হয় না |
| **নিরাপত্তা বাড়ে** | একটাই শক্তিশালী পাসওয়ার্ড + MFA, ১০টা দুর্বল পাসওয়ার্ডের বদলে |
| **সহজ ব্যবস্থাপনা** | কর্মী চাকরি ছাড়লে এক জায়গায় অ্যাকাউন্ট বন্ধ করলেই সব অ্যাক্সেস বন্ধ |
| **অডিট** | কে কখন কোথায় লগইন করল, সব এক জায়গায় লগ থাকে |

**ঝুঁকি:** একটাই দরজা মানে — সেই দরজা ভাঙলে সব খুলে যাবে। তাই আইডেন্টিটি প্রোভাইডারে **MFA (দুই স্তরের যাচাই)** অবশ্যই চালু রাখুন।

## 📌 দ্রুত রিভিশন চিট-শিট

**মূল শব্দগুলো:**

| শব্দ | এক লাইনে |
|---|---|
| **Authentication** | তুমি কে? (পরিচয় যাচাই) |
| **Authorization** | তুমি কী করতে পারবে? (অনুমতি যাচাই) |
| **OAuth 2.0** | অনুমতি দেওয়ার প্রোটোকল |
| **OIDC** | OAuth + পরিচয় যাচাই (`id_token` দেয়) |
| **JWT** | নিজেই তথ্য বহনকারী সাইন করা টোকেন |
| **Access Token** | ছোট মেয়াদের চাবি (১৫ মিনিট) |
| **Refresh Token** | দীর্ঘ মেয়াদের চাবি, নতুন access token আনে |
| **Scope** | টোকেনটা কী কী করতে পারবে |
| **PKCE** | কোড চুরি ঠেকানোর কৌশল (মোবাইল অ্যাপে বাধ্যতামূলক) |
| **SSO** | একবার লগইন, সব জায়গায় প্রবেশ |
| **mTLS** | দুই পক্ষই একে অপরকে যাচাই করে |
| **RBAC** | ভূমিকা দিয়ে অনুমতি |
| **ABAC** | বৈশিষ্ট্য ও শর্ত দিয়ে অনুমতি |

**যে ভুলগুলো কখনো করবেন না:**

1. ❌ পাসওয়ার্ড plain text বা MD5-এ রাখা → ✅ bcrypt/Argon2 ব্যবহার করুন
2. ❌ JWT-এর payload-এ গোপন তথ্য রাখা → ✅ JWT পড়া যায়, শুধু বদলানো যায় না
3. ❌ `localStorage`-এ টোকেন রাখা → ✅ `HttpOnly` কুকি ব্যবহার করুন
4. ❌ Access token-এর মেয়াদ ৩০ দিন রাখা → ✅ ১৫ মিনিট + refresh token
5. ❌ Redirect URI `startsWith()` দিয়ে চেক করা → ✅ হুবহু মিল দেখুন
6. ❌ মোবাইল অ্যাপে PKCE ছাড়া OAuth → ✅ পাবলিক ক্লায়েন্টে PKCE বাধ্যতামূলক
7. ❌ Implicit Flow ব্যবহার করা → ✅ Authorization Code Flow + PKCE

**একটা টিপিক্যাল লগইনের পুরো যাত্রা:**
```
ব্যবহারকারী → লগইন পেজ → পরিচয় যাচাই (AuthN)
                              ↓
                    Access Token + Refresh Token
                              ↓
              API কল (Authorization: Bearer <token>)
                              ↓
              সার্ভার Signature যাচাই করল ✅
                              ↓
              টোকেনের role/scope দেখে অনুমতি চেক (AuthZ)
                              ↓
                        উত্তর পাঠাল
```
