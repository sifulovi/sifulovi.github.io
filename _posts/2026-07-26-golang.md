## ১. Goroutine কী? এটা Thread থেকে কীভাবে আলাদা?

**সংজ্ঞা:** Goroutine হলো একটা হালকা থ্রেড, যেটা Go রানটাইম নিজে ম্যানেজ করে। OS-লেভেলের থ্রেডের তুলনায় এটা অনেক কম রিসোর্স খায়।

থ্রেডের সময়সূচি ঠিক করে **অপারেটিং সিস্টেম**, কিন্তু goroutine-এর সময়সূচি ঠিক করে **Go রানটাইম নিজে**। ফলে Go অল্প কয়েকটা থ্রেড দিয়েই হাজার হাজার goroutine চালাতে পারে।

**বাস্তব উদাহরণ — রেস্টুরেন্টের ওয়েটার:**

| | Thread | Goroutine |
|---|---|---|
| উপমা | প্রতি টেবিলের জন্য **একজন করে আলাদা ওয়েটার** নিয়োগ | **৩ জন ওয়েটার**, যারা ২০টা টেবিল সামলায় |
| খরচ | ১০০ টেবিল = ১০০ জন কর্মচারী (বেতন অনেক!) | ১০০ টেবিল = ৩ জন কর্মচারী |
| কে সামলায় | রেস্টুরেন্টের মালিক (OS) | হেড ওয়েটার (Go রানটাইম) |

একজন ওয়েটার যখন রান্নাঘরে অর্ডার দিতে যায়, তখন অলস দাঁড়িয়ে থাকে না — অন্য টেবিলের অর্ডার নিতে চলে যায়। Goroutine-ও ঠিক এভাবে কাজ করে: কোনো goroutine যখন ফাইল পড়ার বা নেটওয়ার্ক রেসপন্সের অপেক্ষায় থাকে, Go রানটাইম সেই থ্রেডে অন্য একটা goroutine চালিয়ে দেয়।

```go
go doSomething()   // ব্যস! এটুকুই। একটা goroutine চালু হয়ে গেল।
```

**সংখ্যায় পার্থক্যটা দেখুন:**
- একটা OS থ্রেড শুরুতেই নেয় **~১ MB** মেমরি → ১০,০০০ থ্রেড = ১০ GB ❌
- একটা goroutine শুরুতে নেয় **~২ KB** → ১০,০০০ goroutine = মাত্র ২০ MB ✅

## ২. Go-তে Slice কী, আর Array থেকে এটা কীভাবে আলাদা?

Go-তে **Slice** হলো একটা গতিশীল, আকার-পরিবর্তনযোগ্য তালিকা। আর **Array**-এর আকার নির্দিষ্ট, বদলানো যায় না।

**Array:** দৈর্ঘ্য নির্দিষ্ট, বাড়তে বা কমতে পারে না। ঘোষণার সময়ই আকার বলে দিতে হয়।
```go
var arr [3]int = [3]int{1, 2, 3}   // নির্দিষ্ট আকার: ৩টা এলিমেন্ট
```

**Slice:** Array-এর উপরেই তৈরি, কিন্তু দরকার অনুযায়ী বাড়তে-কমতে পারে। এর দুইটা মাপ আছে — **length** (কতগুলো এলিমেন্ট আছে) এবং **capacity** (ভেতরের array-তে মোট কত জায়গা আছে)।
```go
slice := []int{1, 2, 3}   // গতিশীল আকার: আরও যোগ করা যাবে
slice = append(slice, 4)  // এখন ৪টা এলিমেন্ট
```

**বাস্তব উদাহরণ — ডিমের ট্রে:**

- **Array** = **৩০ খোপের ডিমের ট্রে**। ৩০টার বেশি ডিম রাখা যাবে না, ট্রে কাটাও যাবে না।
- **Slice** = **একটা ব্যাগ**, যার ভেতরে ট্রে আছে। ট্রে ভরে গেলে? Go চুপচাপ একটা **দ্বিগুণ বড় ট্রে** এনে সব ডিম সেখানে সরিয়ে নেয়, আপনি টেরও পান না।

**Length vs Capacity বুঝুন:**
```go
s := make([]int, 3, 10)
//                 ↑  ↑
//          length=3  capacity=10

fmt.Println(len(s), cap(s))  // 3 10
// মানে: এখন ৩টা ডিম আছে, কিন্তু ট্রেতে ১০ খোপ আছে।
// ১০টা পর্যন্ত যোগ করলে নতুন ট্রে লাগবে না — দ্রুত!
```

**⚠️ একটা বিপজ্জনক ফাঁদ — Slice কিন্তু ভেতরের Array শেয়ার করে:**

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]        // b = [2, 3]
b[0] = 99
fmt.Println(a)     // [1, 99, 3, 4, 5]  ← a-ও বদলে গেল! 😱
```

`b` আসলে `a`-এর কোনো কপি নয় — এটা একই মেমরির দিকে তাক করা একটা জানালা। আলাদা কপি চাইলে:
```go
b := make([]int, 2)
copy(b, a[1:3])    // এখন b সম্পূর্ণ আলাদা ✅
```

## ৩. Go-তে Error Handling কীভাবে হয়?

Go একটা খুব সহজ প্যাটার্ন ব্যবহার করে — ফাংশন তার **দ্বিতীয় রিটার্ন ভ্যালু হিসেবে একটা `error`** ফেরত দেয়। `err` যদি `nil` হয় তাহলে কোনো সমস্যা হয়নি; নাহলে সমস্যাটা সামলাতে হবে।

```go
file, err := os.Open("data.txt")
if err != nil {
    log.Fatal(err)   // সমস্যা সামলান
    return
}
defer file.Close()
// এখানে নিশ্চিতভাবে file ব্যবহার করা যাবে
```

**অন্য ভাষার সাথে পার্থক্য:**

| | Java/Python | Go |
|---|---|---|
| উপায় | `try { ... } catch (Exception e) { }` | `if err != nil { }` |
| এরর কি লুকানো যায়? | হ্যাঁ — কোন ফাংশন এরর ছুঁড়বে বোঝা যায় না | না — সিগনেচারেই লেখা থাকে |
| কোডের চেহারা | সংক্ষিপ্ত | বেশি লাইন, কিন্তু স্পষ্ট |

**বাস্তব উদাহরণ:** Java-তে ব্যতিক্রম (exception) হলো **ফায়ার অ্যালার্ম** — কোথাও আগুন লাগলে অ্যালার্ম বাজে, কিন্তু সেটা কে থামাবে তা কোডে দেখে বোঝা যায় না; হয়তো ৫ লেভেল উপরে কেউ ধরবে।

Go-তে এরর হলো **প্রতিটা দরজায় একটা করে চেকপোস্ট**। প্রতিটা ধাপে আপনাকে জিজ্ঞেস করতে হয় "সব ঠিক আছে তো?" — লিখতে বেশি লাগে, কিন্তু কোনো সমস্যা চুপচাপ পাশ কাটিয়ে যেতে পারে না।

**নিজের এরর বানানো:**
```go
// সহজভাবে
return errors.New("ব্যবহারকারী খুঁজে পাওয়া যায়নি")

// প্রেক্ষাপট জুড়ে দিয়ে (এটাই ভালো চর্চা)
if err != nil {
    return fmt.Errorf("ব্যবহারকারী আনতে সমস্যা (id=%d): %w", id, err)
}
```
`%w` দিয়ে মূল এররটা "মুড়ে" (wrap) রাখা হয়, তাই পরে `errors.Is()` বা `errors.As()` দিয়ে আসল কারণটা খুঁজে বের করা যায়।

## ৪. Go-তে Struct কী?

**Struct** হলো একটা যৌগিক ডেটা টাইপ, যা কয়েকটা ভেরিয়েবলকে একটা নামের নিচে জড়ো করে। এই ভেরিয়েবলগুলোকে বলে **field**।

```go
type Employee struct {
    Name     string
    Age      int
    Salary   float64
    IsActive bool
}

karim := Employee{
    Name:     "করিম উদ্দিন",
    Age:      ৩০,
    Salary:   75000,
    IsActive: true,
}

fmt.Println(karim.Name)   // করিম উদ্দিন
```

**বাস্তব উদাহরণ:** Struct হলো একটা **ফর্মের মতো** — যেমন চাকরির আবেদন ফর্ম। ফর্মে নির্দিষ্ট ঘর থাকে (নাম, বয়স, ঠিকানা), আর প্রতিটা আবেদনকারী সেই ঘরগুলো পূরণ করে। Struct-এর সংজ্ঞা = খালি ফর্ম, আর `karim` = পূরণ করা একটা ফর্ম।

**Struct-এ Method যোগ করা:**
```go
func (e Employee) Description() string {
    return fmt.Sprintf("%s, বয়স %d", e.Name, e.Age)
}

func (e *Employee) GiveRaise(amount float64) {
    e.Salary += amount    // পয়েন্টার রিসিভার — আসল ভ্যালু বদলায়
}
```

**⚠️ গুরুত্বপূর্ণ:** `(e Employee)` = ভ্যালু রিসিভার, একটা কপি পায়, বদলালেও আসলটা বদলায় না। `(e *Employee)` = পয়েন্টার রিসিভার, আসলটাকেই বদলাতে পারে। **যদি ফিল্ড বদলাতে চান, পয়েন্টার রিসিভার ব্যবহার করুন।**

## ৫. Go-তে `make` আর `new`-এর পার্থক্য কী?

দুইটাই মেমরি বরাদ্দ করে, কিন্তু কাজ আলাদা:

**`make`:** শুধু **slice, map এবং channel** বানাতে ও চালু করতে ব্যবহার হয়। এটা মেমরি বরাদ্দ করে **এবং ভেতরের কাঠামোটাও প্রস্তুত করে দেয়**, যাতে সাথে সাথে ব্যবহার করা যায়।
```go
slice := make([]int, 5)      // ৫ দৈর্ঘ্যের একটা slice
m     := make(map[string]int) // একটা খালি map
ch    := make(chan int)       // একটা channel
```

**`new`:** যেকোনো টাইপের জন্য শূন্য-মান (zero value) সহ মেমরি বরাদ্দ করে এবং সেই মেমরির **পয়েন্টার** ফেরত দেয়।
```go
num := new(int)     // *int, যার মান 0
fmt.Println(*num)   // 0
```

**পার্থক্যের টেবিল:**

| | `make` | `new` |
|---|---|---|
| কী কী টাইপে চলে | শুধু slice, map, channel | যেকোনো টাইপ |
| কী ফেরত দেয় | টাইপটা নিজেই (`[]int`) | পয়েন্টার (`*int`) |
| ব্যবহারের জন্য প্রস্তুত? | ✅ হ্যাঁ | ভেতরের কাঠামো তৈরি হয় না |

**বাস্তব উদাহরণ — নতুন অফিস:**
- `new` = **একটা খালি ঘর** পেলেন। চার দেয়াল আছে, আর কিছু নেই।
- `make` = **সাজানো-গোছানো অফিস** পেলেন — টেবিল, চেয়ার, ইন্টারনেট সব রেডি। বসেই কাজ শুরু করতে পারবেন।

**⚠️ সবচেয়ে কমন ভুল — `make` ছাড়া map ব্যবহার:**
```go
var m map[string]int   // m হলো nil!
m["a"] = 1             // 💥 panic: assignment to entry in nil map

// সঠিক:
m := make(map[string]int)
m["a"] = 1   // ✅
```
Map-এর ক্ষেত্রে `make` **বাধ্যতামূলক**, কারণ map-এর ভেতরে হ্যাশ টেবিলের কাঠামো তৈরি করতে হয়। কিন্তু slice-এ `append` করলে `make` ছাড়াও চলে, কারণ `append` নিজেই দরকার হলে জায়গা বানিয়ে নেয়।

## ৬. Go-তে `defer` স্টেটমেন্ট কী?

`defer` কোনো ফাংশনের চালানো **পিছিয়ে দেয়** — যতক্ষণ না বাইরের ফাংশনটা রিটার্ন করে। সাধারণত রিসোর্স পরিষ্কার করার জন্য এটা ব্যবহার হয়, যেমন ফাইল বন্ধ করা।

```go
func readFile() error {
    f, err := os.Open("data.txt")
    if err != nil {
        return err
    }
    defer f.Close()   // ফাংশন যেভাবেই শেষ হোক, এটা চলবেই

    // ... অনেক কোড, অনেকগুলো return ...
    // প্রতিটা return-এর আগে f.Close() লিখতে হচ্ছে না ✅
    return nil
}
```

**বাস্তব উদাহরণ:** ঘর থেকে বের হওয়ার সময় **লাইট বন্ধ করার কথা মনে রাখা**। `defer` হলো দরজায় লাগানো একটা অটোমেটিক সুইচ — আপনি সামনের দরজা দিয়ে বের হন, পেছনের দরজা দিয়ে বের হন, বা জানালা দিয়ে লাফ দেন — লাইট নিজে থেকেই বন্ধ হয়ে যাবে।

**তিনটা গুরুত্বপূর্ণ নিয়ম:**

**১) একাধিক `defer` উল্টো ক্রমে চলে (LIFO — শেষেরটা আগে):**
```go
defer fmt.Println("এক")
defer fmt.Println("দুই")
defer fmt.Println("তিন")
// আউটপুট: তিন → দুই → এক
```
এটা যুক্তিসঙ্গত — যে রিসোর্স সবার শেষে খোলা হয়েছে, সেটাই আগে বন্ধ হওয়া উচিত।

**২) আর্গুমেন্টগুলো `defer` লেখার সময়েই হিসাব হয়ে যায়:**
```go
i := 0
defer fmt.Println(i)   // এখানেই i-এর মান 0 ধরে রাখা হলো
i = 100
// আউটপুট: 0 (100 নয়!)
```

**৩) `defer` লুপের ভেতরে দেবেন না:**
```go
// ❌ খারাপ — ১০০০টা ফাইল একসাথে খোলা থাকবে!
for _, name := range files {
    f, _ := os.Open(name)
    defer f.Close()   // লুপ শেষে নয়, পুরো ফাংশন শেষে চলবে
}

// ✅ ভালো — আলাদা ফাংশনে মুড়ে দিন
for _, name := range files {
    func() {
        f, _ := os.Open(name)
        defer f.Close()   // এই ছোট ফাংশনটা শেষ হলেই বন্ধ হবে
    }()
}
```

## ৭. Go-তে Interface কীভাবে বাস্তবায়ন করবেন?

Go-তে **Interface** হলো এমন একটা টাইপ, যা কতগুলো মেথডের নাম-স্বাক্ষর ঠিক করে দেয়। কোনো টাইপ যদি ঐ সব মেথড লিখে ফেলে, তাহলে সে **স্বয়ংক্রিয়ভাবেই** ঐ interface বাস্তবায়ন করে ফেলল। এর জন্য আলাদা কোনো কীওয়ার্ড (যেমন Java-এর `implements`) লাগে না।

```go
type Shape interface {
    Area() float64
    Perimeter() float64
}

type Rectangle struct {
    Width, Height float64
}

func (r Rectangle) Area() float64      { return r.Width * r.Height }
func (r Rectangle) Perimeter() float64 { return 2 * (r.Width + r.Height) }

// ব্যস! Rectangle এখন স্বয়ংক্রিয়ভাবে Shape ✅
var s Shape = Rectangle{Width: 5, Height: 3}
fmt.Println(s.Area())   // 15
```

**বাস্তব উদাহরণ — "হাঁসের পরীক্ষা" (Duck Typing):**
> "যদি সেটা হাঁসের মতো হাঁটে আর হাঁসের মতো ডাকে, তাহলে সেটা হাঁসই।"

Java-তে আপনাকে ঘোষণা দিতে হয়: `class Duck implements Bird`। Go-তে দরকার নেই — আপনি যদি `Fly()` আর `Quack()` মেথড লিখে ফেলেন, তাহলেই আপনি `Bird`।

**এতে সুবিধা কী:** আপনি এমন কোনো লাইব্রেরির টাইপকেও নিজের interface মেনে চলা বানাতে পারেন, যেটার সোর্স কোড আপনার হাতে নেই!

**সবচেয়ে বেশি ব্যবহৃত উদাহরণ — টেস্ট লেখা সহজ হয়:**
```go
type UserStore interface {
    GetUser(id int) (*User, error)
}

// আসল কোডে
type PostgresStore struct{ db *sql.DB }
func (p PostgresStore) GetUser(id int) (*User, error) { /* ডেটাবেজ কল */ }

// টেস্টে — কোনো ডেটাবেজ ছাড়াই!
type FakeStore struct{}
func (f FakeStore) GetUser(id int) (*User, error) {
    return &User{Name: "টেস্ট ইউজার"}, nil
}
```
সার্ভিসটা `UserStore` চায়, তাই টেস্টে `FakeStore` দিয়ে দিলেই হলো — ডেটাবেজ চালু করার দরকার নেই। ⚡

**💡 Go-এর সোনালি নিয়ম:** *"ছোট ছোট interface বানান।"* Go-এর সবচেয়ে জনপ্রিয় interface-এ মাত্র একটা মেথড:
```go
type Writer interface { Write(p []byte) (n int, err error) }
```

## ৮. Concurrency বনাম Parallelism

**Goroutine:** Goroutine তৈরি হয়েছে **concurrency**-র জন্য। এরা একটা OS থ্রেডের উপরেই পালা করে (interleaved) চলে। এতে একটা CPU কোরেই দক্ষভাবে অনেক কাজ সামলানো যায়।

**সাধারণ Thread:** থ্রেড সাধারণত **parallelism**-এর জন্য ব্যবহার হয়। এরা একাধিক CPU কোরে সত্যিকারের সমান্তরালে চলে। তবে থ্রেড তৈরি ও ম্যানেজ করার খরচ অনেক বেশি।

**পার্থক্যটা এক লাইনে:**
- **Concurrency** = অনেকগুলো কাজ **সামলানো** (একসাথে চলা লাগবে না)
- **Parallelism** = অনেকগুলো কাজ **একসাথেই করা**

**বাস্তব উদাহরণ — রান্নাঘর:**

**Concurrency (১ জন রাঁধুনি):**
> ভাত চড়িয়ে দিলেন → ফুটতে থাকুক → এই ফাঁকে পেঁয়াজ কাটলেন → তরকারি বসালেন → ভাত নেড়ে দিলেন → আবার তরকারিতে ফিরলেন

একজন মানুষ, কিন্তু ৩টা কাজ চলছে। ভাত ফোটার সময়টা অলস বসে থাকেননি। ✅

**Parallelism (৩ জন রাঁধুনি):**
> একজন ভাত রাঁধছে, একজন তরকারি, একজন সালাদ — **একই মুহূর্তে**।

**Go-তে দুটোই পাবেন:**
```go
runtime.GOMAXPROCS(1)   // ১টা কোর → শুধু concurrency
runtime.GOMAXPROCS(4)   // ৪টা কোর → concurrency + parallelism
```
ডিফল্টে Go আপনার মেশিনের সব কোর ব্যবহার করে।

> **Rob Pike-এর বিখ্যাত উক্তি:** *"Concurrency is not parallelism"* — Concurrency হলো **ডিজাইন**, Parallelism হলো **বাস্তবায়ন**।

## ৯. হালকা বনাম ভারী (Goroutine বনাম Thread)

**Goroutine:** থ্রেডের তুলনায় অনেক হালকা। শুরুতে খুব ছোট স্ট্যাক নেয় (সাধারণত ২ KB বা ৪ KB) এবং কম মেমরি খরচ করে। ফলে একটা Go প্রোগ্রাম খুব কম খরচে হাজার হাজার goroutine চালাতে পারে।

**সাধারণ Thread:** মেমরি ও রিসোর্সের দিক থেকে অনেক ভারী। বেশি সংখ্যক থ্রেড বানালে মেমরির চাপ ও ব্যবস্থাপনার জটিলতা দুটোই বাড়ে।

**সংখ্যা দিয়ে তুলনা:**

| | OS Thread | Goroutine |
|---|---|---|
| শুরুর স্ট্যাক | ১–৮ MB (স্থির) | ২ KB (দরকারে বাড়ে) |
| তৈরির সময় | ~১০০ মাইক্রোসেকেন্ড | ~০.৩ মাইক্রোসেকেন্ড |
| সুইচ করার খরচ | বেশি (কার্নেলে যেতে হয়) | কম (Go রানটাইমেই হয়) |
| কতগুলো চালানো যায় | কয়েক হাজার | **কয়েক লক্ষ** |

**বাস্তব উদাহরণ:** একটা ওয়েব সার্ভারে ১০,০০০ ব্যবহারকারী একসাথে সংযুক্ত।
- **Java (থ্রেড প্রতি রিকোয়েস্ট):** ১০,০০০ × ১ MB = **১০ GB RAM** 💀
- **Go (goroutine প্রতি রিকোয়েস্ট):** ১০,০০০ × ২ KB = **২০ MB RAM** ✅

এই কারণেই Go দিয়ে লেখা সার্ভার এত বেশি সংযোগ সামলাতে পারে।

**Goroutine-এর স্ট্যাক বাড়ে-কমে:** শুরু হয় ২ KB দিয়ে, দরকার হলে Go রানটাইম নিজেই বড় করে দেয়। থ্রেডে এটা সম্ভব নয় — শুরুতেই পুরো জায়গা বরাদ্দ করতে হয়।

## ১০. Go প্রোগ্রামে `main` ফাংশন শেষ হলে কী হয়?

`main` ফাংশন শেষ হওয়ামাত্র **পুরো প্রোগ্রাম সাথে সাথে বন্ধ হয়ে যায়** — এমনকি যদি কিছু goroutine তখনো চলতে থাকে, তবুও।

যেসব goroutine তখনো কাজ শেষ করেনি, সেগুলো **কাজ অসমাপ্ত রেখেই থেমে যাবে**। তাই `sync.WaitGroup` বা `context`-এর মতো ব্যবস্থা ব্যবহার করা জরুরি, যাতে `main` শেষ হওয়ার আগে সব প্রয়োজনীয় কাজ শেষ হয়।

**সমস্যাটা দেখুন:**
```go
func main() {
    go fmt.Println("আমি একটা goroutine")
    // main এখানেই শেষ
}
// আউটপুট: (কিছুই না!) 😱
```

goroutine-টা চালু হওয়ার সুযোগই পেল না, তার আগেই `main` শেষ।

**সঠিক সমাধান — `sync.WaitGroup`:**
```go
func main() {
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Println("আমি একটা goroutine")
    }()
    wg.Wait()   // সব goroutine শেষ হওয়া পর্যন্ত অপেক্ষা
}
// আউটপুট: আমি একটা goroutine ✅
```

**❌ যেটা করবেন না:**
```go
go doWork()
time.Sleep(2 * time.Second)   // "২ সেকেন্ডে নিশ্চয়ই শেষ হবে"
```
এটা **অনুমান**, নিশ্চয়তা নয়। সার্ভার ব্যস্ত থাকলে ৩ সেকেন্ড লাগতে পারে — তখন কাজ অসমাপ্ত থেকে যাবে।

**বাস্তব উদাহরণ:** অফিস বন্ধ করার সময় ম্যানেজার যদি না দেখেই তালা মেরে দেন, তাহলে ভেতরে আটকে পড়া কর্মচারীর কাজ অসমাপ্তই থেকে যাবে। `WaitGroup` হলো সেই তালিকা, যেখানে সবাই বের হওয়ার সময় নাম কাটে — সবার নাম কাটা হলেই তালা লাগে।

## ১১. Go-তে Channel কী এবং কীভাবে ব্যবহার করে?

Channel দিয়ে goroutine-রা একে অপরের সাথে **যোগাযোগ** করে। মান পাঠানো ও গ্রহণ করার মাধ্যমে এরা নিজেদের মধ্যে সমন্বয়ও (synchronize) করে।

```go
ch := make(chan int)

go func() {
    ch <- 5          // channel-এ ৫ পাঠানো হলো
}()

value := <-ch        // channel থেকে মান নেওয়া হলো
fmt.Println(value)   // আউটপুট: 5
```

**তীরচিহ্নটা মনে রাখার সহজ উপায়:** তীর সবসময় **ডেটার যাওয়ার দিক** দেখায়।
- `ch <- 5` → ডেটা channel-এ **ঢুকছে** (পাঠানো)
- `<-ch` → ডেটা channel থেকে **বেরোচ্ছে** (গ্রহণ)

**বাস্তব উদাহরণ — রান্নাঘরের জানালা:**

রেস্টুরেন্টে রান্নাঘর আর ডাইনিং হলের মাঝে একটা ছোট জানালা থাকে। শেফ প্লেট রাখে, ওয়েটার তুলে নেয়। শেফ আর ওয়েটারের সরাসরি কথা বলার দরকার নেই — জানালাটাই যোগাযোগের মাধ্যম।

**Go-এর মূলমন্ত্র:**
> *"Don't communicate by sharing memory; share memory by communicating."*
> (মেমরি ভাগ করে যোগাযোগ কোরো না; যোগাযোগ করে মেমরি ভাগ করো।)

মানে — একই ভেরিয়েবলে কয়েকজন হাত দেওয়ার চেয়ে (তাতে lock লাগে, race condition হয়), channel দিয়ে ডেটা হস্তান্তর করাই ভালো।

**Channel বন্ধ করা ও তার উপর লুপ চালানো:**
```go
ch := make(chan int, 3)
go func() {
    for i := 1; i <= 3; i++ {
        ch <- i
    }
    close(ch)     // "আর কিছু আসবে না"
}()

for v := range ch {   // channel বন্ধ হলে লুপ নিজেই থামবে
    fmt.Println(v)    // 1, 2, 3
}
```

**⚠️ Channel-এর নিয়ম:**
1. **পাঠানোর দায়িত্ব যার, বন্ধ করার দায়িত্বও তার।** গ্রহীতা কখনো channel বন্ধ করবে না।
2. বন্ধ channel-এ পাঠালে → **panic** 💥
3. বন্ধ channel থেকে পড়লে → সাথে সাথে zero value পাওয়া যায় (ব্লক হয় না)
4. `v, ok := <-ch` → `ok` মিথ্যা মানে channel বন্ধ ও খালি

## ১২. Go মেমরি কীভাবে ম্যানেজ করে? Garbage Collection কী?

Go একটা **Garbage Collector (GC)** ব্যবহার করে মেমরি স্বয়ংক্রিয়ভাবে সামলায়। এটা খুঁজে বের করে কোন অবজেক্টগুলোতে আর কোনো রেফারেন্স নেই, তারপর তাদের মেমরি মুক্ত করে দেয় — ফলে মেমরি লিক হয় না।

এতে Go সেই ভাষাগুলোর চেয়ে ব্যবহার করা সহজ, যেখানে হাতে হাতে মেমরি ম্যানেজ করতে হয়। তবে GC চক্রের কারণে মাঝে মাঝে সামান্য দেরি (latency) হতে পারে।

**বাস্তব উদাহরণ:** GC হলো **অফিসের পরিচ্ছন্নতাকর্মী**। আপনি ব্যবহার শেষে কাগজ ডাস্টবিনে ফেলে দিলেন, তারপর ভুলেই গেলেন। কর্মী নিয়মিত এসে ডাস্টবিন খালি করে দেয় — আপনাকে মনে রাখতে হয় না।

**তুলনা:**

| ভাষা | মেমরি ব্যবস্থাপনা | ঝুঁকি |
|---|---|---|
| C/C++ | হাতে (`malloc`/`free`) | মেমরি লিক, dangling pointer, double free |
| Java | GC | GC pause বেশি হতে পারে |
| **Go** | **GC (কম pause-এর জন্য অপ্টিমাইজড)** | সাধারণত < ১ মিলিসেকেন্ড pause |
| Rust | কম্পাইল টাইমে (ownership) | GC নেই, কিন্তু শেখা কঠিন |

**Go-এর GC-এর বিশেষত্ব:** এটা **concurrent** — মানে আপনার প্রোগ্রাম চলতে চলতেই GC কাজ করে। পুরো প্রোগ্রাম থামিয়ে দেয় না। Go ১.৮ থেকে GC pause সাধারণত **১ মিলিসেকেন্ডের নিচে** থাকে।

**Escape Analysis — একটা চমৎকার অপ্টিমাইজেশন:**
কম্পাইলার দেখে কোনো ভেরিয়েবল ফাংশনের বাইরে যাচ্ছে কিনা।
- না গেলে → **স্ট্যাকে** রাখে (খুব দ্রুত, GC-এর দরকার নেই)
- গেলে → **হিপে** রাখে (GC সামলাবে)

```bash
go build -gcflags="-m" main.go   # কোনটা কোথায় যাচ্ছে দেখতে
```

**GC-এর চাপ কমানোর টিপস:**
- Slice-এর আকার আগে থেকে জানা থাকলে `make([]int, 0, 100)` লিখুন — বারবার বড় করতে হবে না
- বারবার একই অবজেক্ট বানালে `sync.Pool` ব্যবহার করুন
- লুপের ভেতরে অপ্রয়োজনীয় পয়েন্টার বানানো এড়িয়ে চলুন

## ১৩. Python বা Java-এর তুলনায় Go ব্যবহারের সুবিধা কী?

### ক) Concurrency
Go-তে goroutine-এর মাধ্যমে কনকারেন্সির সাপোর্ট **ভাষার ভেতরেই** আছে। ফলে একসাথে অনেক কাজ করা প্রোগ্রাম লেখা সহজ। এটা Python-এর threading-এর চেয়ে অনেক দক্ষ এবং Java-এর থ্রেড ম্যানেজমেন্টের চেয়ে অনেক সরল।

> **Python-এর একটা বড় সীমাবদ্ধতা — GIL (Global Interpreter Lock):** আপনার মেশিনে ৮টা কোর থাকলেও Python-এর থ্রেড একসাথে মাত্র একটা কোরই ব্যবহার করতে পারে (CPU-নির্ভর কাজে)। Go-তে এই সীমাবদ্ধতা নেই।

### খ) Performance
Go একটা **কম্পাইলড ভাষা** — কোড সরাসরি মেশিন কোডে রূপান্তরিত হয়। তাই এটা Python-এর (যেটা ইন্টারপ্রেটেড) চেয়ে অনেক দ্রুত এবং প্রায়ই Java-এর কাছাকাছি। উচ্চ-পারফরম্যান্সের ওয়েব সার্ভার ও ব্যাকএন্ড সার্ভিস বানানোর জন্য দুর্দান্ত।

### গ) সরলতা ও পঠনযোগ্যতা
Go-এর সিনট্যাক্স সহজ, ফিচারের সংখ্যাও কম — তাই শেখা ও ব্যবহার করা সহজ। Java-এর মতো ইনহেরিটেন্সের মতো জটিল ফিচার নেই, ফলে কোড পড়তে ও রক্ষণাবেক্ষণ করতে সুবিধা হয়।

> **মজার তথ্য:** Go-তে কীওয়ার্ড আছে মাত্র **২৫টা**। Java-তে ৫০+, C++-এ ৯০+। এক সপ্তাহেই পুরো ভাষা শিখে ফেলা সম্ভব।
>
> এছাড়া `gofmt` টুলটা সব কোড **একই স্টাইলে** ফরম্যাট করে দেয়। ফলে "ট্যাব নাকি স্পেস", "ব্রেস কোথায় বসবে" — এসব নিয়ে টিমে ঝগড়া হয় না। 😄

### ঘ) Cross-Platform Compilation
Go একটা প্রোগ্রামকে **একটাই বাইনারি ফাইলে** কম্পাইল করতে পারে, যেটা বিভিন্ন অপারেটিং সিস্টেমে (Windows, macOS, Linux) চলে। ফলে ডিপ্লয়মেন্ট অনেক সহজ — Python-এর মতো প্রতিটা পরিবেশে আলাদা সেটআপ লাগে না।

```bash
GOOS=linux GOARCH=amd64 go build   # Mac-এ বসে Linux-এর জন্য বানানো
```
তারপর শুধু ফাইলটা সার্ভারে কপি করে চালান — **কোনো রানটাইম, কোনো ডিপেন্ডেন্সি ইনস্টল করতে হবে না**। Docker ইমেজও তাই মাত্র ১০-২০ MB হয় (Java-এর ৩০০ MB-এর তুলনায়)।

### ঙ) Memory Management
Go-তে garbage collector আছে যা মেমরি নিজে সামলায় — C বা C++-এর মতো হাতে ম্যানেজ করতে হয় না। এতে পারফরম্যান্স ও ব্যবহারের সহজতার মধ্যে একটা ভারসাম্য পাওয়া যায়, অনেকটা Java-এর মতো কিন্তু আরও সরল।

### চ) শক্তিশালী Standard Library
Go-এর সাথেই একটা সমৃদ্ধ স্ট্যান্ডার্ড লাইব্রেরি আসে — ওয়েব সার্ভার, নেটওয়ার্কিং, ফাইল হ্যান্ডলিং সব কিছুর জন্য প্যাকেজ আছে। ফলে বাইরের লাইব্রেরি ছাড়াই অনেক কিছু বানানো যায়, Python-এর মতো নয়।

```go
// শুধু স্ট্যান্ডার্ড লাইব্রেরি দিয়েই একটা পূর্ণাঙ্গ ওয়েব সার্ভার!
package main

import ("fmt"; "net/http")

func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "হ্যালো!")
    })
    http.ListenAndServe(":8080", nil)
}
```
কোনো Flask, কোনো Spring Boot লাগেনি। ✅

**⚖️ ন্যায্যতার খাতিরে — Go-এর দুর্বলতাও জেনে রাখুন:**
- মেশিন লার্নিং / ডেটা সায়েন্সে Python অনেক এগিয়ে
- `if err != nil` বারবার লিখতে গিয়ে কোড লম্বা হয়ে যায়
- জেনেরিক এসেছে অনেক দেরিতে (Go ১.১৮, ২০২২ সালে)
- Java-এর মতো বিশাল এন্টারপ্রাইজ ইকোসিস্টেম নেই

## ১৪. Go ভেতরে ভেতরে কনকারেন্সি কীভাবে অর্জন করে?

Go-এর রানটাইম **GOMAXPROCS** নামে একটা মডেল ব্যবহার করে, যা ঠিক করে দেয় goroutine চালানোর জন্য সর্বোচ্চ কতগুলো OS থ্রেড ব্যবহার হবে।

Go অল্প কয়েকটা OS থ্রেডের উপর অনেকগুলো goroutine বসিয়ে দেয় এবং প্রয়োজন অনুযায়ী তাদের অদল-বদল (multiplex) করে। একে বলে **M:N scheduling** — মানে অনেক (M) goroutine কম সংখ্যক (N) OS থ্রেডে চলে।

**G-M-P মডেল (Go-এর শিডিউলারের আসল কাঠামো):**

| অক্ষর | মানে | উপমা |
|---|---|---|
| **G** | Goroutine — আপনার কাজ | রান্নার একটা অর্ডার |
| **M** | Machine — একটা OS থ্রেড | একজন রাঁধুনি |
| **P** | Processor — শিডিউলিংয়ের প্রেক্ষাপট, অর্ডারের সারি ধরে রাখে | একটা রান্নার স্টেশন (চুলা + অর্ডারের তালিকা) |

**কীভাবে চলে:**
```
   P1 (স্টেশন ১)          P2 (স্টেশন ২)
   [G1][G2][G3]           [G4][G5]
        ↓                      ↓
      M1 (রাঁধুনি)          M2 (রাঁধুনি)
        ↓                      ↓
      CPU কোর ১             CPU কোর ২
```

**Work Stealing — সবচেয়ে চমৎকার অংশটা:**
P2-এর সারি খালি হয়ে গেলে সে বসে থাকে না — **P1-এর সারি থেকে কাজ চুরি করে নেয়!** ফলে কোনো কোর অলস বসে থাকে না।

> রেস্টুরেন্টে একজন রাঁধুনির অর্ডার শেষ হয়ে গেলে সে পাশের ব্যস্ত রাঁধুনির কিছু অর্ডার নিয়ে নেয়। কাজ সবসময় সমানভাবে ভাগ থাকে। ✅

**একটা goroutine যখন অপেক্ষায় থাকে:**
কোনো goroutine যদি ফাইল পড়ার বা নেটওয়ার্ক কলের জন্য অপেক্ষা করে, Go রানটাইম সেটাকে সরিয়ে রেখে ঐ থ্রেডে **অন্য goroutine** চালিয়ে দেয়। থ্রেডটা এক মুহূর্তও অলস থাকে না।

```go
runtime.GOMAXPROCS(0)      // বর্তমান মান জানতে
fmt.Println(runtime.NumCPU())  // কয়টা কোর আছে
```
Go ১.৫ থেকে ডিফল্টে `GOMAXPROCS = CPU কোরের সংখ্যা`।

## ১৫. Go-তে Race Condition কীভাবে সামলাবেন?

Race condition ধরতে **`-race` ফ্ল্যাগ** ব্যবহার করা যায়:
```bash
go run -race main.go
go test -race ./...
```

সামলানোর জন্য শেয়ার করা ডেটা লক করতে **`sync.Mutex`** ব্যবহার করুন, আর goroutine শেষ হওয়ার অপেক্ষা করতে **`sync.WaitGroup`**।

```go
var mu sync.Mutex
mu.Lock()
// ক্রিটিক্যাল সেকশন — একসাথে একজনই ঢুকতে পারবে
mu.Unlock()
```

**Race Condition আসলে কী — বাস্তব উদাহরণ:**

স্বামী-স্ত্রী দুজনেরই একই ব্যাংক অ্যাকাউন্ট, ব্যালেন্স ১০০০ টাকা। দুজনে **একই মুহূর্তে** দুইটা ATM থেকে ৮০০ টাকা তুলতে গেলেন।

```
সময়  স্বামীর ATM              স্ত্রীর ATM
 ১    ব্যালেন্স পড়ল: ১০০০
 ২                             ব্যালেন্স পড়ল: ১০০০
 ৩    ১০০০ ≥ ৮০০? হ্যাঁ ✅
 ৪                             ১০০০ ≥ ৮০০? হ্যাঁ ✅
 ৫    লিখল: ১০০০-৮০০ = ২০০
 ৬                             লিখল: ১০০০-৮০০ = ২০০
```
মোট ১৬০০ টাকা বেরিয়ে গেল, কিন্তু ব্যালেন্স দেখাচ্ছে ২০০! ব্যাংক ৮০০ টাকা হারাল। 💸

**কোডে সেই একই সমস্যা:**
```go
counter := 0
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++          // 💥 RACE!
    }()
}
wg.Wait()
fmt.Println(counter)   // ১০০০ আশা করেছিলেন, পাবেন ৯৭৩ বা ৯৯১...
```

`counter++` দেখতে একটা কাজ মনে হলেও আসলে তিনটা: **পড়ো → ১ যোগ করো → লেখো**। মাঝখানে অন্য goroutine ঢুকে পড়লেই গোলমাল।

**সমাধান ১ — Mutex:**
```go
var mu sync.Mutex
counter := 0
// ...
mu.Lock()
counter++
mu.Unlock()   // ✅ এখন ঠিক ১০০০ পাবেন
```

> **Mutex = বাথরুমের দরজার ছিটকিনি।** একজন ঢুকে ছিটকিনি দিল, বাকিরা বাইরে অপেক্ষা করে। বের হয়ে ছিটকিনি খুলে দিলে পরের জন ঢোকে।

**সমাধান ২ — Atomic (সাধারণ সংখ্যার জন্য দ্রুততর):**
```go
var counter int64
atomic.AddInt64(&counter, 1)
```

**সমাধান ৩ — Channel (Go-সুলভ পদ্ধতি):**
```go
ch := make(chan int)
go func() {
    sum := 0
    for v := range ch { sum += v }
}()
```
এখানে শুধু একটা goroutine-ই `sum`-এ হাত দিচ্ছে, তাই কোনো লক লাগছে না।

**⚠️ Mutex-এর নিয়ম:**
- সবসময় `defer mu.Unlock()` লিখুন — না হলে কোথাও `return` করলে চিরতরে লক হয়ে থাকবে (**deadlock**)
- ক্রিটিক্যাল সেকশন যত ছোট রাখা যায়, তত ভালো
- লক ধরে রেখে অন্য কোনো লক নেওয়ার চেষ্টা করবেন না → deadlock-এর সবচেয়ে সাধারণ কারণ

## ১৬. Go-তে Context কী এবং কেন গুরুত্বপূর্ণ?

`context` প্যাকেজ দিয়ে **ডেডলাইন, বাতিলের সংকেত (cancellation signal)** এবং রিকোয়েস্ট-সংক্রান্ত অন্যান্য মান API ও goroutine-এর মধ্যে বহন করা যায়। বিশেষত টাইমআউট সামলাতে এবং goroutine বাতিল করতে এটা খুবই কাজের।

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()

select {
case <-ctx.Done():
    fmt.Println("টাইমআউট বা বাতিল হয়েছে")
case result := <-ch:
    fmt.Println("পেলাম:", result)
}
```

**সমস্যাটা কী — বাস্তব উদাহরণ:**

একজন ব্যবহারকারী আপনার সাইটে সার্চ করল। সেই একটা রিকোয়েস্ট থেকে ভেতরে ভেতরে চলল:
```
API → ডেটাবেজ কল
    → রেকমেন্ডেশন সার্ভিস
    → স্টক চেক সার্ভিস
    → দাম হিসাবের সার্ভিস
```

**২ সেকেন্ড পর ব্যবহারকারী ব্রাউজার ট্যাব বন্ধ করে দিল।** কিন্তু আপনার সার্ভারে ঐ ৪টা কাজ **তখনো চলছে** — CPU খাচ্ছে, ডেটাবেজ কানেকশন ধরে রেখেছে, অথচ ফলাফলটা কেউ দেখবেই না। ১০০০ ব্যবহারকারী এমন করলে সার্ভার বসে যাবে। 💀

**Context এই সমস্যার সমাধান:** এটা একটা **সংকেতের তার** — এক জায়গা থেকে "বাতিল!" বললে পুরো চেইনে সবাই খবর পেয়ে যায়।

**তিন ধরনের Context:**

```go
// ১. টাইমআউট — "৩ সেকেন্ডের বেশি নয়"
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

// ২. হাতে বাতিল — "যখন বলব, থেমে যাবে"
ctx, cancel := context.WithCancel(context.Background())
go func() { time.Sleep(5*time.Second); cancel() }()

// ৩. মান বহন — "এই রিকোয়েস্টের সাথে এই আইডিটা নিয়ে চলো"
ctx = context.WithValue(ctx, "requestID", "abc-123")
```

**goroutine-এর ভেতরে যেভাবে সাড়া দেবেন:**
```go
func worker(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            fmt.Println("বন্ধ করছি:", ctx.Err())
            return                       // ✅ পরিষ্কারভাবে বেরিয়ে গেল
        default:
            // কাজ চালিয়ে যান
        }
    }
}
```

**⚠️ Context-এর নিয়ম:**
1. Context সবসময় ফাংশনের **প্রথম প্যারামিটার** হবে: `func Foo(ctx context.Context, ...)`
2. Struct-এর ভেতরে context রাখবেন না
3. `nil` context পাঠাবেন না — `context.TODO()` ব্যবহার করুন
4. **সবসময় `defer cancel()` লিখুন** — না হলে রিসোর্স লিক হবে
5. `WithValue` শুধু রিকোয়েস্ট-সংক্রান্ত ছোট তথ্যের জন্য (যেমন trace ID), ফাংশনের প্যারামিটার পাঠানোর জন্য নয়

## ১৭. `sync.Mutex` আর `sync.RWMutex`-এর পার্থক্য কী?

**`sync.Mutex`** পারস্পরিক বর্জন (mutual exclusion) দেয় — একসাথে মাত্র একটা goroutine ক্রিটিক্যাল সেকশনে ঢুকতে পারে।

**`sync.RWMutex`** একসাথে **অনেক পাঠক** (reader) ঢুকতে দেয়, কিন্তু **লেখক** (writer) একজনই। যেসব ক্ষেত্রে পড়ার কাজ অনেক বেশি হয়, সেখানে এটা খুব উপকারী — কারণ অনেক goroutine একসাথে পড়তে পারে।

```go
var rw sync.RWMutex

rw.RLock()      // পড়ার জন্য
// ... ডেটা পড়ুন ...
rw.RUnlock()

rw.Lock()       // লেখার জন্য
// ... ডেটা বদলান ...
rw.Unlock()
```

**বাস্তব উদাহরণ — নোটিশ বোর্ড:**

| কাজ | কতজন একসাথে? | কারণ |
|---|---|---|
| **পড়া** (RLock) | যত খুশি 👥👥👥 | ১০ জন একসাথে নোটিশ পড়লে কারও সমস্যা নেই |
| **লেখা** (Lock) | মাত্র একজন ✍️ | নোটিশ বদলানোর সময় কাউকে পড়তে দেওয়া যাবে না — অর্ধেক পুরনো, অর্ধেক নতুন পড়ে ফেলবে! |

**কখন কোনটা ব্যবহার করবেন:**

| পরিস্থিতি | ব্যবহার করুন |
|---|---|
| পড়া ও লেখা প্রায় সমান | `Mutex` (সহজ, কম ওভারহেড) |
| পড়া অনেক বেশি (৯০%+), লেখা কম | `RWMutex` ✅ |
| শুধু একটা সংখ্যা বাড়ানো-কমানো | `sync/atomic` (সবচেয়ে দ্রুত) |

**বাস্তব ব্যবহারের উদাহরণ — একটা ক্যাশ:**
```go
type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()                  // অনেকে একসাথে পড়তে পারবে ⚡
    defer c.mu.RUnlock()
    v, ok := c.data[key]
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()                   // লেখার সময় একচেটিয়া
    defer c.mu.Unlock()
    c.data[key] = value
}
```
একটা ক্যাশে সাধারণত ৯৯% কাজই `Get`। `RWMutex` ব্যবহার করায় হাজারো রিকোয়েস্ট একসাথে পড়তে পারছে, লাইনে দাঁড়াতে হচ্ছে না।

**⚠️ সতর্কতা:** `RWMutex` সাধারণ `Mutex`-এর চেয়ে একটু বেশি ভারী। পড়া-লেখার অনুপাত যদি খুব বেশি পড়ার দিকে ঝোঁকা না থাকে, তাহলে সাধারণ `Mutex`-ই দ্রুত হবে।

## ১৮. `panic` এবং `recover` ফাংশনের উদ্দেশ্য কী?

**`panic`:** প্রোগ্রামের স্বাভাবিক চলা থামিয়ে দেয়। ব্যতিক্রমী পরিস্থিতিতে এরর তোলার জন্য ব্যবহার করা যায়।

**`recover`:** panic হওয়া goroutine-এর নিয়ন্ত্রণ ফিরে পেতে ব্যবহার হয়। এটা শুধু একটা `defer` ফাংশনের ভেতরে কাজ করে।

```go
func main() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Panic থেকে রক্ষা পেলাম:", r)
        }
    }()
    panic("কিছু একটা গড়বড় হয়েছে")
}
// আউটপুট: Panic থেকে রক্ষা পেলাম: কিছু একটা গড়বড় হয়েছে
```

**panic হলে কী ঘটে:**
```
panic ঘটল
    ↓
সব defer ফাংশন উল্টো ক্রমে চলে
    ↓
কোনো recover পেল? → হ্যাঁ: স্বাভাবিক চলা ফিরে এল ✅
                    → না: প্রোগ্রাম ক্র্যাশ, stack trace ছাপে 💥
```

**⚠️ সবচেয়ে গুরুত্বপূর্ণ কথা — `panic` কে exception ভাববেন না!**

| পরিস্থিতি | কী করবেন |
|---|---|
| ব্যবহারকারী ভুল ইনপুট দিল | `return error` ✅ |
| ফাইল খুঁজে পাওয়া গেল না | `return error` ✅ |
| ডেটাবেজ সংযোগ ব্যর্থ | `return error` ✅ |
| প্রোগ্রামারের বাগ (nil pointer, index out of range) | `panic` (Go নিজেই করে) |
| প্রোগ্রাম চালুর সময় জরুরি কনফিগ নেই | `panic` গ্রহণযোগ্য |

**Go-এর দর্শন:** *এরর হলো স্বাভাবিক ব্যাপার, তাই সেগুলো রিটার্ন করো। Panic হলো "এই প্রোগ্রাম আর চলার যোগ্য নয়"।*

**`recover` কোথায় সত্যিই দরকার — ওয়েব সার্ভার:**
```go
func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Printf("panic: %v\n%s", err, debug.Stack())
                http.Error(w, "সার্ভারে সমস্যা হয়েছে", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```
একজন ব্যবহারকারীর রিকোয়েস্টে বাগ থাকলে শুধু **সেই রিকোয়েস্টটাই** ব্যর্থ হবে — পুরো সার্ভার ক্র্যাশ করে বাকি ১০,০০০ ব্যবহারকারীকে বিপদে ফেলবে না। ✅

**⚠️ একটা মারাত্মক ফাঁদ:** এক goroutine-এর `recover` অন্য goroutine-এর panic ধরতে পারে না!
```go
func main() {
    defer func() { recover() }()   // এটা কাজে আসবে না
    go func() {
        panic("boom")              // 💥 পুরো প্রোগ্রাম ক্র্যাশ
    }()
    time.Sleep(time.Second)
}
```
**নিয়ম:** প্রতিটা goroutine-কে **নিজের `recover` নিজে** রাখতে হবে।

## ১৯. Go-তে Variadic Function কী?

Variadic ফাংশন **যত খুশি তত আর্গুমেন্ট** নিতে পারে। প্যারামিটারের টাইপের আগে `...` লিখতে হয়।

```go
func sum(nums ...int) int {
    total := 0
    for _, num := range nums {
        total += num
    }
    return total
}

fmt.Println(sum(1, 2, 3, 4))   // আউটপুট: 10
fmt.Println(sum())             // আউটপুট: 0  (শূন্যটা আর্গুমেন্টও চলে)
```

**ভেতরে যা হয়:** `nums` আসলে একটা **slice** (`[]int`)। Go নিজে থেকেই আর্গুমেন্টগুলো একটা slice-এ ভরে দেয়।

**একটা slice পাঠাতে চাইলে `...` ব্যবহার করুন:**
```go
numbers := []int{1, 2, 3, 4, 5}
fmt.Println(sum(numbers...))   // slice-টা "ছড়িয়ে" দেওয়া হলো ✅
// sum(numbers) লিখলে কম্পাইল এরর হবে
```

**বাস্তব উদাহরণ:** সবচেয়ে পরিচিত variadic ফাংশনটা আপনি রোজই ব্যবহার করেন:
```go
fmt.Println("ক", "খ", "গ")      // যত খুশি আর্গুমেন্ট
// সংজ্ঞা: func Println(a ...interface{}) (n int, err error)
```

**⚠️ নিয়ম:** variadic প্যারামিটার সবসময় **সবার শেষে** থাকতে হবে।
```go
func log(level string, args ...interface{})   // ✅ ঠিক
func log(args ...interface{}, level string)   // ❌ কম্পাইল এরর
```

**একটা কাজের প্যাটার্ন — Functional Options:**
```go
type Server struct { host string; port int; timeout time.Duration }
type Option func(*Server)

func WithPort(p int) Option      { return func(s *Server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{host: host, port: 8080, timeout: 30 * time.Second}  // ডিফল্ট
    for _, opt := range opts { opt(s) }
    return s
}

// ব্যবহার — যা যা লাগে শুধু সেটাই দিন
srv := NewServer("localhost", WithPort(9000))
```
Go-তে ডিফল্ট প্যারামিটার নেই, তাই এই প্যাটার্নটা খুব জনপ্রিয়।

## ২০. Go-তে `select` স্টেটমেন্ট কী করে?

`select` স্টেটমেন্ট channel-এর সাথে ব্যবহার হয়, একাধিক channel অপারেশন সামলানোর জন্য। এটা একটা goroutine-কে **একসাথে কয়েকটা channel-এর জন্য অপেক্ষা** করার সুযোগ দেয়।

```go
func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)

    go func() { ch1 <- "hello" }()
    go func() { ch2 <- "world" }()

    select {
    case msg1 := <-ch1:
        fmt.Println("পেলাম:", msg1)
    case msg2 := <-ch2:
        fmt.Println("পেলাম:", msg2)
    }
}
```

**বাস্তব উদাহরণ:** `select` হলো **একজন রিসেপশনিস্ট**, যার সামনে ৩টা ফোন। যেটা আগে বাজবে, সেটাই ধরবে। কোনটা আগে বাজবে তা আগে থেকে জানা নেই — যেটাই আসুক, সাড়া দেওয়ার জন্য প্রস্তুত।

**`select`-এর নিয়ম:**
1. একাধিক case একসাথে প্রস্তুত থাকলে → Go **এলোমেলোভাবে** একটা বাছে (কেউ যেন অনাহারে না থাকে)
2. কোনোটাই প্রস্তুত না থাকলে → **অপেক্ষা করে** (`default` না থাকলে)
3. `default` থাকলে → অপেক্ষা না করে সাথে সাথে `default` চালায়

**সবচেয়ে দরকারি ব্যবহার — টাইমআউট:**
```go
select {
case result := <-slowAPI:
    fmt.Println("ফলাফল:", result)
case <-time.After(3 * time.Second):
    fmt.Println("টাইমআউট! ৩ সেকেন্ড অপেক্ষা করেছি")   // ⏰
}
```
কোনো API যদি ঝুলে যায়, আপনার প্রোগ্রাম চিরকাল আটকে থাকবে না।

**ব্লক না হয়ে চেক করা (`default` দিয়ে):**
```go
select {
case msg := <-ch:
    fmt.Println("বার্তা:", msg)
default:
    fmt.Println("এখন কোনো বার্তা নেই")   // অপেক্ষা না করেই এগিয়ে গেল
}
```

**বাতিলযোগ্য ওয়ার্কার (সবচেয়ে বেশি ব্যবহৃত প্যাটার্ন):**
```go
for {
    select {
    case job := <-jobs:
        process(job)
    case <-ctx.Done():
        return                 // পরিষ্কারভাবে বন্ধ ✅
    }
}
```

**⚠️ চিরকাল ব্লক:** `select {}` (খালি) লিখলে চিরকাল অপেক্ষা করবে → deadlock।

## ২১. `sync.WaitGroup`-এর উদ্দেশ্য কী?

`sync.WaitGroup` ব্যবহার হয় একগুচ্ছ goroutine শেষ হওয়া পর্যন্ত অপেক্ষা করার জন্য। প্রতিটা goroutine-এর জন্য কাউন্টার বাড়ান, আর goroutine শেষ হলে `Done()` ডাকুন। `Wait()` ততক্ষণ ব্লক করে রাখে যতক্ষণ না কাউন্টার শূন্য হয়।

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    fmt.Println("Goroutine শেষ")
}()
wg.Wait()
```

**তিনটা মেথড:**

| মেথড | কাজ | উপমা |
|---|---|---|
| `Add(n)` | কাউন্টার n বাড়ায় | "৩ জন কর্মী পাঠাচ্ছি" |
| `Done()` | কাউন্টার ১ কমায় | "আমার কাজ শেষ" |
| `Wait()` | কাউন্টার ০ না হওয়া পর্যন্ত ব্লক | "সবাই শেষ করলে ডেকো" |

**বাস্তব উদাহরণ — স্কুল বাস:**
ড্রাইভার গুনে রাখলেন **৩০ জন ছাত্র** নেমেছে (`Add(30)`)। প্রতিটা ছাত্র ফিরে এসে হাজিরা দিল (`Done()`)। ৩০ জনই না ফেরা পর্যন্ত বাস ছাড়বে না (`Wait()`)।

**পূর্ণাঙ্গ বাস্তব উদাহরণ — সমান্তরালে ৫টা API কল:**
```go
func fetchAll(urls []string) []string {
    var wg sync.WaitGroup
    results := make([]string, len(urls))

    for i, url := range urls {
        wg.Add(1)
        go func(idx int, u string) {
            defer wg.Done()
            resp, _ := http.Get(u)
            results[idx] = readBody(resp)      // আলাদা index, তাই race নেই ✅
        }(i, url)
    }

    wg.Wait()        // পাঁচটাই শেষ হওয়ার অপেক্ষা
    return results
}
```
একটা একটা করে করলে ৫ × ২ সেকেন্ড = **১০ সেকেন্ড**। একসাথে করলে মাত্র **২ সেকেন্ড**। ⚡

**⚠️ তিনটা কমন ভুল:**

**১) `Add()` goroutine-এর ভেতরে লেখা:**
```go
go func() {
    wg.Add(1)      // ❌ Wait() হয়তো এর আগেই চলে যাবে!
    defer wg.Done()
}()
```
সবসময় `go` লেখার **আগেই** `Add()` করুন।

**২) `Done()` ভুলে যাওয়া** → `Wait()` চিরকাল আটকে থাকবে (deadlock)। তাই সবসময় `defer wg.Done()` লিখুন।

**৩) `WaitGroup` কপি করে ফেলা:**
```go
func work(wg sync.WaitGroup) { }   // ❌ কপি হয়ে গেল, আসলটা কখনো শূন্য হবে না
func work(wg *sync.WaitGroup) { }  // ✅ পয়েন্টার দিন
```

## ২২. Buffered ও Unbuffered Channel-এর পার্থক্য কী?

**Unbuffered Channel:**
- ধারণক্ষমতা শূন্য।
- পাঠানো ও গ্রহণ — দুই পক্ষই প্রস্তুত না হওয়া পর্যন্ত **দুজনেই অপেক্ষা করে**।
- goroutine-দের মধ্যে সমন্বয়ের (synchronization) জন্য ব্যবহার হয়।
```go
ch := make(chan int)       // unbuffered
```

**Buffered Channel:**
- ধারণক্ষমতা শূন্যের বেশি।
- Channel **পুরো ভরে না যাওয়া পর্যন্ত** পাঠানো ব্লক হয় না, আর **খালি না হওয়া পর্যন্ত** গ্রহণ ব্লক হয় না।
- গ্রহীতা সাথে সাথে না থাকলেও নির্দিষ্ট সংখ্যক মান জমা রাখা যায়।
```go
ch := make(chan int, 5)    // ৫ ধারণক্ষমতার buffered channel
```

**বাস্তব উদাহরণ:**

**Unbuffered = হাতে হাতে জিনিস দেওয়া 🤝**
আপনি বন্ধুকে একটা বই দিতে চান। বন্ধু হাত না বাড়ানো পর্যন্ত আপনি দাঁড়িয়ে থাকবেন। আর বন্ধুও হাত বাড়িয়ে আপনার জন্য অপেক্ষা করবে। **দুজনকেই একই মুহূর্তে থাকতে হবে।**

**Buffered = টেবিলের উপর রেখে যাওয়া 📦**
টেবিলে ৫টা বই রাখার জায়গা আছে। আপনি বই রেখে চলে গেলেন — বন্ধু কখন নেবে সেটা আপনার সমস্যা নয়। কিন্তু টেবিল ভরে গেলে (৫টা হয়ে গেলে) আপনাকে অপেক্ষা করতেই হবে।

**পাশাপাশি আচরণ:**

| অবস্থা | Unbuffered | Buffered (cap=3) |
|---|---|---|
| পাঠানো, কেউ নিচ্ছে না | ব্লক 🛑 | চলবে (৩টা পর্যন্ত) ✅ |
| ৪র্থ বার পাঠানো (৩টা ভরা) | — | ব্লক 🛑 |
| খালি channel থেকে নেওয়া | ব্লক 🛑 | ব্লক 🛑 |

**Deadlock-এর ফাঁদ:**
```go
func main() {
    ch := make(chan int)
    ch <- 1              // 💥 fatal error: all goroutines are asleep - deadlock!
    fmt.Println(<-ch)
}
```
কেউ নেওয়ার জন্য নেই, তাই `ch <- 1` চিরকাল অপেক্ষা করবে। সমাধান — হয় `make(chan int, 1)` করুন, নয়তো আলাদা goroutine-এ নিন।

**কখন কোনটা:**

| দরকার | ব্যবহার করুন |
|---|---|
| দুই goroutine-কে সমন্বিত রাখা ("কাজ শেষ হলে জানাও") | Unbuffered |
| Producer আর Consumer-এর গতি আলাদা | Buffered |
| একসাথে কতগুলো কাজ চলবে সীমিত রাখা | Buffered (semaphore হিসেবে) |
| নিশ্চিত হতে হবে মেসেজটা সত্যিই পৌঁছেছে | Unbuffered |

**⚠️ বড় buffer সমস্যা লুকিয়ে রাখে।** Buffer বাড়িয়ে দিলে সমস্যাটা দেরিতে ধরা পড়ে — Consumer ধীর হলে buffer ভরতে ভরতে হঠাৎ একদিন সব আটকে যাবে। ছোট buffer দিয়ে শুরু করুন, মেপে তারপর বাড়ান।

## ২৩. Interface-এর সাথে Type Assertion কীভাবে ব্যবহার করবেন?

```go
var i interface{} = "hello"

str, ok := i.(string)
if ok {
    fmt.Println(str)   // আউটপুট: hello
}
```

**Type assertion কী:** একটা interface-এর ভেতরে আসলে কী টাইপের মান আছে, সেটা বের করে আনা।

**দুইটা রূপ:**

```go
// ১. নিরাপদ রূপ (সবসময় এটা ব্যবহার করুন) ✅
str, ok := i.(string)
if !ok {
    fmt.Println("এটা string নয়")
}

// ২. ঝুঁকিপূর্ণ রূপ ❌
str := i.(string)   // ভুল টাইপ হলে সাথে সাথে panic! 💥
```

**বাস্তব উদাহরণ:** একটা **বন্ধ বাক্স** পেলেন যাতে লেখা "কিছু একটা আছে"। ভেতরে কী আছে জানতে খুলতে হবে।
- নিরাপদ রূপ: "এটা কি বই? হ্যাঁ/না বলো" → না হলেও সমস্যা নেই
- ঝুঁকিপূর্ণ রূপ: "এটা বই, দাও!" → বই না হলে আপনি হতভম্ব হয়ে পড়বেন (panic)

**Type Switch — একাধিক টাইপ চেক করতে সবচেয়ে ভালো:**
```go
func describe(i interface{}) {
    switch v := i.(type) {
    case string:
        fmt.Printf("string, দৈর্ঘ্য %d\n", len(v))
    case int:
        fmt.Printf("int, দ্বিগুণ করলে %d\n", v*2)
    case []int:
        fmt.Printf("int-এর slice, %d টা এলিমেন্ট\n", len(v))
    case nil:
        fmt.Println("কিছুই নেই")
    default:
        fmt.Printf("অজানা টাইপ: %T\n", v)
    }
}
```

**বাস্তবে যেখানে সবচেয়ে বেশি লাগে — এরর হ্যান্ডলিং:**
```go
if err != nil {
    var netErr net.Error
    if errors.As(err, &netErr) && netErr.Timeout() {
        // নেটওয়ার্ক টাইমআউট → আবার চেষ্টা করা যায়
        return retry()
    }
    return err
}
```

**💡 পরামর্শ:** `interface{}` (বা Go ১.১৮+ এ `any`) যত কম ব্যবহার করা যায় তত ভালো। এটা টাইপ সেফটি নষ্ট করে দেয়। আধুনিক Go-তে অনেক ক্ষেত্রে **Generics** ব্যবহার করাই ভালো:
```go
func Max[T int | float64](a, b T) T {
    if a > b { return a }
    return b
}
```

## ২৪. Goroutine Leak কীভাবে ঠেকাবেন?

**Goroutine Leak কী:** যখন একটা goroutine-এর আর দরকার নেই, কিন্তু সেটা তখনো চলছে — প্রায়ই এমন কোনো channel-এর জন্য অপেক্ষা করছে যেখানে কখনো কিছু আসবে না।

**ঠেকানোর উপায়:**
- **`select` এর সাথে `default` ব্যবহার করুন:** যাতে channel-এ চিরকাল আটকে না থাকে।
- **`context.Context` ব্যবহার করুন:** goroutine-এ একটা context পাঠান এবং `context.WithCancel` বা `context.WithTimeout` দিয়ে থামার সংকেত দিন।
- **ঠিকভাবে channel বন্ধ করুন:** channel বন্ধ করলে গ্রহীতা goroutine-গুলো বুঝতে পারে আর কিছু আসবে না, এবং বেরিয়ে যেতে পারে।

**লিক দেখতে কেমন হয়:**
```go
func leaky() {
    ch := make(chan int)      // unbuffered
    go func() {
        val := <-ch           // 🚨 চিরকাল অপেক্ষা করবে
        fmt.Println(val)
    }()
    return                    // কেউ কিছু পাঠাল না, goroutine আটকে রইল
}
```
এই ফাংশনটা ১০,০০০ বার ডাকলে **১০,০০০টা goroutine** মেমরি খেয়ে বসে থাকবে। প্রোগ্রাম বন্ধ না হওয়া পর্যন্ত এরা মরবে না। 💀

**বাস্তব উদাহরণ:** একজন কর্মচারীকে বললেন "গুদামে যাও, মাল এলে খবর দিও।" তারপর আপনি ভুলে গেলেন, আর মালও কখনো এল না। কর্মচারী **বছরের পর বছর গুদামে দাঁড়িয়ে থাকল**, বেতনও নিতে থাকল। এটাই goroutine leak।

**সমাধান ১ — Context:**
```go
func noLeak(ctx context.Context) {
    ch := make(chan int)
    go func() {
        select {
        case val := <-ch:
            fmt.Println(val)
        case <-ctx.Done():
            return              // ✅ সংকেত পেলে বেরিয়ে যায়
        }
    }()
}
```

**সমাধান ২ — Buffered channel (পাঠানো ব্লক হবে না):**
```go
ch := make(chan int, 1)   // গ্রহীতা না থাকলেও পাঠানো যাবে
```

**সমাধান ৩ — সবসময় channel বন্ধ করুন:**
```go
go func() {
    defer close(ch)         // ✅ শেষ হলে জানিয়ে দেয়
    for _, v := range data { ch <- v }
}()

for v := range ch { }      // close() পেলে লুপ থামবে
```

**লিক খুঁজে বের করার উপায়:**
```go
fmt.Println("Goroutine সংখ্যা:", runtime.NumGoroutine())
```
সংখ্যাটা যদি সময়ের সাথে **শুধু বাড়তেই থাকে** আর কখনো না কমে — নিশ্চিত লিক আছে। বিস্তারিত দেখতে:
```bash
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**💡 সোনালি নিয়ম:** *goroutine বানানোর আগেই ঠিক করে নিন সেটা কীভাবে শেষ হবে।* উত্তর না জানা থাকলে goroutine বানাবেন না।

## ২৫. Worker Pool কী এবং Go-তে কীভাবে বানাবেন?

**Worker Pool** হলো এমন একটা প্যাটার্ন, যেখানে কয়েকটা worker goroutine বানিয়ে কাজগুলো তাদের মধ্যে ভাগ করে দেওয়া হয় — যাতে কাজের ভার দক্ষভাবে বণ্টিত হয়।

```go
func worker(id int, jobs <-chan int, results chan<- int) {
    for job := range jobs {
        fmt.Printf("Worker %d কাজ %d করছে\n", id, job)
        results <- job * 2
    }
}

func main() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)

    // ৩ জন worker চালু করলাম
    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results)
    }

    // ৫টা কাজ পাঠালাম
    for j := 1; j <= 5; j++ {
        jobs <- j
    }
    close(jobs)

    // ৫টা ফলাফল সংগ্রহ করলাম
    for a := 1; a <= 5; a++ {
        fmt.Println(<-results)
    }
}
```

**বাস্তব উদাহরণ — ব্যাংকের কাউন্টার:**
- **কাজের সারি (`jobs`)** = টোকেন নিয়ে অপেক্ষারত গ্রাহকদের লাইন
- **Worker** = ৩ জন ক্যাশিয়ার
- প্রতিটা ক্যাশিয়ার লাইন থেকে পরের গ্রাহককে ডেকে নেয়, কাজ শেষ করে আবার পরের জনকে ডাকে

**Worker Pool কেন দরকার — সীমাহীন goroutine বানালে কী হয়:**
```go
// ❌ বিপজ্জনক
for _, url := range oneMillionURLs {
    go fetch(url)      // ১০ লক্ষ goroutine একসাথে!
}
```
১০ লক্ষ HTTP কানেকশন একসাথে → সার্ভার ক্র্যাশ, টার্গেট সাইট DDoS হয়ে যাবে, মেমরি শেষ। 💥

Worker Pool দিয়ে একসাথে সর্বোচ্চ কতগুলো কাজ চলবে সেটা **নিয়ন্ত্রণে থাকে**। ✅

**⚠️ উপরের কোডে একটা লুকানো সমস্যা:** `results` channel-এর buffer যদি ভরে যায়, worker-রা আটকে যাবে। উৎপাদনে যাওয়ার মতো সংস্করণ:

```go
func workerPool(jobs []int, numWorkers int) []int {
    jobsCh := make(chan int, len(jobs))
    resultsCh := make(chan int, len(jobs))
    var wg sync.WaitGroup

    for w := 1; w <= numWorkers; w++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for job := range jobsCh {
                resultsCh <- job * 2
            }
        }(w)
    }

    for _, j := range jobs { jobsCh <- j }
    close(jobsCh)

    wg.Wait()          // সব worker শেষ হোক
    close(resultsCh)   // তারপর results বন্ধ করুন

    var out []int
    for r := range resultsCh { out = append(out, r) }
    return out
}
```

### Semaphore প্যাটার্ন (আরেকটা উপায়)

```go
package main

import (
    "fmt"
    "sync"
)

func worker(id int, sem chan struct{}, wg *sync.WaitGroup) {
    defer wg.Done()
    sem <- struct{}{}          // একটা স্লট দখল করলাম
    defer func() {
        <-sem                  // স্লটটা ছেড়ে দিলাম
    }()
    fmt.Printf("Worker %d কাজ করছে\n", id)
    // এখানে আপনার কাজ
}

func main() {
    numWorkers := 3
    sem := make(chan struct{}, numWorkers)
    var wg sync.WaitGroup

    for i := 1; i <= numWorkers; i++ {
        wg.Add(1)
        go worker(i, sem, &wg)
    }

    wg.Wait()
}
```

**Semaphore-এর ধারণাটা বুঝুন:**

`sem` হলো একটা **সীমিত জায়গার পার্কিং লট** (এখানে ৩টা স্লট)।
- `sem <- struct{}{}` = একটা স্লটে গাড়ি রাখলাম। লট ভরা থাকলে অপেক্ষা করতে হবে 🛑
- `<-sem` = গাড়ি সরিয়ে নিলাম, স্লট খালি হলো ✅

**`struct{}{}` কেন?** খালি struct **শূন্য বাইট** মেমরি নেয়! আমরা তো ডেটা পাঠাচ্ছি না, শুধু "একটা জায়গা দখল হলো" এই সংকেতটা দিচ্ছি। `bool` ব্যবহার করলে অযথা ১ বাইট করে খরচ হতো।

**Worker Pool বনাম Semaphore:**

| | Worker Pool | Semaphore |
|---|---|---|
| goroutine তৈরি হয় | নির্দিষ্ট কয়েকটা, পুনর্ব্যবহৃত হয় | প্রতিটা কাজের জন্য নতুন |
| কখন ভালো | কাজ অনেক বেশি, কাজগুলো ছোট | কাজ কম, কিন্তু প্রতিটা ভারী |
| ওভারহেড | কম (goroutine বারবার বানাতে হয় না) | একটু বেশি |

## ২৬. `sync.Once` কেন ব্যবহার করবেন?

`sync.Once` নিশ্চিত করে যে একটা নির্দিষ্ট কোড **মাত্র একবারই চলবে** — এমনকি একাধিক goroutine থেকে ডাকা হলেও। সাধারণত lazy initialization বা singleton প্যাটার্নে এটা ব্যবহার হয়।

```go
var once sync.Once

func initialize() {
    fmt.Println("চালু করা হলো")
}

func main() {
    for i := 0; i < 5; i++ {
        go once.Do(initialize)
    }
    time.Sleep(1 * time.Second)
}
// আউটপুট: চালু করা হলো   ← ৫ বার নয়, মাত্র একবার! ✅
```

**বাস্তব উদাহরণ — অফিসের এসি:**
সকালে ১০ জন কর্মচারী অফিসে ঢুকল। প্রত্যেকেই ভাবল "এসিটা চালু করি"। কিন্তু এসি তো **একবারই** চালু করা দরকার। `sync.Once` হলো সেই নিয়ম — প্রথম যে সুইচ টিপবে, তারই কাজ হবে; বাকিরা টিপলেও কিছু হবে না।

**বাস্তবে সবচেয়ে বেশি ব্যবহার — ডেটাবেজ কানেকশন:**
```go
var (
    db     *sql.DB
    dbOnce sync.Once
)

func GetDB() *sql.DB {
    dbOnce.Do(func() {
        var err error
        db, err = sql.Open("postgres", connStr)
        if err != nil {
            log.Fatal(err)
        }
        db.SetMaxOpenConns(25)
    })
    return db
}
```
১০০০টা goroutine একসাথে `GetDB()` ডাকলেও কানেকশন পুল **মাত্র একবার** তৈরি হবে। ✅

**`sync.Once` ছাড়া করলে কী হয়:**
```go
// ❌ Race condition!
if db == nil {
    db = connectDB()    // দুই goroutine একসাথে ঢুকে দুইটা কানেকশন বানিয়ে ফেলতে পারে
}
```

**`sync.Once`-এর গুরুত্বপূর্ণ বৈশিষ্ট্য:**
1. প্রথম কলটা চলার সময় **বাকি সব কল অপেক্ষা করে** — কাজ শেষ হলে তবেই এগোয়। তাই "অর্ধেক তৈরি" অবস্থায় কেউ ব্যবহার করতে পারে না।
2. ভেতরের ফাংশন panic করলেও Go সেটাকে "চলে গেছে" ধরে নেয় — আর কখনো চালাবে না। ⚠️
3. একটা `Once` ভেরিয়েবল **একটাই কাজের জন্য**। রিসেট করা যায় না।

**⚠️ ভুল ব্যবহার:**
```go
func doSomething() {
    var once sync.Once          // ❌ প্রতিবার নতুন Once তৈরি হচ্ছে!
    once.Do(initialize)         // ফলে প্রতিবারই চলবে
}
```
`Once` অবশ্যই **প্যাকেজ লেভেলে** বা struct-এর ফিল্ড হিসেবে রাখতে হবে।

## 📌 দ্রুত রিভিশন চিট-শিট

### কনকারেন্সির টুলগুলো — কখন কোনটা

| দরকার | ব্যবহার করুন |
|---|---|
| goroutine-দের মধ্যে ডেটা পাঠানো | `channel` |
| শেয়ার করা ভেরিয়েবল রক্ষা করা | `sync.Mutex` |
| পড়া অনেক বেশি, লেখা কম | `sync.RWMutex` |
| শুধু একটা কাউন্টার | `sync/atomic` |
| সব goroutine শেষ হওয়ার অপেক্ষা | `sync.WaitGroup` |
| কোড মাত্র একবার চালানো | `sync.Once` |
| একাধিক channel-এ অপেক্ষা / টাইমআউট | `select` |
| goroutine বাতিল বা টাইমআউট | `context` |
| একসাথে কতগুলো কাজ চলবে সীমিত রাখা | Worker Pool / Semaphore |

### যে ভুলগুলো জুনিয়ররা সবচেয়ে বেশি করে

1. ❌ `make` ছাড়া map ব্যবহার → panic
2. ❌ লুপের ভেতরে `defer` → রিসোর্স জমতে থাকে
3. ❌ `go` লেখার পরে `wg.Add(1)` → রেস
4. ❌ Mutex-এ `defer Unlock()` না লেখা → deadlock
5. ❌ `cancel()` না ডাকা → context লিক
6. ❌ Slice কপি ভেবে নেওয়া → আসলে মেমরি শেয়ার করে
7. ❌ এররের জায়গায় `panic` ব্যবহার → Go-এর দর্শনের বিরুদ্ধে
8. ❌ goroutine-এর শেষ হওয়ার উপায় ঠিক না করা → লিক

### কাজের কমান্ড

```bash
go run -race main.go        # race condition ধরতে
go vet ./...                # সন্দেহজনক কোড ধরতে
gofmt -w .                  # কোড ফরম্যাট করতে
go test -cover ./...        # টেস্ট কভারেজ
go build -gcflags="-m"      # কোন ভেরিয়েবল হিপে যাচ্ছে দেখতে
GOOS=linux go build         # অন্য OS-এর জন্য বাইনারি
```

### মনে রাখার মতো তিনটা মূলমন্ত্র

1. *"Don't communicate by sharing memory; share memory by communicating."* → channel ব্যবহার করুন
2. *"Concurrency is not parallelism."* → একটা ডিজাইন, আরেকটা বাস্তবায়ন
3. *"Errors are values."* → এরর ছুঁড়ে ফেলবেন না, রিটার্ন করুন
